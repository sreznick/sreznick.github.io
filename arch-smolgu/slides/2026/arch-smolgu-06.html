Загрузка ЭВМ

От включения питания до работающей ОС

  • Что происходит между нажатием кнопки Power и рабочим столом
  • Каждый этап — отдельная программа со своей задачей
  • Почему этапов так много и что было бы без каждого

Карта пути

  • ПЗУ (Reset Vector) → код вендора
  • BIOS/UEFI → поиск загрузчика
  • MBR → загрузчик (GRUB)
  • Загрузчик → ядро ОС
  • Ядро → первый процесс (PID 1)
  • PID 1 → все остальные процессы

Это лестница: каждый этап передаёт управление следующему

Принцип: каждый этап продолжает работу предыдущего

  • ПЗУ не знает про ОС
  • BIOS не знает про загрузчики
  • MBR не знает про ядро
  • Каждый слой — интерфейс, скрывающий сложность

Структура лекции

Этап 0: Reset Vector

  • Что: процессор включается и исполняет код по фиксированному адресу (0xFFFFFFF0)
  • Зачем: процессору нужно сказать, где первая инструкция
  • Без него: процессор не знает, что исполнять — компьютер просто висит
# Аппаратно зашитый адрес
# 0xFFFFFFF0 — последние 16 байт 4 ГБ
# Туда отображается ПЗУ с кодом вендора

Этап 1: Код вендора (BIOS/UEFI)

  • Что: программа из ПЗУ инициализирует железо: память, контроллеры, видео, диски
  • Зачем: ОС слишком сложная, чтобы стартовать с нуля — ей нужен рабочий компьютер
  • Без него: ОС должна знать все детали конкретной материнки — жёсткая связка железо-ОС

Этап 2: Поиск загрузчика

  • Что: BIOS/UEFI ищут устройство с загрузочным кодом (диск, USB, сеть)
  • Зачем: BIOS не знает про ОС — он только находит код и передаёт управление
  • Без него: BIOS должен уметь грузить все ОС — распух бы до размера ОС

Этап 3: MBR

  • Что: первый сектор диска (512 байт): код (446) + таблица разделов (64) + сигнатура (2)
  • Зачем: стандартный интерфейс: BIOS проверяет сигнатуру 0xAA55 и прыгает на код
  • Без него: BIOS должен знать про каждый загрузчик в мире

Этап 4: Загрузчик (Bootloader)

  • Что: программа, которая умеет грузить ядро ОС (GRUB, Windows Boot Manager)
  • Зачем: ядро не помещается в 512 байт MBR — нужен посредник
  • Без него: MBR-код должен сам переключать режимы, читать ФС, грузить ELF

Этап 5: Ядро ОС

  • Что: получает управление от загрузчика, инициализирует драйверы, память, планировщик
  • Зачем: точка входа в ОС — всё до этого было подготовкой
  • Без него: загрузчик передал бы управление в никуда

Этап 6: Userspace

  • Что: PID 1 (init/systemd) запускает службы, появляется логин, shell, рабочий стол
  • Зачем: ядро — менеджер ресурсов, пользователю нужны программы
  • Без него: система загрузилась, но ничего не делает

Итоговая схема

ПЗУ → BIOS/UEFI → MBR → Загрузчик → Ядро → PID 1 → Userspace
 │         │         │        │         │        │
 │         │         │        │         │        └─ без него: нет программ
 │         │         │        │         └─ без него: нечего запускать
 │         │         │        └─ без него: ядро не влезает в 512 байт
 │         │         └─ без него: BIOS не знает про загрузчики
 │         └─ без него: ОС привязана к железу
 └─ без него: процессор не знает, что исполнять

Ключевая мысль

  • Каждый этап — интерфейс
  • Каждый скрывает сложность нижележащего
  • Каждый решает проблему предыдущего
  • Убираете любой — всё разваливается

Диски: базовые понятия

  • Диск — массив секторов
  • Сектор — минимальная адресуемая единица (512 байт)
  • LBA (Logical Block Address) — просто номер сектора от 0 до N
  • BIOS читает сектора по номеру

MBR: структура (512 байт)

┌─────────────────────────────────────────┐
│ 446 байт — код загрузчика               │
├─────────────────────────────────────────┤
│ 64 байта — таблица разделов (4 × 16)    │
├─────────────────────────────────────────┤
│ 2 байта — сигнатура 0xAA55              │
└─────────────────────────────────────────┘
  • Сигнатура — признак загрузочного сектора
  • BIOS проверяет её перед передачей управления

Разделы (Partitions)

  • Диск делится на разделы (C:, D:, /dev/sda1...)
  • Каждый раздел — непрерывная область секторов
  • Внутри раздела — файловая система (NTFS, ext4, FAT32)
  • Один раздел помечается как активный (загрузочный)

VBR (Volume Boot Record)

  • Первый сектор раздела
  • MBR-код читает его и передаёт управление
  • VBR — вторая стадия загрузки
  • Умеет больше, чем MBR (может читать ФС)

GPT: замена MBR

  • Таблица разделов не в первом секторе, а после него
  • Поддерживает диски больше 2 ТБ
  • Не ограничена 4 разделами
  • Резервная копия таблицы в конце диска
  • Используется с UEFI

EFI System Partition (ESP)

  • Раздел с файловой системой FAT32
  • Содержит загрузчики (.efi файлы)
  • UEFI читает его напрямую
  • Не нужен классический MBR

QEMU: пустой диск

# Создаём пустой образ
dd if=/dev/zero of=disk.img bs=512 count=2048

# Запускаем — BIOS не находит загрузчик
qemu-system-x86_64 -drive format=raw,file=disk.img

# Результат: "No bootable device"

BIOS прошёл все устройства, ничего не нашёл — и остановился.

QEMU: диск с сигнатурой, но без кода

# Записываем сигнатуру 0xAA55 в конец первого сектора
printf '\x55\xAA' | dd of=disk.img bs=1 seek=510 conv=notrunc

# Запускаем
qemu-system-x86_64 -drive format=raw,file=disk.img

# BIOS нашёл сигнатуру, прыгнул на 0x7C00
# А там нули — процессор исполняет мусор и падает

QEMU: Reset Vector

# Лог первых инструкций процессора
qemu-system-x86_64 -d int,cpu_reset -D qemu.log

# В логе:
# CS=0xF000 IP=0xFFF0
# Первая инструкция — из ПЗУ по адресу 0xFFFFFFF0

Процессор «просыпается» в 16-битном режиме, даже если он 64-битный.

QEMU: свой код в ПЗУ

# Собираем свой firmware
nasm -f bin my_firmware.asm -o my_firmware.bin

# Запускаем с нашим ПЗУ
qemu-system-x86_64 -bios my_firmware.bin
; my_firmware.asm
[bits 16]
mov ah, 0x0E
mov al, 'F'
int 0x10
jmp $

Linker script для ПЗУ

OUTPUT_FORMAT(binary)
ENTRY(_start)

SECTIONS
{
    . = 0xFFFF0000;  /* адрес, куда QEMU поместит ПЗУ */
    .text : {
        *(.text)
    }
}

Настоящий код вендора занимает мегабайты. Наш — 64 КБ, для демонстрации достаточно.

QEMU: BIOS (SeaBIOS)

# Дефолтный BIOS от QEMU
qemu-system-x86_64 -d int,cpu_reset -D qemu.log

# В логе видно, как SeaBIOS:
# 1. Инициализирует память
# 2. Ищет видео
# 3. Проверяет клавиатуру
# 4. Ищет загрузочные устройства

Это и есть «код вендора» — он исполняется до вашей ОС.

QEMU: рабочий MBR

; mbr.asm
[org 0x7C00]
mov ah, 0x0E
mov al, 'M'
int 0x10
jmp $
times 510-($-$$) db 0
dw 0xAA55

# Сборка и запуск
nasm -f bin mbr.asm -o mbr.bin
dd if=mbr.bin of=disk.img conv=notrunc
qemu-system-x86_64 -drive format=raw,file=disk.img

На экране — буква 'M'. BIOS передал управление нашему коду.

Linker script для MBR

OUTPUT_FORMAT(binary)
ENTRY(_start)

SECTIONS
{
    . = 0x7C00;  /* адрес, куда BIOS загружает MBR */
    .text : {
        *(.text)
    }
    . = 0x7DFE;  /* сигнатура в конце сектора */
    .sig : {
        SHORT(0xAA55)
    }
}

Чтение диска: int 0x13

; Чтение сектора 2 (LBA 1) в память по адресу 0x8000
mov ah, 0x02        ; функция: чтение секторов
mov al, 0x01        ; количество: 1
mov ch, 0x00        ; цилиндр 0
mov cl, 0x02        ; сектор 2
mov dh, 0x00        ; головка 0
mov dl, 0x80        ; диск: первый жёсткий
mov bx, 0x8000      ; адрес буфера
mov es, bx
mov bx, 0x0000
int 0x13            ; вызов BIOS
jc .error           ; CF=1 — ошибка

Это делает код в MBR: читает следующий сектор и передаёт управление.

Цепочка загрузки

MBR (446 байт)
  │
  │ читает VBR (первый сектор раздела)
  ▼
VBR (512 байт)
  │
  │ читает следующий кусок загрузчика
  ▼
GRUB stage 2 (несколько КБ)
  │
  │ читает ядро с файловой системы
  ▼
Ядро ОС

Каждый этап — чуть больше возможностей, чуть больше кода.

QEMU: ядро напрямую

# QEMU сам загружает ядро, минуя BIOS/MBR/загрузчик
qemu-system-x86_64 -kernel vmlinuz -initrd initrd.img \
    -append "console=ttyS0" -nographic

# Удобно для отладки, но скрывает весь путь загрузки

QEMU делает работу загрузчика: грузит ядро в память и передаёт управление.

Linker script для ядра

OUTPUT_FORMAT(binary)
ENTRY(_start)

SECTIONS
{
    . = 0x100000;  /* 1 МБ — стандартный адрес загрузки ядра */
    .text : {
        *(.text)
    }
    .rodata : {
        *(.rodata)
    }
    .data : {
        *(.data)
    }
    .bss : {
        *(.bss)
    }
}

QEMU: userspace

# Ядро монтирует initramfs и запускает /bin/sh как PID 1
qemu-system-x86_64 -kernel vmlinuz -initrd initramfs.cpio.gz \
    -append "rdinit=/bin/sh console=ttyS0" -nographic

# Сразу shell, без единого диска

Всё в памяти. Нет жёсткого диска, нет разделов — только ядро и initramfs.

Отладка: видеобуфер

; Видеопамять по адресу 0xB8000
; Каждые 2 байта = символ + атрибут (цвет)

mov ax, 0xB800
mov es, ax
mov byte [es:0x00], 'A'   ; символ
mov byte [es:0x01], 0x07  ; белый на чёрном
jmp $

Не нужны прерывания BIOS. Просто запись в память — символ появляется на экране.

Отладка: семафоры

; Точка A
mov byte [es:0x00], 'A'
; ... какой-то код ...
; Точка B
mov byte [es:0x02], 'B'
; ... какой-то код ...
; Точка C
mov byte [es:0x04], 'C'

Если на экране 'AB', но нет 'C' — падение между B и C.

Отладка: лог инструкций

# Каждая исполненная инструкция с адресом и байтами
qemu-system-x86_64 -d in_asm -D qemu.log \
    -drive format=raw,file=disk.img

# С регистрами:
qemu-system-x86_64 -d in_asm,int,cpu_reset -D qemu.log \
    -drive format=raw,file=disk.img

Видно, что именно исполняет процессор и какие значения в регистрах.

; Щелчок динамиком через порт 0x61
in al, 0x61
or al, 0x03
out 0x61, al

; Работает даже если видео сломано

Три кита ОС

  • Прерывания — как железо сообщает процессору о событиях
  • Защищённый режим — изоляция программ друг от друга
  • Таблицы страниц — виртуальная память

Без этих трёх механизмов современная ОС невозможна.

Прерывания: зачем

  • Таймер, клавиатура, диск — генерируют прерывания
  • Процессор откладывает текущую задачу и вызывает обработчик
  • Адреса обработчиков — в таблице IDT
  • Без прерываний: процессор должен сам опрашивать устройства (polling)

Прерывания: QEMU

# Лог прерываний
qemu-system-x86_64 -d int -D qemu.log \
    -drive format=raw,file=disk.img

# В логе: interrupt 0x20 (таймер) снова и снова
# Это ядро получает управление от таймера

Защищённый режим: зачем

  • В реальном режиме любая программа может писать куда угодно
  • Защищённый режим: кольца защиты (ring 0 — ядро, ring 3 — пользователь)
  • Программа из ring 3 не может трогать память ядра
  • Без него: любая программа может перезаписать ОС

Защищённый режим: QEMU

# После перехода в защищённый режим
# появляются исключения при попытке доступа к памяти
qemu-system-x86_64 -d int,cpu_reset -D qemu.log \
    -drive format=raw,file=disk.img

# В логе: interrupt 0x0D (general protection fault)

Таблицы страниц: зачем

  • Виртуальная память: программа думает, что у неё вся память
  • Процессор транслирует виртуальные адреса в физические
  • Изоляция: программа не видит память другой программы
  • Swap: неиспользуемые страницы выгружаются на диск

Таблицы страниц: QEMU

# Page fault при обращении к несуществующей странице
qemu-system-x86_64 -d int -D qemu.log \
    -drive format=raw,file=disk.img

# В логе: interrupt 0x0E (page fault)
# С адресом, к которому обратились
