Цикл разработки: лекция 5

  • Путь: текст программы → байты, которые выполняет процессор
  • Компилятор, ассемблер, линкер — отдельные инструменты
  • Freestanding-разработка: ОС, загрузчики, embedded
  • Финал: загрузка реального десктопа

Невидимая цепочка

  • Прикладной разработчик видит единое целое
  • gcc, системы сборки, IDE — незаметно дёргают инструменты по цепочке
  • Каждый этап — отдельная программа
  • Обычно это скрыто за одной командой

Freestanding: всё видно

  • В ОС, загрузчиках, embedded — цепочка видимая
  • Каждый шаг управляется руками
  • Нет сборочной системы, которая прячет детали
  • Отсюда — необходимость понимать каждый этап

Структура лекции

  • Hosted vs Freestanding — формальная рамка
  • Компилятор, ассемблер, линкер — инструменты
  • Системная библиотека и syscall'ы
  • QEMU — инструмент разработки
  • Загрузка реального десктопа — кульминация

Hosted vs Freestanding

  • Термины из стандарта ISO C
  • Формальная классификация окружения выполнения
  • Не бытовое деление на «ОС / без ОС»
  • Определяет, что гарантировано программе

Hosted environment

  • Полная стандартная библиотека (libc)
  • Гарантированная точка входа: main()
  • Окружение предоставляет рантайм
  • Инициализация глобальных объектов до main()

Hosted: что делает рантайм

  • argc/argv — собираются из командной строки
  • exit() — реально завершает процесс через ОС
  • stdio — буферизация, файловые дескрипторы
  • malloc/free — работают через системные вызовы

Freestanding environment

  • Никаких предположений об ОС
  • Гарантированы только несколько заголовков
  • stddef.h, stdint.h, float.h, limits.h, stdarg.h
  • main() не обязан существовать

Freestanding: точка входа

  • Определяется вами и линкером
  • Может называться _start, kernel_main, что угодно
  • Линкер получает явное указание через linker script
  • Никто не вызывает main() — вы сами решаете

Флаг -ffreestanding

  • GCC/Clang: отключает предположения о libc
  • Запрещает подставлять memcpy/memset без ведома
  • Компилятор не «оптимистично» вставляет вызовы
  • Вы контролируете каждый вызов

Пример: оптимизация memset

// Без -ffreestanding:
// компилятор может заменить цикл на вызов memset
for (int i = 0; i < 100; i++) {
    arr[i] = 0;
}
// С -ffreestanding:
// цикл останется циклом

Кто обязан быть freestanding

  • Ядро ОС — нет libc под ним
  • Загрузчик — работает до ОС
  • Прошивка embedded — голое железо
  • Им буквально не на что «хоститься»

Компилятор: общая схема

  • Препроцессинг — текстовые подстановки, #include
  • Frontend — разбор синтаксиса, AST
  • Оптимизации — внутреннее представление
  • Backend — генерация кода

Стадии: препроцессинг

  • #include — вставка содержимого файлов
  • #define — макроподстановки
  • #ifdef — условная компиляция
  • Результат: чистый код на C без директив

Стадии: frontend и оптимизации

  • Frontend: синтаксический анализ → AST
  • AST → внутреннее представление (IR)
  • Оптимизации: dead code, inline, loop unrolling
  • IR не привязан к конкретной архитектуре

Стадии: backend

  • Выбор инструкций под архитектуру
  • Регистровое распределение
  • Планирование инструкций
  • Результат: ассемблер или объектный код

Кросс-компиляция

  • Компилятор на одной архитектуре → код для другой
  • Необходимость для freestanding-разработки
  • Target triple: x86_64-elf
  • Без привязки к хостовой ОС

gcc -S: посмотреть ассемблер

// C код
int add(int a, int b) {
    return a + b;
}

// gcc -S add.c → add.s
// add:
//     push rbp
//     mov  rbp, rsp
//     mov  DWORD PTR [rbp-4], edi
//     mov  DWORD PTR [rbp-8], esi
//     mov  eax, DWORD PTR [rbp-8]
//     mov  edx, DWORD PTR [rbp-4]
//     add  eax, edx
//     pop  rbp
//     ret

Компилятор не делает exe

  • Компилятор — только объектный код или ассемблер
  • Исполняемый файл собирают дальше
  • Ассемблер и линкер — следующие шаги
  • Это ключевая мысль: цепочка инструментов

Ассемблер: задача

  • Текст на ассемблере → машинный код
  • Почти 1:1 соответствие мнемоника → инструкция
  • В отличие от компилятора — без оптимизаций
  • Каждая строка — одна инструкция

Intel vs AT&T синтаксис

  • Intel: NASM, YASM — mov eax, ebx
  • AT&T: GNU as — mov %ebx, %eax
  • Порядок операндов разный
  • Источник постоянной путаницы у новичков

Пример: Intel vs AT&T

; Intel (NASM):
mov eax, [ebx]    ; eax = *ebx
add eax, 10       ; eax += 10

; AT&T (GAS):
mov (%ebx), %eax  ; eax = *ebx
add $10, %eax     ; eax += 10
; Внимание: направление операндов!

Секции объектного файла

  • .text — исполняемый код
  • .data — инициализированные данные
  • .bss — неинициализированные данные
  • .rodata — константы (read-only)

.bss: экономия места

  • Неинициализированные данные — нули по умолчанию
  • Не занимают места на диске
  • Только размер записан в объектном файле
  • При загрузке — выделяется и обнуляется

ELF: формат объектного файла

  • Executable and Linkable Format
  • Стандарт на Linux
  • Содержит секции, символы, релокации
  • Позже линкер будет его разбирать

Символы (symbols)

  • Имена функций и переменных
  • Экспортируемые — видны другим .o файлам
  • Импортируемые — ссылки на внешние
  • Ещё не адреса — только имена
  • Адреса разрешит линкер

Линкер: задача

  • Собирает несколько .o файлов и библиотек
  • Результат: исполняемый файл или .so
  • Разрешает символы и релокации
  • Создаёт финальный образ

Разрешение символов

  • Вызов функции из другого .o
  • Линкер ищет определение по имени
  • Находит в другом объектном файле или библиотеке
  • Если не нашёл — ошибка undefined reference

Релокации

  • Объектный файл не знает финальных адресов
  • Линкер подставляет адреса при сборке
  • Статическая линковка — адреса фиксируются сейчас
  • Динамическая — загрузчик ОС сделает это позже

Статическая vs динамическая

  • .a — статические библиотеки
  • .so — разделяемые (динамические)
  • Статика: всё в одном файле, больше размер
  • Динамика: меньше, но нужны .so при запуске
  • Компромисс: размер vs гибкость обновлений

Linker script: зачем

  • Явное управление размещением секций
  • Какой адрес считается точкой входа
  • Куда в памяти попадает каждая секция
  • Критично для ОС и загрузчиков

Почему linker script необходим

  • Линкер по умолчанию не знает физический адрес
  • Он собирает под виртуальную память ОС
  • Ядро должно грузиться по конкретному адресу
  • Например, 0x100000 для Multiboot

Минимальный linker script

ENTRY(_start)

SECTIONS {
    . = 0x100000;  /* адрес загрузки */

    .text : {
        *(.text)
    }

    .data : {
        *(.data)
    }

    .bss : {
        *(.bss)
    }
}

Демонстрация: сборка ядра

# Компиляция без libc
gcc -ffreestanding -c kernel.c -o kernel.o
# Ассемблирование
nasm -f elf64 start.asm -o start.o
# Линковка с явным скриптом
ld -T linker.ld kernel.o start.o -o kernel.bin

Вопрос: статическая линковка и адреса

  • Собрали статический исполняемый файл
  • Линкер не знает, куда ОС загрузит программу
  • Но адреса в коде уже проставлены?
  • Как это разрешается?

Короткий ответ

  • Статическая линковка ≠ фиксированные адреса
  • Линкер знает относительное расположение секций
  • Абсолютные адреса решает ОС при загрузке
  • Механизм: PIE или релокации

ELF: относительные смещения

Исполняемый файл (ELF):
┌─────────────────────┐
│ ELF Header          │
├─────────────────────┤
│ Program Headers     │
├─────────────────────┤
│ .text (код)         │  ← смещение 0x1000
├─────────────────────┤
│ .rodata (константы) │  ← смещение 0x2000
├─────────────────────┤
│ .data (данные)      │  ← смещение 0x3000
├─────────────────────┤
│ .bss  (нули)        │  ← смещение 0x4000
└─────────────────────┘

Загрузка: базовый адрес

Виртуальная память процесса:
┌─────────────────────────┐
│ 0x400000 (base)         │ ← ОС выбирает адрес
├─────────────────────────┤
│ base + 0x1000 → .text   │
├─────────────────────────┤
│ base + 0x2000 → .rodata │
├─────────────────────────┤
│ base + 0x3000 → .data   │
└─────────────────────────┘
  • ОС решает, куда загрузить
  • Обычно 0x400000 для x86-64 Linux

PIE: Position Independent Executable

# Современный стандарт:
gcc -fPIE -pie main.c -o program

# Код использует относительные адреса:
; вместо: mov rax, [0x400123]
; используется:
lea rax, [rip + offset]  ; адрес от текущей позиции

# Никаких исправлений при загрузке не нужно!

ET_EXEC: фиксированный base

# Старый формат:
gcc -no-pie main.c -o program

# Линкер зашивает адреса от 0x400000:
mov rax, [0x400123]  ; абсолютный адрес

# Загрузчик ОС обязан загрузить по 0x400000
# Если занято — программа не запустится

Аналогия с ядром ОС

  • Обычная программа: ОС выбирает адрес (PIE)
  • Ядро ОС: вы выбираете адрес (linker script)
  • Ядро не может быть PIE — оно само создаёт таблицы страниц
  • Поэтому для ядра нужен явный linker script

Системная библиотека: роль

  • Прослойка между кодом и ядром
  • malloc, printf, fopen — обёртки над syscall'ами
  • Добавляет буферизацию и абстракции
  • Скрывает детали системных вызовов

Пример: printf → write

// printf("Hello\n") внутри делает:
// 1. Форматирует строку в буфер
// 2. Вызывает write(1, buf, len)
// 3. write — это системный вызов

// Пользователь видит только printf
// Библиотека скрывает syscall

Hosted: библиотека всегда есть

  • glibc — стандарт на Linux
  • musl — легковесная альтернатива
  • Разный компромисс: размер, строгость POSIX
  • Подключается автоматически

Freestanding: без библиотеки

  • Пишете свою минимальную замену
  • Или обходитесь вовсе без неё
  • Каждая функция — только если нужна
  • Полный контроль над кодом

Мостик к syscall'ам

  • Библиотека внутри — через системные вызовы
  • Она не более «привилегированна», чем ваш код
  • Просто удобная обёртка
  • Следующий раздел: как работают syscall'ы

Системные вызовы: зачем

  • Запрос услуг ядра из пользовательского пространства
  • Файловый ввод-вывод, процессы, память
  • Единственный легальный способ попасть в ядро
  • Безопасный переход между кольцами

Кольца защиты

  • Ring 0 — ядро, полный доступ
  • Ring 3 — пользовательский код
  • Промежуточные — драйверы (редко)
  • Переход: только через syscall/int

Эволюция: int 0x80

  • 32-битный Linux
  • Программное прерывание
  • Номер вызова в eax
  • Аргументы в ebx, ecx, edx, esi, edi
  • Медленно: полный цикл прерывания

Современный: syscall/sysenter

  • x86-64 Linux
  • Быстрый механизм через MSR
  • Без полноценного прерывания
  • Минимальные накладные расходы

Соглашение о вызове x86-64

  • rax — номер системного вызова
  • rdi, rsi, rdx, r10, r8, r9 — аргументы
  • Не совпадает с обычным ABI функций
  • Обычный ABI: rdi, rsi, rdx, rcx, r8, r9

Пример: write() без libc

; write(1, msg, len)
mov rax, 1       ; номер write
mov rdi, 1       ; fd = stdout
mov rsi, msg     ; буфер
mov rdx, len     ; длина
syscall

; exit(0)
mov rax, 60      ; номер exit
mov rdi, 0       ; код возврата
syscall

Inline-ассемблер в C

static inline long syscall1(long n, long a1) {
    long ret;
    asm volatile (
        "syscall"
        : "=a"(ret)
        : "a"(n), "D"(a1)
        : "rcx", "r11", "memory"
    );
    return ret;
}

// Использование:
syscall1(1, 1);  // write(1, ...)

Демонстрация: Hello без libc

// Полный freestanding Hello, world!
void _start() {
    char msg[] = "Hello!\n";
    syscall1(1, 1);  // write(1, msg, 7)
    syscall1(60, 0); // exit(0)
}
// Собрано: gcc -ffreestanding -nostdlib
// Запущено: ./hello  (работает!)

QEMU: что это

  • Эмулятор/виртуализатор
  • Запускает freestanding-бинарник без железа
  • Поддерживает x86, ARM, RISC-V и др.
  • Два режима: эмуляция и виртуализация

Запуск ядра напрямую

# Multiboot-совместимое ядро
qemu-system-x86_64 -kernel your_kernel.bin

# С отладкой: остановить на первой инструкции
qemu-system-x86_64 -kernel your_kernel.bin -s -S

# -s: GDB server на порту 1234
# -S: остановить CPU сразу

Полная эмуляция загрузки

  • Эмулируется BIOS/UEFI
  • Ваш код грузится как на реальной машине
  • С образа диска или ISO
  • Максимальная реалистичность

Отладка с GDB

# Терминал 1: QEMU с GDB server
qemu-system-x86_64 -kernel kernel.bin -s -S

# Терминал 2: GDB
gdb kernel.bin
(gdb) target remote :1234
(gdb) break _start
(gdb) continue
(gdb) info registers

Почему QEMU, а не железо

  • Быстрый цикл: секунды, не перезагрузка
  • Безопасно: падение ядра не роняет машину
  • Воспроизводимость: одинаковое поведение
  • Снапшоты: сохранить/восстановить состояние

Доступ к недостижимому

  • Первая инструкция после сброса
  • Состояние регистров в любой момент
  • На реальном железе — почти невозможно
  • QEMU даёт полный контроль

Загрузка: общая схема

  • Включение питания → Reset Vector
  • POST → поиск загрузочного устройства
  • BIOS или UEFI → загрузчик
  • Загрузчик → ядро ОС

Reset Vector

  • Процессор стартует в Real Mode
  • Фиксированный адрес: 0xFFFFFFF0
  • Аппаратно отображён на ПЗУ прошивки
  • Первая инструкция — из BIOS/UEFI

POST

  • Power-On Self-Test
  • Базовая диагностика прошивки
  • Проверка памяти, устройств
  • Инициализация контроллеров

Legacy BIOS: MBR

  • Чтение первого сектора (512 байт)
  • Проверка сигнатуры 0x55AA
  • Загрузка в память по адресу 0x7C00
  • Переход на него в 16-битном Real Mode

Ограничение MBR

  • Первая стадия: ~446 байт кода
  • Остальное — таблица разделов
  • Слишком мало для полноценного загрузчика
  • Решение: двухстадийная загрузка

Двухстадийная загрузка

  • Стадия 1 (MBR): найти и загрузить стадию 2
  • Стадия 2 (например, GRUB): уже полноценная
  • Может читать файловые системы
  • Может показывать меню выбора ОС

Real Mode: ограничения

  • 16-битные регистры
  • Максимум 1 МБ адресуемой памяти
  • Нет защиты памяти
  • Нужен переход в Protected/Long Mode

Переход в Long Mode

  • Настройка GDT (Global Descriptor Table)
  • Включение линии A20 (доступ к >1 МБ)
  • Установка бита PE в CR0
  • Переход в 64-битный режим

UEFI: другая модель

  • Прошивка понимает FAT32 (ESP)
  • EFI System Partition
  • Загружает PE/COFF файл напрямую
  • Без классического MBR

UEFI: преимущества

  • Загрузчик — обычный исполняемый файл
  • Может быть большим, с драйверами
  • Secure Boot — проверка подписи
  • Legacy-режим — для совместимости

Multiboot: протокол

  • Загрузчик размещает ядро в памяти
  • Передаёт карту памяти от BIOS/UEFI
  • Передаёт информацию о железе
  • QEMU -kernel использует тот же принцип

Инициализация ядра

  • Собственные таблицы страниц
  • IDT (Interrupt Descriptor Table)
  • Драйверы устройств
  • Монтирование корневой ФС
  • Запуск init/systemd

Замыкающая мысль

  • Ядро ОС на старте — это freestanding-программа
  • Собрана тем же путём: компилятор → ассемблер → линкер
  • С явным linker script
  • Только запущена на реальном процессоре

Итоги: цепочка

  • Компилятор: C → ассемблер
  • Ассемблер: ассемблер → объектный код
  • Линкер: .o файлы → финальный образ
  • Linker script — explicit-план размещения

Итоги: freestanding

  • Без ОС снизу — образ должен сам стать «ОС снизу»
  • Для чего-то ещё
  • Каждый инструмент виден и управляем
  • Нет скрытых механизмов

Итоги: QEMU

  • Не просто «удобная замена железу»
  • Доступ к моментам выполнения
  • Первая инструкция после сброса
  • Недостижимо на реальном железе
