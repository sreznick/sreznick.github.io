Размер пула и диагностика

  • maximumPoolSize: предел соединений; minimumIdle: целевой минимум свободных.
  • maxLifetime: обновление физических соединений.

JDBC: commit и rollback

try (Connection c = dataSource.getConnection()) {
    c.setAutoCommit(false);
    try {
        long id = insertOrder(c, order);
        insertItems(c, id, order.getItems());
        c.commit();
    } catch (SQLException | RuntimeException e) {
        try {
            c.rollback();
        } catch (SQLException rollbackError) {
            e.addSuppressed(rollbackError);
        }
        throw e;
    }
}

Оба метода получают тот же Connection; SQL хранится в репозитории.

19 / 66

Изоляция: что видит транзакция

  • Read Committed: в PostgreSQL новый снимок на каждую команду.
  • Repeatable Read: в PostgreSQL стабильный снимок; возможен write skew.
  • Serializable: эффект успешных транзакций эквивалентен последовательному выполнению.
  • При конфликтах возможен отказ: приложение повторяет всю транзакцию.

Пример write skew: два врача видят второго на дежурстве и оба снимают своё дежурство.

Миграция: добавляем статус

-- V2__add_order_status.sql (PostgreSQL)
ALTER TABLE orders ADD COLUMN status varchar(20);

UPDATE orders SET status = 'NEW' WHERE status IS NULL;

ALTER TABLE orders ADD CONSTRAINT orders_status_check

EntityManager и persistence context

  • Persistence context хранит управляемые сущности и отслеживает их состояние.
  • Для типа и идентификатора в одном контексте — один managed-экземпляр.
  • Повторный find() может вернуть тот же объект без SELECT.
  • EntityManager не предназначен для совместного использования потоками.

Persistence context живёт на стороне Java; его границы и границы транзакции — разные понятия.

Изменение без отдельного save()

EntityTransaction tx = em.getTransaction();
tx.begin();
try {
    Order order = em.find(Order.class, orderId);
    order.cancel(); // изменяет status managed-сущности
    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) {
        try { tx.rollback(); }
        catch (RuntimeException re) { e.addSuppressed(re); }
    }
    throw e;
}

Dirty checking обнаруживает изменение; при flush ORM выполняет UPDATE.

34 / 66

Flush ≠ commit

  • Flush синхронизирует изменения контекста с БД через SQL.
  • Может происходить явно, перед commit и перед некоторыми запросами.
  • SQL уже выполнен, но изменения ещё можно откатить до commit.
  • INSERT может потребоваться раньше, например для получения IDENTITY-id.
  • После rollback безопаснее завершить этот unit of work и начать с новым контекстом.

Не привязываем каждый Java-вызов к немедленной SQL-команде.

Каскады и удаление из коллекции

  • PERSIST распространяет сохранение новых сущностей.
  • MERGE распространяет перенос состояния при merge().
  • REMOVE распространяет удаление; ALL включает все каскады.
  • orphanRemoval удаляет дочернюю сущность при разрыве связи в подходящей модели владения.
  • Каскады ORM отличаются от ON DELETE CASCADE в БД.

Не выбираем ALL автоматически: жизненный цикл связанных сущностей может быть независимым.

Fetch join: явно загрузить связь

List<Order> orders = em.createQuery("""
    select distinct o
    from Order o
    left join fetch o.items
    """, Order.class).getResultList();
  • JPQL использует имена сущностей и полей, а не таблиц.
  • LEFT JOIN сохраняет заказы без позиций.
  • Данные заказа повторяются в SQL-строках для каждой позиции.
  • Несколько to-many JOIN могут дать декартово разрастание.

Не загружаем весь граф «на всякий случай».

Коллекция fetch join и LIMIT

  • LIMIT ограничивает SQL-строки, а нужен лимит заказов.
  • Fetch join коллекции вместе с пагинацией может привести к выборке всех строк и ограничению в памяти.
  • Решение: сначала страница id заказов, затем загрузка заказов с позициями по этим id.
  • Восстанавливаем порядок страницы; учитываем изменения между двумя запросами.
  • Альтернатива: DTO или отдельная пакетная загрузка позиций.

В Hibernate можно включить fail_on_pagination_over_collection_fetch, чтобы обнаруживать такой сценарий.

Массовая запись

// Настройка Hibernate: hibernate.jdbc.batch_size=50
for (int i = 0; i < orders.size(); i++) {
    em.persist(orders.get(i));
    if ((i + 1) % 50 == 0) {
        em.flush();
        em.clear();
    }
}
  • flush отправляет изменения; clear освобождает контекст и отсоединяет сущности.
  • flush не фиксирует транзакцию: её размер выбираем отдельно.
  • IDENTITY обычно мешает batching INSERT в Hibernate; стратегию id выбираем осознанно.

Перед clear() нужен flush(), иначе несинхронизированные изменения теряются из контекста.

→

  • Бизнес-изменение и событие записываем атомарно в одной БД.

Идемпотентность и eventual consistency

  • Повтор одной команды не должен повторно списывать деньги.
  • Используем operationId / messageId и уникальное ограничение.
  • Запись о принятом сообщении и бизнес-изменение фиксируем одной транзакцией.
  • Промежуточные статусы: PENDING → CONFIRMED / REJECTED.
  • Сходимость требует доставки, работающих обработчиков и восстановления ошибок.

В интерфейсе показываем реальное состояние процесса, а не преждевременный успех.

Проекции и CQRS

Команда
→
Поток событий
→
Проекция
→
Чтение
  • Проекция строит удобное представление: таблицу заказов, поиск, статистику.
  • CQRS разделяет модели записи и чтения; не требует Event Sourcing.
  • Асинхронная проекция может отставать; обработчик должен переносить повтор события.
  • Повторное проигрывание не должно повторно выполнять внешние платежи.

Saga — процесс; outbox — доставка; Event Sourcing — хранение; CQRS — разделение моделей.
