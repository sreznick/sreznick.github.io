Рефлексия

Интроспекция классов в рантайме

01

Рефлексия: Определение

  • Возможность программы исследовать себя в рантайме
  • Получение информации о классах, методах, полях без знания их имен на этапе компиляции
  • Точка входа — объект Class<?>

Что дает

  • Создание объектов без new
  • Вызов методов по имени (из строки)
  • Доступ к private-полям и методам
  • Чтение аннотаций

Рефлексия: Получение Class

Три способа получить Class<?>:

// 1. Через .class (compile-time)
Class<String> c1 = String.class;

// 2. Через getClass() (runtime)
String s = "hello";
Class<? extends String> c2 = s.getClass();

// 3. Через Class.forName() (динамически)
Class<?> c3 = Class.forName("java.lang.String");

Способ 3 — самый гибкий: имя класса можно получить из конфигурации

Рефлексия: Исследование класса

Class<?> clazz = User.class;

// Поля
Field[] fields = clazz.getDeclaredFields();

// Методы
Method[] methods = clazz.getDeclaredMethods();

// Конструкторы
Constructor<?>[] constructors = clazz.getDeclaredConstructors();

// Аннотации
Annotation[] annotations = clazz.getAnnotations();

// Суперкласс и интерфейсы
Class<?> superclass = clazz.getSuperclass();
Class<?>[] interfaces = clazz.getInterfaces();

Рефлексия: Создание объекта

// Через конструктор по умолчанию
Class<?> clazz = Class.forName("com.example.User");
User user = (User) clazz.getDeclaredConstructor().newInstance();

// Через конструктор с параметрами
Constructor<?> constructor = clazz.getConstructor(String.class, int.class);
User user2 = (User) constructor.newInstance("Alice", 30);

// Private-конструктор
Constructor<?> privateCtor = clazz.getDeclaredConstructor();
privateCtor.setAccessible(true);
User user3 = (User) privateCtor.newInstance();

Рефлексия: Вызов методов

Method method = clazz.getMethod("setName", String.class);
method.invoke(user, "Bob");

// Private-метод
Method privateMethod = clazz.getDeclaredMethod("secretMethod");
privateMethod.setAccessible(true);
privateMethod.invoke(user);

// Статический метод
Method staticMethod = clazz.getMethod("staticMethod");
staticMethod.invoke(null);

invoke — главный метод для динамического вызова

Рефлексия: Доступ к полям

Field field = clazz.getDeclaredField("name");
field.setAccessible(true); // ломаем инкапсуляцию

// Чтение
String name = (String) field.get(user);

// Запись
field.set(user, "Charlie");

С Java 9+ модули могут запретить доступ (exports/opens)

Рефлексия: Дженерики

// Получить параметризованный тип
Method method = clazz.getMethod("getList");
Type returnType = method.getGenericReturnType();

if (returnType instanceof ParameterizedType) {
    ParameterizedType pt = (ParameterizedType) returnType;
    Type[] typeArgs = pt.getActualTypeArguments();
    // typeArgs[0] = String.class
}

// Пример: List<String> getList()

Нужно для библиотек, работающих с типами (Jackson, Hibernate)

Рефлексия: Как работает под капотом

// Упрощенная схема method.invoke(obj, args)
public Object invoke(Object obj, Object... args) {
    // 1. Проверка доступа (SecurityManager, модули)
    // 2. Проверка типов аргументов (каждый раз!)
    // 3. Упаковка/распаковка (boxing/unboxing)
    // 4. Вызов через нативный метод (native)
    // 5. JIT не может инлайнить (метод неизвестен)
}
ПроблемаПричина
Проверка доступаКаждый вызов проверяет SecurityManager
Проверка типовinvoke(Object, Object[]) — все как Object
Boxingint -> Integer -> Object -> int
Нативный вызовJIT не видит тело метода
Нет инлайнингаJIT не знает, какой метод будет вызван

Рефлексия: Производительность

ОперацияВремя (относительно прямого вызова)
Прямой вызов1x
invoke()10-100x медленнее
setAccessible(true)Ускоряет, но ломает инкапсуляцию
Кэширование Method2-5x медленнее (вместо 100x)

Кэшируйте Method и Field — не вызывайте getMethod() каждый раз

Рефлексия: Ограничения и опасности

  • Производительность: invoke() медленный, JIT не оптимизирует
  • Безопасность: setAccessible(true) ломает инкапсуляцию
  • Модули (Java 9+): модуль должен открыть пакет (opens)
  • Ошибки: NoSuchMethodException, IllegalAccessException — в рантайме, не на компиляции

MethodHandle и LambdaMetafactory

Производительный доступ к методам

02

MethodHandle: Определение

  • Типизированная ссылка на метод (Java 7+)
  • Альтернатива java.lang.reflect.Method
  • Типы известны — JIT может оптимизировать
// Создание
MethodHandles.Lookup lookup = MethodHandles.lookup();
MethodHandle handle = lookup.findVirtual(User.class, "getName",
    MethodType.methodType(String.class));

// Вызов
String name = (String) handle.invoke(user);       // с проверкой типов
String name2 = (String) handle.invokeExact(user); // без проверки (быстрее)

MethodHandle: Типы вызовов

// invoke() — с проверкой типов и адаптацией
// Может делать boxing/unboxing, приведение типов
String name = (String) handle.invoke(user);

// invokeExact() — без проверки, типы должны совпадать точно
// Быстрее, но требует точного соответствия
String name2 = (String) handle.invokeExact(user);

// invokeWithArguments() — как рефлексия (медленно)
Object result = handle.invokeWithArguments(user);

invokeExact — самый быстрый, но самый строгий

MethodHandle: Как работает под капотом

// JIT видит:
//   handle.invokeExact(user) -> User.getName() -> return this.name;

// JIT может инлайнить:
//   String name = user.name;  // прямой доступ к полю

// В отличие от рефлексии:
//   method.invoke(user) -> ??? (JIT не знает, какой метод)
//   JIT НЕ может инлайнить
  • Проверка доступа — один раз при создании
  • Типы известны из MethodType
  • Нет нативного вызова — обычный Java-код
  • JIT видит цепочку вызовов

MethodHandle: Сравнение с рефлексией

КритерийMethodMethodHandle
ТипобезопасностьНетДа (MethodType)
Проверка доступаКаждый вызовОдин раз при создании
BoxingДаНет
Нативный вызовДаНет
Инлайнинг JITНетДа
Скорость10-100x медленнее1-2x (почти как прямой)

MethodHandle: Дополнительные возможности

// Доступ к полям
MethodHandle getter = lookup.findGetter(User.class, "name", String.class);
MethodHandle setter = lookup.findSetter(User.class, "name", String.class);

// Композиция
MethodHandle fullName = lookup.findVirtual(User.class, "getFullName",
    MethodType.methodType(String.class));
MethodHandle upperCase = lookup.findVirtual(String.class, "toUpperCase",
    MethodType.methodType(String.class));
MethodHandle composed = MethodHandles.filterReturnValue(fullName, upperCase);

// Привязка аргументов
MethodHandle greet = lookup.findVirtual(User.class, "greet",
    MethodType.methodType(String.class, String.class));
MethodHandle greetAlice = MethodHandles.insertArguments(greet, 1, "Alice");

LambdaMetafactory: Определение

  • Генерация реализации функционального интерфейса (Java 8+)
  • Использует invokedynamic — инструкцию JVM
  • Создает класс, который вызывает метод напрямую
// Функциональный интерфейс
interface Greeter {
    String greet(String name);
}

// Лямбда (компилятор использует LambdaMetafactory)
Greeter greeter = name -> "Hello, " + name;

LambdaMetafactory: Как работает

// Исходный код
Greeter greeter = name -> "Hello, " + name;

// Компилятор генерирует invokedynamic
// JVM вызывает LambdaMetafactory.metafactory()
// LambdaMetafactory генерирует класс:

class Greeter$$Lambda {
    public String greet(String name) {
        return "Hello, " + name;  // прямой вызов, без рефлексии
    }
}
  • Нет рефлексии — сгенерированный класс вызывает метод напрямую
  • Нет проверок — типы известны на этапе генерации
  • Инлайнинг — JIT видит весь код

LambdaMetafactory: Ручное создание

MethodHandles.Lookup lookup = MethodHandles.lookup();

// Тип создаваемой реализации
MethodType factoryType = MethodType.methodType(Greeter.class);

// Тип метода интерфейса
MethodType interfaceMethodType = MethodType.methodType(String.class, String.class);

// Реализация (статический метод)
MethodHandle implMethod = lookup.findStatic(GreeterFactory.class, "greetImpl",
    MethodType.methodType(String.class, String.class));

// Создание
CallSite site = LambdaMetafactory.metafactory(
    lookup, "greet", factoryType, interfaceMethodType, implMethod, interfaceMethodType
);

Greeter greeter = (Greeter) site.getTarget().invoke();
System.out.println(greeter.greet("Alice"));

Рефлексия10-100xПроверки, нативный вызов, нет инлайнинга

MethodHandle: Итог — почему быстрее

Класс-лоадеры

Откуда берутся классы

03

Класс-лоадеры: Зачем нужны

  • Загрузка .class файлов в JVM
  • Определение видимости классов (изоляция)
  • Динамическая загрузка (плагины, модули)

Без класс-лоадеров невозможно

  • Tomcat: разные приложения не видят классы друг друга
  • OSGi: модули с версиями
  • Java Modules (JPMS)

Класс-лоадеры: Иерархия

Bootstrap (JDK, java.base)
    |
    +-- Platform/Extension (Java 9+, java.sql, java.xml)
        |
        +-- Application/System (classpath)
            |
            +-- Пользовательские (Tomcat, OSGi, свой ClassLoader)
  • Bootstrap: встроен в JVM, загружает java.base
  • Platform: модули JDK
  • Application: ваш classpath
  • Пользовательские: создаются приложением

Класс-лоадеры: Parent Delegation

  1. Спросить родителя: "Ты знаешь этот класс?"
  2. Если родитель не знает — загрузить самому
protected Class<?> loadClass(String name) {
    // 1. Проверить, не загружен ли уже
    Class<?> c = findLoadedClass(name);
    if (c != null) return c;
    
    // 2. Спросить родителя
    try {
        c = parent.loadClass(name);
    } catch (ClassNotFoundException e) {
        // 3. Загрузить самому
        c = findClass(name);
    }
    return c;
}

Класс-лоадеры: Почему Parent Delegation

  • Безопасность: нельзя подменить java.lang.String своей версией
  • Экономия: класс загружается один раз
  • Иерархия: стандартные классы всегда доступны

Исключение: Thread Context ClassLoader

  • Иногда родитель не знает о классах ребенка (JDBC, JNDI)
  • Решение: Thread.currentThread().getContextClassLoader()

Класс-лоадеры: Свой ClassLoader

public class MyClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) {
        // Читаем .class файл (БД, сеть, генерация)
        byte[] bytes = loadFromDatabase(name);
        return defineClass(name, bytes, 0, bytes.length);
    }
}

Применения:

  • Загрузка классов из БД или сети
  • Генерация классов на лету (CGLIB, Byte Buddy)
  • Изоляция (Tomcat, OSGi)

Класс-лоадеры: Связь с рефлексией

  • Class<?> — результат работы ClassLoader
  • Рефлексия работает с уже загруженными классами
  • ClassLoader определяет, какие классы доступны
// Динамическая загрузка
Class<?> clazz = Class.forName("com.example.Plugin");
// Использует ClassLoader текущего потока

// Явный ClassLoader
Class<?> clazz2 = myClassLoader.loadClass("com.example.Plugin");

Аннотации

Декларативное метапрограммирование

04

Аннотации: Определение

  • Метаданные в коде — не влияют на выполнение сами по себе
  • Обрабатываются инструментами: компилятор, фреймворки
  • Примеры: @Override, @Deprecated, @SpringBootApplication

Создание своей аннотации

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Loggable {
    String level() default "INFO";
    boolean logParams() default true;
}

Аннотации: Retention Policy

RetentionГде доступнаПример
SOURCEТолько в исходном коде@Override, @SuppressWarnings
CLASSВ байткоде, но не в рантайме@Lombok (частично)
RUNTIMEДоступна через рефлексию@SpringBootApplication, @Test

Для рефлексии нужен RUNTIME

Аннотации: Target

Куда можно вешать аннотацию:

@Target({
    ElementType.TYPE,       // класс, интерфейс, enum
    ElementType.METHOD,     // метод
    ElementType.FIELD,      // поле
    ElementType.PARAMETER,  // параметр
    ElementType.CONSTRUCTOR,// конструктор
    ElementType.ANNOTATION_TYPE, // другая аннотация
    ElementType.PACKAGE     // пакет
})

Аннотации: Чтение через рефлексию

// Читаем аннотацию с класса
Class<?> clazz = UserService.class;
if (clazz.isAnnotationPresent(Loggable.class)) {
    Loggable loggable = clazz.getAnnotation(Loggable.class);
    String level = loggable.level();
}

// Читаем с метода
Method method = clazz.getMethod("save", User.class);
Loggable loggable = method.getAnnotation(Loggable.class);

// Все аннотации
Annotation[] annotations = method.getAnnotations();

Аннотации: Пример — Свой DI-контейнер

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Inject { }

// Использование
public class UserService {
    @Inject private UserRepository repository;
}

// Обработка
for (Field field : clazz.getDeclaredFields()) {
    if (field.isAnnotationPresent(Inject.class)) {
        field.setAccessible(true);
        Object dependency = container.get(field.getType());
        field.set(instance, dependency);
    }
}

Динамические прокси

Перехват вызовов методов

05

Прокси: Определение

  • Создание реализации интерфейса на лету
  • Перехват вызовов методов без изменения оригинального кода

Применения

  • AOP: транзакции, логирование, безопасность
  • Mock-объекты (Mockito)
  • Remote calls (RMI, Feign)
  • Lazy-loading (Hibernate)

Прокси: java.lang.reflect.Proxy

// Интерфейс
public interface UserService {
    void save(User user);
}

// InvocationHandler — перехватывает все вызовы
InvocationHandler handler = (proxy, method, args) -> {
    System.out.println("Before: " + method.getName());
    Object result = method.invoke(target, args);
    System.out.println("After: " + method.getName());
    return result;
};

// Создание прокси
UserService proxy = (UserService) Proxy.newProxyInstance(
    UserService.class.getClassLoader(),
    new Class[]{UserService.class},
    handler
);

Прокси: Ограничения Proxy

  • Только интерфейсы: нельзя проксировать классы
  • Производительность: рефлексия под капотом
  • final-методы: не перехватываются

Когда использовать

  • Класс реализует интерфейс
  • Нужна простота
  • Не критична производительность

Прокси: CGLIB

  • Code Generation Library
  • Прокси для классов (не только интерфейсов)
  • Механизм: наследование — создает подкласс
// Класс без интерфейса
public class UserService {
    public void save(User user) { ... }
}

// CGLIB создает подкласс
UserService proxy = (UserService) Enhancer.create(
    UserService.class,
    new MethodInterceptor() {
        @Override
        public Object intercept(Object obj, Method method,
                Object[] args, MethodProxy proxy) throws Throwable {
            System.out.println("Before: " + method.getName());
            Object result = proxy.invokeSuper(obj, args);
            System.out.println("After: " + method.getName());
            return result;
        }
    }
);

Прокси: CGLIB — Как работает

// Оригинальный класс
public class UserService {
    public void save(User user) { ... }
}

// CGLIB генерирует подкласс (через ASM)
public class UserService$$EnhancerByCGLIB extends UserService {
    private MethodInterceptor interceptor;
    
    @Override
    public void save(User user) {
        interceptor.intercept(this, saveMethod, new Object[]{user}, null);
    }
}
  • Генерация байткода на лету (ASM)
  • Переопределение методов
  • MethodInterceptor — аналог InvocationHandler

Прокси: CGLIB — Ограничения

  • final-классы: нельзя создать подкласс
  • final-методы: нельзя переопределить
  • private-методы: не перехватываются
  • static-методы: не перехватываются

Когда использовать

  • Класс без интерфейса
  • Spring AOP (по умолчанию с Spring 3.2+)
  • Mockito для классов

Прокси: Сравнение Proxy vs CGLIB

КритерийProxyCGLIB
Что проксируетТолько интерфейсыКлассы и интерфейсы
МеханизмКомпозицияНаследование

Генерация байткода

Создание классов на лету

06

Генерация: Зачем

  • Динамическое создание классов (прокси, DTO)
  • Оптимизация: избежать рефлексию
  • AOP, ORM, сериализация

Примеры

  • Hibernate: прокси для lazy-loading
  • Spring AOP: CGLIB-прокси
  • Jackson: генерация сериализаторов

Генерация: Инструменты

ИнструментУровеньСложностьКогда использовать

CGLIBСреднийСредняяПрокси для классов

Генерация: ASM

  • Низкоуровневый — прямой манипуляции байткодом
  • Работает с ClassWriter, MethodVisitor
  • Сложно, но максимально гибко
ClassWriter cw = new ClassWriter(0);
cw.visit(V1_8, ACC_PUBLIC, "com/example/Generated", null, "java/lang/Object", null);

MethodVisitor mv = cw.visitMethod(ACC_PUBLIC, "hello", "()V", null, null);
mv.visitFieldInsn(GETSTATIC, "java/lang/System", "out", "Ljava/io/PrintStream;");
mv.visitLdcInsn("Hello from generated class!");
mv.visitMethodInsn(INVOKEVIRTUAL, "java/io/PrintStream", "println", "(Ljava/lang/String;)V");
mv.visitInsn(RETURN);
mv.visitMaxs(2, 1);

byte[] bytes = cw.toByteArray();

Генерация: Byte Buddy

  • Высокоуровневый, удобный API
  • Использует ASM под капотом
  • Современная альтернатива CGLIB
Class<?> dynamicType = new ByteBuddy()
    .subclass(Object.class)
    .method(ElementMatchers.named("toString"))
    .intercept(FixedValue.value("Hello from Byte Buddy!"))
    .make()
    .load(Main.class.getClassLoader())
    .getLoaded();

Object instance = dynamicType.getDeclaredConstructor().newInstance();
System.out.println(instance.toString()); // "Hello from Byte Buddy!"

APT

Метапрограммирование на этапе компиляции

07

APT: Определение

  • Annotation Processing Tool — обработка аннотаций при компиляции
  • Генерация кода (исходников или байткода)
  • Ошибки на этапе компиляции, а не в рантайме

Примеры

  • Lombok: @Getter, @Builder — генерация методов
  • MapStruct: генерация мапперов
  • Dagger: DI на этапе компиляции

APT: Как работает

  1. Компилятор вызывает Annotation Processor
  2. Processor находит аннотации в исходниках
  3. Генерирует новые исходники или байткод
  4. Компилятор компилирует сгенерированный код

Round-based: несколько раундов — процессор может генерировать код, который тоже содержит аннотации

APT: Пример — Свой процессор

@SupportedAnnotationTypes("com.example.GenerateBuilder")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class BuilderProcessor extends AbstractProcessor {
    
    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment roundEnv) {
        for (Element element : roundEnv.getElementsAnnotatedWith(
                GenerateBuilder.class)) {
            // Генерация Builder-класса
            generateBuilder((TypeElement) element);
        }
        return true;
    }
}

APT: Lombok — Как работает

// Исходный код
@Getter
@Builder
public class User {
    private String name;
    private int age;
}

// Сгенерированный код (упрощенно)
public class User {
    private String name;
    private int age;
    
    public String getName() { return name; }
    public int getAge() { return age; }
    
    public static UserBuilder builder() { return new UserBuilder(); }
    
    public static class UserBuilder {
        private String name;
        private int age;
        
        public UserBuilder name(String name) { this.name = name; return this; }
        public UserBuilder age(int age) { this.age = age; return this; }
        public User build() { return new User(name, age); }
    }
}

APT: Преимущества

  • Скорость: нет рефлексии в рантайме
  • Типобезопасность: ошибки на этапе компиляции
  • Производительность: сгенерированный код работает как обычный

Ограничения

  • Только на этапе компиляции
  • Сложно отлаживать
  • Нельзя генерировать код для уже скомпилированных классов

Сравнение: Как выбрать

  1. Нужно прочитать аннотацию? — Рефлексия
  2. Нужно вызвать метод динамически, критична скорость? — MethodHandle
  3. Нужно перехватить вызов метода? — Proxy (интерфейс) или CGLIB (класс)
  4. Нужно создать класс на лету? — Byte Buddy
  5. Нужно генерировать код при компиляции? — APT
  6. Критична производительность? — Генерация, не рефлексия

Итоги

  • Рефлексия — фундамент, но медленная
  • MethodHandle — быстрый динамический вызов (JIT инлайнит)
  • LambdaMetafactory — генерация реализации интерфейса
  • Класс-лоадеры — откуда берутся классы
  • Аннотации — декларативное метапрограммирование
  • Proxy / CGLIB — перехват вызовов
  • Генерация байткода — максимальная производительность
  • APT — метапрограммирование на этапе компиляции
