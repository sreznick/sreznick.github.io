Класс как основная сущность

  • В Java нет функций вне классов
  • И нет глобальных данных вне классов/объектов
  • На уровне JVM нет сущности "приложение"
  • Есть классы
  • JVMS описывает жизненный цикл класса
  • https://docs.oracle.com/javase/specs/jvms/se26/html/jvms-5.html

Жизненный цикл класса

  • Создание
  • Загрузка
  • Связывание/линковка - linking
  • Инициализация
  • Иногда - удаление

Жизненный цикл класса

  • Создание - выделение памяти под внутреннее представление класса
  • Загрузка - поиск байткода и чтение его в память виртуальной машины
  • В общем случае формами загрузки можно управлять
  • Можно создавать свои загрузчики классов - реализовывать как Java-код
  • Свой загрузчик может добывать байткод из произвольных источников
  • Добыть набор байтов в соответствии со специальным API
  • Стандартный загрузчик по умолчанию ищет класс в класс-путях

Жизненный цикл класса

  • Linking включает в себя verification, preparing и resolution
  • Verification - проверка структурных ограничений на байткод
  • Preparation - устовка статических полей в значеня по умолчанию
  • Resolution - разрешение ссылок на другие классы
  • Resolution может быть ленивым - отложенным до момента использования разрешаемой сущности

Пример



class C2 {
    static int v = 5;
}

public class C1 {
     public static void main(String[] args) {
         if (args.length > 0) {
             System.out.println(C2.v);
         }
     }
}

Разберем

  • Отсутствие класса может не помешать исполнению
  • Даже если на него ссылается используемый класс
  • Во время верификации JVM проверифицировала соответствие типа поля v и типа параметра println
  • Но загрузка класса C2 была отложена
  • Если бы в позднее загруженном классе тип поля оказался другим - тоже сломались бы

Важно

  • В байткоде класса C2 виден синтетический метод
  • С присваиванием 5 статической перед
  • Это метод инициализации класса
  • Присвание целочисленной константы статическому полю происходит в коде
  • То есть существует момент по времени, когда в статическом поле лежит значение по умолчанию (0)
  • Это может приводить к неочевидному поведению при сложных зависимостях

Пример


          
class C2 {
    static int v = C3.m();
    static int v2 = 5;
}

class C3 {
     static int m() {
         return C2.v2;
     }
}

public class C1 {
     public static void main(String[] args) {
         System.out.println(C2.v);
     }
}

Сравним



class C2 {
    static int v = C3.m();
    static final int v2 = 5;
}

class C3 {
     static int m() {
         return C2.v2;
     }
}

public class C1 {
     public static void main(String[] args) {
         System.out.println(C2.v);
     }
}

Типы данных

  • Есть примитивные типы данных и объекты
  • 4 целочисленных примитивных типа: byte, short, int, long
  • 2 вещественных примитивных типа: float, double
  • Символьный примитивный тип: char
  • Логический примитивный тип: bool
  • void

Типы данных

  • Размеры почти всех примитивных типов зафиксированы
  • byte - 8, short - 16, int - 32, long - 64
  • float - 32, double - 64
  • char - 16
  • bool - на усмотрение реализации

Типы данных

  • Объекты представлены как указатели
  • Нет арифметики указателей
  • Массив формально является объектом
  • Создается только синтакическими средствами
  • Нельзя явным образом вызвать конструктор массива
  • Массив объектов - массив указателей
  • Многомерные массивы - массивы указателей на подмассивы

Важные следствия

  • Нет способа хранить массив структур сплошной областью памяти
  • Как минимум - простого способа
  • Эффективные многомерные числовые массивы нужно реализовывать своими руками
  • Через одномерный массив со своей индексацией

Классы, интерфейсы, записи

  • Есть классы и интерфейсы
  • Множественного наследования нет
  • Можно реализовывать много интерфейсов
  • Возможен интефейс с реализацией по умолчанию
  • Состояния у интерфеса нет
  • Запись - упрощенный синтаксис для data-класса

Пакеты (package)

  • Классы/интерфейсы/записи в полноценном приложении должны жить в пакетах
  • Пакеты в исходниках должны храниться в каталогах
  • Повторяя структуру вложенности
  • Во время исполнения - в общем случае зависит от class-loader-а
  • Стандартный class-loader предполагает аналогичеую структуру вложенности

Классы, интерфейсы, записи

  • Для класса/интерфейса/записи в пакете есть два варианты с точки зрения видимости
  • Публичный или непубличный
  • Непубличный класс недоступен вне своего пакета
  • Публиный класс обязан храниться в одноименном файле
  • У пакетов нет "вложенности"
  • Содержимое пакета a.b.c не является частью содержимого пакета a.b

Элементы класса

  • В классе могут описываться поля, конструкторы и методы
  • Поля и методы могут быть статическими
  • Поля могут быть финальными (final)
  • final - не всегда константа в строгом смысле
  • Модификаторы доступа: public, private, protected
  • Отсутствие модификатора - отдельный режим (default access)

Пример



class C {
  // код для примера, не надо так писать в жизни
  int v1;
  final int v2 = 5;
  static int v3;
  static final int v4 = 123;
  static String v5 = "hello";
}

Разбор

  • Код корректен и компилируем
  • Но совсем не идиоматичен
  • Можно посмотреть байткод
  • В нем будет конструктор без параметров и статический инициализатор
  • Хотя в коде их в явном виде нет

Инициализация класса и объекта

  • В момент создания класса все статические поля устанавливаются в "нулевые" значения
  • 0, 0.0, false, null
  • Потом запускается статический инициализатор
  • Он может быть явно прописан в классе
  • Но все "просто" инициализации в него добавляются компилятором

Пример



class C {
  public static void main(String[] args) {
  }
  static int v1 = 123;
  static {
     System.out.println(v1);
  }
  static String v2 = "hello";
  static {
    System.out.println(v2);
  }
}

Инициализация класса и объекта

  • Подобное происходит с нестатическими полями при инициализации объекта
  • Прописанные вне конструкторов присваивания полям добавляются в начало всех конструкторов
  • Полю можно не присвоить значение
  • Оно останется в "нулевом" значении

Пример


        
class C {
  public static void main(String[] args) {
     new C();
     new C(1);
  }
  int v1;
  C() {
     System.out.println(v1);
     System.out.println(v2);
  }
  String v2 = "hello";
  C(int v) {
    System.out.println(v1);
    System.out.println(v2);
  }
}

final

  • Модификатор final означает, что значение полю может быть присвоено 1 раз
  • И это должно быть сделано - в термих JVM - в конструкторе
  • Причем в final-поле присваивание обязано состояться явным образом
  • Отдельный нюанс есть у статического публичного финального поля

static final

  • Статическое финальное поле может стать чем-то вроде константы
  • Если оно примитивного или строкового типа
  • И инициализируется непосредственно константным выражением
  • Там, где происходит обращение к такому полю - непосредственно подставляется такое значение
  • Не байткодовая инструкция загрузки статического поля

final в контексте паралелизма

  • final-поля (не статические) очень полезны в контексте параллелизма
  • Java Memory Model гарантирует отношение happens-before между присваиванием final-полю внутри конструктора и чтением поля из сконструированного объекта
  • Другими словами - final-поля не надо синхронизировать
  • Хороша мотивация работать в immutable-стиле

Наследование

  • Все просто и естественно
  • Есть общей корень иерархии - java.lang.Object
  • Его прямыми потомками являются все классы без явного указания родителя
  • И все массивы
  • И все интерфейсы

Интерфейсы

  • Интерфейс - контракт на реализации методов интерфейса
  • Возможны реализации по умолчанию
  • Интерфейсы могут содержать статические поля
  • И статические методы

Доступ к полям и методам

  • На одном полюсе - public, на другом private
  • private относительно мягок
  • Объект класса C может обращаться к приватным методам/полям другого объекта класса C
  • Два других варианта немного необычны

protected и package-private

  • Ожидаемо - наследники видят protected-элементы предков
  • Менее очевидно - protected-элементы доступны объектам любого класса того же пакета
  • Без модификатора - доступ package-private
  • Элемент виден изнутри пакета
  • Вне пакета никто не видит
  • Построже, чем protected - наследование не помогает

Максимальное ограничение видимости

  • При дизайне имеет смысл давать минимально необходимый уровень доступа до элемента
  • Это ограничивает варианты возможного поведения
  • Проще тестировать и делать утверждения о поведении системы
  • И уменьшает обязательства по поддержке обратной совместимости

Вложенные классы

  • Бывают статически вложенные и внутренние (inner) классы
  • Статическая вложенность - просто namespace
  • Объекты синтаксически вложенного класса никак не связаны с объектами объемлющего
  • И сами классы для JVM никак содержательно между собой не связаны

Пример


class C {
  static class C1 {}
  static class C2 {}

  C1 c1;
  C2 c2;

  C() {
     c1 = new C1();
     c2 = new C2();
  }

}

class D {
   C.C1 c1;
}

Пример


class C {
  private static class C1 {}
  static class C2 {}

  C1 c1;
  C2 c2;

  C() {
     c1 = new C1();
     c2 = new C2();
  }

}

class D {
   // C.C1 c1;
}

inner-классы

  • Синтаксически это класс, определенный внутри другого определения класса
  • Без слова static
  • Объекты inner-класса могут создаваться только нестатическим кодом объемлющего класса
  • Объект inner-класса хранит ссылку на создавший его объект объемлющего класса
  • Мотивирующий пример: класс Table и inner-класс Column

Пример



class C {
  private int v = 123;
  class C1 {
     C1() {
        System.out.println(C.this.v);
     }
  }

  void m() {
     var c1 = new C1();

  }

}

Пример: опасный код


class C {
  private final int v;

  class C1 {
     C1() {
        System.out.println(C.this.v);
     }
  }

  C(int v) {
     var c1 = new C1();
     this.v = v;
  }

  public static void main(String[] args) {
        new C(5);
  }
}

record

  • Сокращенная форма для класса, с приватными финальными полями
  • Можно добавить компактный конструктор
  • (это официальный термин)
  • Может содержать методы - обычные и статические

Ввод-вывод в Java

  • Первое API - java.io
  • Довольно регулярное и продуманное
  • Но не очень подходящее для асинхронности
  • Или для переинтерпретации байтовых данных
  • И без готовых высокоуровневых операций
  • Эти проблемы решает новое API - java.nio

Понятия java.io

  • Первая пара базовых классов - InputStream и OutputStream
  • Работают с потоками байтов
  • Вторая пара базовых классов - Reader и Writer
  • Работают с потоками символов

Понятия java.io

  • У каждого из базовых классов есть наследники
  • Есть "терминальные" - обеспечивают привязку к реальным источникам или целям
  • Примеры: FileInputStream, FileOutputStream, FileReader, FileWriter
  • Есть "трансформирующие" - преобразуют входной/выходной поток байтов/символов
  • Наследники классов FilterInputStream, FilterOutputStream, FileReader, FileWriter
