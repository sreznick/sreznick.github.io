Память обычного Unix-процесса

Адресное пространство процесса
├── Код и данные только для чтения
├── Статические данные: .data и .bss
├── Область brk: традиционная куча
├── Отображения: библиотеки, файлы, анонимная память

  • Код обращается к виртуальным адресам своего процесса.
  • ОС создаёт отображения при загрузке программы и по запросам процесса.

Это схема состава памяти. Порядок областей и их адреса зависят от ОС, загрузчика и ASLR.

Статические, автоматические и динамические данные

int total = 7;             // статические данные: .data
static int requests;       // статические данные: .bss

void work(void) {
    int local = 3;         // автоматическая переменная
    char *buffer = malloc(1024);
    if (buffer == NULL) return;
    /* Используем buffer. */
    free(buffer);
}
  • total и requests существуют всё время работы программы.
  • local обычно хранится в стеке или регистре; buffer — указатель на отдельный динамический блок.

Возврат из work() сам по себе не освобождает блок malloc. Это делает free().

5 / 82

Как malloc получает память

  • malloc() и free() — функции аллокатора в библиотеке, а не системные вызовы.
  • Аллокатор получает память у ОС крупными областями и выдаёт из них блоки нужного размера.
  • В Linux аллокатор glibc может использовать brk() и анонимные отображения mmap().
  • brk() меняет границу традиционной области динамических данных; mmap() создаёт отдельные отображения.

free() возвращает блок аллокатору. Аллокатор может сохранить его для следующих malloc(), поэтому RSS не обязан уменьшиться.

6 / 82

Виртуальный адрес и физическая страница

  • Адрес в указателе относится к виртуальному адресному пространству процесса.
  • MMU переводит виртуальные адреса в физические с помощью таблиц страниц, которыми управляет ОС.
  • Для диапазона задаются правила: доступ на чтение, запись, исполнение и источник данных.
  • Существование диапазона адресов не означает наличия отдельной физической страницы для каждой его страницы.

Например, ОС может создать анонимное отображение сейчас, а физические страницы предоставлять позже, по мере записи.

7 / 82

mmap: отдельная область памяти

size_t size = 1024 * 1024;
void *p = mmap(NULL, size, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (p == MAP_FAILED) { /* Обрабатываем ошибку. */ }
else {
    /* Читаем и записываем данные через p. */
    munmap(p, size);
}
  • NULL: адрес выбирает ядро; size: длина области.
  • PROT_READ | PROT_WRITE: разрешены чтение и запись.
  • MAP_ANONYMOUS: данные не берутся из файла; munmap() удаляет отображение.

Здесь mmap создаёт динамическую память вне области brk.

8 / 82

Как HotSpot резервирует адреса в Linux

void *base = mmap(NULL, size, PROT_NONE,
                  MAP_PRIVATE | MAP_ANONYMOUS
                              | MAP_NORESERVE,
                  -1, 0);
  • PROT_NONE: доступ к данным по этим адресам пока запрещён.
  • Ядро создаёт отображение: диапазон занят в адресном пространстве процесса.
  • MAP_NORESERVE относится к резервированию swap; виртуальные адреса при этом заняты.

Это обычный путь резервирования HotSpot. Обращение к такой памяти до разрешения доступа вызовет ошибку.

9 / 82

Как HotSpot делает часть области доступной

mmap(base, committed_size, PROT_READ | PROT_WRITE,
     MAP_PRIVATE | MAP_ANONYMOUS | MAP_FIXED,
     -1, 0);
  • Обычный Linux-путь HotSpot заменяет часть своего резервирования доступным отображением.
  • MAP_FIXED задаёт точный адрес; заменять чужие отображения таким способом опасно.
  • Размер доступной части учитывается JVM как committed.

Committed означает доступную JVM ёмкость. Это ещё не число физических страниц, находящихся в RAM.

10 / 82

Что происходит при первом обращении

  • Отображение разрешает запись, но физическая страница для данного адреса может ещё отсутствовать.
  • При первой записи процессор вызывает page fault и передаёт управление ядру.
  • Ядро проверяет права и предоставляет физическую страницу; инструкция продолжает выполнение.
  • Для анонимной памяти чтение может использовать общую нулевую страницу, а запись — потребовать отдельную.

Page fault может быть штатным механизмом. Доступ к PROT_NONE или несуществующему отображению — другая ситуация.

Как увидеть отображения процесса в Linux

cat /proc/PID/maps
cat /proc/PID/smaps_rollup

# Условный фрагмент maps:
70000000-80000000 rw-p 00000000 00:00 0
80000000-b0000000 ---p 00000000 00:00 0
  • maps: диапазоны адресов, права и связанные файлы.
  • rw-p: чтение и запись; ---p: доступа нет; p: private.
  • smaps_rollup: суммарные показатели резидентной памяти и другие данные учёта ОС.

Подпись [heap] в maps обозначает область brk, а не всю динамическую память и не Java heap.

Где находится Java heap

  • У процесса есть виртуальное адресное пространство: адреса, которыми пользуется выполняемый код.
  • ОС управляет отображениями: какие диапазоны доступны процессу и связаны ли они с памятью или файлами.
Адресное пространство процесса JVM
├── Java heap: объекты и массивы
├── Metaspace: метаданные классов
├── Code cache: машинный код
├── Стеки платформенных потоков
└── Библиотеки, буферы, отображения файлов…

Java heap — часть памяти процесса. Metaspace и code cache находятся в том же процессе, но вне Java heap.

Схема показывает состав, а не порядок и размеры областей в адресах.

Что ограничивает -Xmx

java -Xms256m -Xmx1g -Xss1m App
  • -Xms задаёт начальный размер heap, -Xmx — его верхнюю границу.
  • -Xss задаёт размер стека платформенного потока.
  • Лимит памяти контейнера относится ко всему процессу, а не только к heap.

Нельзя выделить под -Xmx всю доступную контейнеру память.

Адреса, ёмкость и занятое место

Пример обычного mmap-пути HotSpot в Linux: резерв 1 GiB, доступно 256 MiB.

ПоказательПримерЧто это означает
Reserved1 GiBmmap создал диапазон 1 GiB. Вне committed доступ запрещён (PROT_NONE).
Committed256 MiBДля 256 MiB разрешены чтение и запись. Физические страницы могут предоставляться по мере обращения.
Used96 MiBАллокатор JVM учитывает 96 MiB как занятые данными внутри committed.

Осталось 160 MiB внутри committed. Чтобы использовать больше 256 MiB, JVM потребуется увеличить committed.

Рост committed может завершиться ошибкой, даже если в reserved ещё есть адреса.

18 / 82

Почему после GC RSS может не уменьшиться

  • RSS — объём страниц процесса, находящихся в физической памяти по учёту ОС. Он включает heap и другие области.
  • GC освободил объекты: used уменьшился, а внутри heap появилось место для новых объектов.
  • JVM может сохранить ёмкость heap: committed не изменился.
  • Если страницы остались в RAM, RSS тоже может не измениться. Возврат памяти ОС — отдельное действие.

Например: used уменьшился с 200 до 80 MiB, committed остался 256 MiB. Неизменный RSS в такой ситуации не доказывает утечку.

19 / 82

Стеки платформенных потоков

  • Содержимое: фреймы, локальные значения и служебные данные, в том числе для нативных вызовов.
  • Освобождение: фреймы снимаются при возврате; стек потока освобождается после его завершения.
  • Разработчик: ограничивает число потоков и глубину вызовов; размер стека задаёт -Xss.
  • Наблюдение: ThreadMXBean — число потоков; Thread.print — вызовы; NMT, категория Thread — память.
jcmd PID Thread.print
jcmd PID VM.native_memory summary

Стеки виртуальных потоков хранятся в heap; стеки потоков-носителей — вне heap.

20 / 82

Metaspace: метаданные классов

  • Содержимое: описания классов и методов, байткод, пулы констант и другие метаданные HotSpot.
  • Освобождение: JVM освобождает метаданные при выгрузке классов; важна достижимость их загрузчика.
  • Разработчик: устраняет удержание старых загрузчиков; ограничивает динамическое создание классов.
  • Наблюдение: пулы Metaspace и Compressed Class Space через MemoryPoolMXBean; число классов — ClassLoadingMXBean.
jcmd PID VM.metaspace basic
jcmd PID VM.classloader_stats

Объекты java.lang.Class находятся в heap. Недостижимость загрузчика не означает немедленной выгрузки.

21 / 82

Code cache: машинный код

  • Содержимое: скомпилированные версии методов, адаптеры вызовов и служебные фрагменты машинного кода.
  • Освобождение: HotSpot удаляет устаревший и больше не используемый код, когда это безопасно.
  • Разработчик: выбирает лимит; исследует чрезмерную генерацию классов и методов.
  • Наблюдение: пулы CodeHeap через MemoryPoolMXBean; заполнение и границы — Compiler.codecache.
jcmd PID Compiler.codecache

Code cache не очищается вызовом close(). При его заполнении работа JIT может ограничиваться.

22 / 82

Direct-буферы: данные вне heap

  • Содержимое: байты, выделенные через ByteBuffer.allocateDirect(); обёртки находятся в heap.
  • Освобождение: в HotSpot — через Cleaner после потери достижимости буфера и удерживающих его представлений.
  • Разработчик: контролирует ссылки и переиспользование; у обычного ByteBuffer нет close().
  • Наблюдение: BufferPoolMXBean, пул direct: Count, TotalCapacity, MemoryUsed.

clear() сбрасывает позицию и лимит; нативную память буфера он не освобождает.

23 / 82

Отображения файлов в память

  • Содержимое: страницы файла, отображённые в адресное пространство через FileChannel.map().
  • Освобождение: для MappedByteBuffer снятие отображения связано с GC; ОС отдельно управляет резидентностью страниц.
  • Разработчик: контролирует число и размер отображений; закрытие канала не снимает существующее отображение.
  • Наблюдение: BufferPoolMXBean, пул mapped; карты памяти и RSS средствами ОС.

force() синхронизирует изменения с файлом, но не снимает отображение.

24 / 82

Arena: явное время жизни памяти

  • Содержимое: нативные сегменты данных, выделенные через Foreign Function & Memory API.
  • Освобождение: для ofConfined() и ofShared() разработчик вызывает close().
  • ofAuto() связывает освобождение с GC; global() не освобождает сегменты до завершения процесса.
  • Наблюдение: учёт числа арен и выделенных байтов в приложении; NMT и показатели ОС — для общей картины.

Сегмент не продлевает жизнь закрытой арены: доступ после close() запрещён.

25 / 82

Служебная память JVM и GC

  • Содержимое: таблицы карт, remembered sets, структуры маркировки, данные JIT и другие структуры HotSpot.
  • Освобождение: JVM переиспользует и освобождает их по правилам соответствующей подсистемы.
  • Разработчик: влияет косвенно — выбором GC, размером heap и характером нагрузки.
  • Наблюдение: категории GC, Compiler и Internal в NMT; динамика reserved и committed.
jcmd PID VM.native_memory summary

Увеличение heap может увеличивать и служебные расходы вне него. Для NMT нужен флаг при запуске.

26 / 82

Память нативных библиотек

  • Содержимое: рабочие области JNI-библиотек, кодеков, TLS и других нативных компонентов.
  • Освобождение: зависит от API библиотеки; возможны явные close(), release или уничтожение контекста.
  • Разработчик: соблюдает контракт владения и освобождает ресурс на всех путях, включая исключения.
  • Наблюдение: метрики библиотеки, RSS и карты памяти; при необходимости — профилировщик нативных аллокаций.

NMT не видит все выделения сторонних библиотек. Стабильный heap не исключает нативную утечку.

Как наблюдать память вне heap

  • Metaspace и code cache: MemoryPoolMXBean; в JConsole — раздел Memory.
  • Direct и mapped: BufferPoolMXBean; в JConsole — раздел MBeans, домен java.nio.
  • Потоки: ThreadMXBean и Thread.print; объём нативных структур — NMT.
  • Прочая нативная память: NMT, метрики библиотек и инструменты ОС.
  • На графиках: расход, предел, темп роста; для буферов и классов — также количество.

Для NMT: -XX:NativeMemoryTracking=summary. Показатель JMX non-heap не включает всю память вне heap.

Из чего состоит объект

Заголовок
→
Поля

  • Заголовок содержит служебную информацию JVM и сведения о классе.
  • Поля содержат примитивные значения и ссылки на другие объекты.

Размер заголовка и ссылок зависит от версии и настроек HotSpot.

31 / 82

Сжатые ссылки

  • На 64-битной платформе ссылка внутри heap может занимать 4 байта.
  • HotSpot может кодировать её как смещение с учётом выравнивания.
  • Возможность сжатия зависит, в частности, от размера и размещения heap.
  • Сжатые ссылки на объекты и на метаданные классов — разные механизмы.

Формула «64-битная JVM → любая ссылка занимает 8 байт» неверна.

32 / 82

Пример расчёта размера

final class Sample {
    int count;
    Object value;
}
  • Для примера: заголовок 12 байт, ссылка 4 байта, выравнивание 8 байт.
  • Поля занимают 4 + 4 байта; вместе с заголовком — 20 байт.
  • После выравнивания получаем 24 байта.
  • Объект, на который указывает value, в эти 24 байта не входит.

Это расчёт для заданной конфигурации, а не гарантия языка. Раскладку можно исследовать с помощью JOL.

Массив — отдельный объект

int[] numbers = new int[1000];
Entry[] entries = new Entry[1000];
  • int[] содержит примитивные значения: 4000 байт данных плюс заголовок и выравнивание.
  • Entry[] содержит 1000 ссылок; изначально каждая равна null.
  • Конструкторы Entry при создании массива не вызываются.
  • Созданные впоследствии Entry и их payload занимают память отдельно.
34 / 82

Как выделяется память

  • В HotSpot небольшие объекты часто выделяются в TLAB — локальном участке heap для потока.
  • Быстрый путь выделения может сводиться к сдвигу указателя свободного места.
  • TLAB принадлежит потоку для выделения памяти; созданные объекты могут быть доступны другим потокам.
  • Пополнение TLAB и выделение крупных объектов требуют других путей обработки.

Создать объект часто дёшево. Стоимость зависит и от того, сколько объектов остаётся жить.

Что хранится во фрейме

  • При вызове метода JVM создаёт фрейм: локальные переменные, стек операндов и служебные данные.
  • Локальная переменная может содержать примитивное значение или ссылку.
  • При завершении вызова его фрейм удаляется.
  • JIT может хранить значения в регистрах, устранять переменные и встраивать вызовы.

Фрейм — модель исполнения JVM. Машинный код может выглядеть иначе.

Зачем нужны поколения

  • Во многих приложениях большинство объектов живёт недолго.
  • Молодые объекты выгодно собирать чаще, отдельно от основной массы долгоживущих.
  • Объекты, пережившие несколько сборок, могут переходить в старое поколение.
  • Разделение на поколения — инженерный приём, а не свойство объектов Java.

Число пережитых сборок — не возраст объекта в секундах.

Одна программа, два режима

import java.util.ArrayList;
import java.util.List;

public class MemoryDemo {
    static volatile int checksum;
    public static void main(String[] args) throws Exception {
        boolean retain = args.length > 0;
        List<byte[]> kept = new ArrayList<>();
        for (int i = 0; i < 320; i++) {
            byte[] block = new byte[256 * 1024];
            block[0] = (byte) i;
            checksum = block[0];
            if (retain) kept.add(block);
            Thread.sleep(25);
        }
        System.out.println("kept=" + kept.size());
    }
}

  • GC освобождает недостижимые объекты; лишние удерживающие ссылки остаются задачей разработчика.
  • Выбор сборщика — компромисс между паузами, CPU, памятью и пропускной способностью.
  • Диагностика связывает рост памяти с конкретным владельцем и временем жизни данных.
