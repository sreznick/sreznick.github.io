Как не скопировать C дважды

evacuate(ref):                 // учебный псевдокод
  if ref == null: return null
  if forwarded(ref): return destination(ref)
  dst = copy_to_free_space(ref)
  set_forwarding(ref, dst)
  return dst
  • B.c и D.c указывают на один C.
  • Первая встреча создаёт C′ и запись C → C′.
  • Вторая встреча возвращает тот же C′. Циклы также завершаются.

Для parallel GC публикация перенаправления требует атомарного протокола.

27 / 87

Почему выделяют молодые объекты

  • Во многих приложениях большая доля объектов быстро становится недостижимой.
  • Небольшую область с малым числом выживших выгодно часто копировать.
  • Долгоживущие объекты можно проверять реже.
  • Гипотеза зависит от нагрузки: высокая выживаемость меняет стоимость GC.

Поколения — стратегия сокращения работы, а не свойство Java-объекта.

Card table ≠ remembered set

A:card7 содержит поле holder.item → объект в B
Учёт входящих ссылок: RSet[B] включает A:card7
Сборка B: сканируем A:card7 → находим holder.item
  • Refinement обрабатывает dirty cards и обновляет remembered sets.
  • При эвакуации B сканируем указанные cards и исправляем найденные ссылки.
  • Card table: где были записи. RSet: откуда могут приходить ссылки в собираемую область.

Учебная схема: B отслеживается отдельно от A.

SATB: сохранить старую ссылку

// Учебная модель pre-write barrier:
old = d.c;
if (marking && old != null) satbQueue.add(old);
d.c = null;
  • До удаления старого ребра запоминаем его цель.
  • GC позже обработает C из очереди SATB.
  • Сохраняем достижимость логического снимка на начало цикла.

Это не физическая копия heap. Барьеры сохраняют достаточно информации.

Incremental update: учесть новое ребро

// Учебная модель insert barrier:
a.c = c;
if (marking && isBlack(a) && isWhite(c))
  shadeGray(c);
  • Другой способ: учитывать появление опасной новой ссылки.
  • Реализация может запоминать объект-источник для повторного просмотра.
  • Псевдокод поясняет инвариант. Атомарность, порядок операций и гонки требуют отдельного протокола.

SATB и incremental update по-разному сохраняют корректность обхода.

Новые объекты и floating garbage

  • Новые аллокации во время цикла требуют специального правила живости.
  • Например, новые выделения в маркируемой области считаются живыми для текущего цикла.
  • В SATB объект, живой в начале, может умереть во время маркировки.
  • Такой floating garbage допустимо освободить в следующем цикле.

Безопасно временно сохранить мусор. Освободить живое — ошибка.

Барьер чтения: получить актуальный объект

// Концептуальная схема, не код конкретного GC:
p = load_reference(slot);
if (needs_resolution(p)) {
  p = resolve_or_relocate(p);
  try_heal_reference(slot, p);
}
use(p);
  • Fast path дешёво проверяет, нужна ли дополнительная работа.
  • Slow path разрешает старый адрес или помогает перемещению.
  • Self-healing уменьшает число будущих обращений по старой ссылке.

Как не потерять запись во время копирования

  • Простая схема «memcpy + forwarding pointer» некорректна при произвольных параллельных записях.
  • Сборщик ограничивает доступ к перемещаемому объекту через свой протокол барьеров.
  • Поток приложения может помочь эвакуации до получения пригодной для использования ссылки.
  • Атомарная публикация выбирает одну каноническую копию.

Разные GC реализуют этот протокол по-разному; универсального одного CAS недостаточно.

Shenandoah load-reference barrier может эвакуировать объект до передачи ссылки приложению. В ZGC границы relocation фаз и обработка ссылок/корней обеспечивают пригодность uncolored указателей; не следует объяснять оба GC как произвольный Brooks read barrier на каждом поле.
45 / 87

Когда можно переиспользовать старое место

  • Создать новую копию недостаточно.
  • Нужно исключить использование старого объекта без разрешения ссылки.
  • Сборщик координирует фазы, обрабатывает корни и обновляет либо разрешает оставшиеся ссылки.
  • Метаданные перенаправления живут столько, сколько они нужны старым ссылкам.

Повторное использование памяти — отдельное условие корректности.

Короткие паузы требуют ресурсов

  • Барьеры выполняются в потоках приложения.
  • Concurrent GC конкурирует за CPU и пропускную способность памяти.
  • Пока идёт цикл, приложение продолжает аллокации.
  • Нужен запас места и возможность завершить цикл вовремя.
Оценка запаса: allocation_rate × cycle_time + резерв

Это грубая модель: поколения, promotion и темп освобождения меняют расчёт.

Humongous objects и нехватка места

  • В G1 JDK 25 humongous: полный размер объекта строго больше половины региона.
  • Такой объект занимает последовательность смежных регионов в old.

ZGC: почему приложение всё же может ждать

  • Конкурентный цикл должен успевать освобождать память.
  • Если нет места для аллокации, поток может ждать работу GC — allocation stall.
  • CPU quota и высокая скорость аллокаций меняют запас времени.
  • Измеряем latency приложения, CPU и stalls вместе с GC-паузами.

Allocation stall и глобальная STW-пауза — разные события.

Shenandoah: конкурентная эвакуация

  • -XX:+UseShenandoahGC при поддержке в сборке JDK.
  • Маркировка, эвакуация и обновление ссылок выполняются преимущественно конкурентно.
  • Load-reference barrier разрешает forwarding; может помочь эвакуации.
  • В JDK 25 forwarding хранится через mark word заголовка.
  • Перед повторным использованием регионов завершается согласование ссылок.
