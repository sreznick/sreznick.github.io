Цель блока — показать, что код может вести себя не так, как написан. Запускаем вживую, желательно с -Xint и без.

Пример 1: флаг остановки

class Stopper {
    static boolean stop = false;

    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> {
            while (!stop) { }          // завершится ли?
            System.out.println("stopped");
        });
        t.start();
        Thread.sleep(1000);
        stop = true;                   // останавливаем t
    }
}
Запустить обычно и с -Xint. Спросить аудиторию, что произойдёт.

Что произошло?

  • Поток t может никогда не увидеть stop = true
  • JIT вправе вынести чтение stop из цикла и превратить его в while (true)
  • С -Xint (интерпретатор) программа завершается, с JIT — зависает
  • Поведение зависит от режима компиляции — значит, это не детерминированный баг, а отсутствие гарантий
  • Проверьте: что изменится, если сделать stop volatile?

Пример 2: порядок операций

static int x, y, r1, r2;

// Поток 1                // Поток 2
x = 1;                    y = 1;
r1 = y;                   r2 = x;

// Возможен ли исход r1 == 0 && r2 == 0 ?

Каждая переменная сначала записывается, потом читается другой. Казалось бы, «кто-то будет первым».

Дать проголосовать. Правильный ответ — да, возможен.

Ответ: да, возможен

  • Исход (0, 0) наблюдается на реальном железе; проверяется тестом jcstress
  • Причины: буфер записи процессора, переупорядочивание JIT
  • Наивная модель «потоки чередуют строки кода» (sequential consistency) не действует
  • Разберёмся, что именно гарантируется: блок 4 (JMM) и блок 6 (Intel)

Программа-пример из блока (очередь) пригодится в блоке 3 как подопытная.

Потоки: создание и запуск

Thread t = new Thread(() -> {
    System.out.println("hello from " + Thread.currentThread().getName());
}, "worker-1");

t.start();     // создаёт поток ОС и вызывает run() в нём
// t.run();    // ОШИБКА: выполнится в текущем потоке
t.join();      // ждём завершения t

// daemon-потоки не удерживают JVM от завершения
t.setDaemon(true);   // до start()

Имя потока пригодится в блоке 3: оно видно в Linux.

Состояния потока

            start()                       run() завершился
  NEW ─────────────► RUNNABLE ────────────────────────► TERMINATED
                       │    ▲
       монитор занят   │    │  монитор получен
                       ▼    │
                      BLOCKED

  RUNNABLE ── wait() / join() / park() ──► WAITING
  RUNNABLE ── sleep(t) / wait(t) ────────► TIMED_WAITING
  WAITING, TIMED_WAITING ── notify / таймаут / interrupt ──► RUNNABLE
Отметить: RUNNABLE в Java включает и «выполняется», и «ждёт в нативном I/O». Вернёмся в блоке 3.

interrupt(): вежливая просьба

  • interrupt() выставляет флаг; сам поток не прерывается
  • Блокирующие методы (sleep, wait, take) бросают InterruptedException и сбрасывают флаг
  • Нельзя «глотать» исключение молча
try {
    queue.take();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // восстановить флаг
    return;                               // и выйти
}

stop() объявлен устаревшим: убивает поток посреди инварианта.

synchronized и монитор

private final Object lock = new Object();
private int count;

void inc() {
    synchronized (lock) {        // захват монитора lock
        count++;
    }                            // освобождение монитора
}

synchronized void dec() { count--; }         // монитор this
static synchronized void reset() { }         // монитор Foo.class
  • У каждого объекта есть монитор; реентерабельный
  • Кроме взаимного исключения даёт видимость (блок 4)
  • Лучше синхронизироваться на приватном объекте

wait / notify: правила

  • Зачем: ждать выполнения условия, а не крутить цикл
  • Вызывать только под монитором этого же объекта, иначе IllegalMonitorStateException
  • wait() отпускает монитор и усыпляет поток
  • notify() будит один поток, notifyAll() — все; монитор при этом не отпускается до конца блока
  • После пробуждения поток должен заново захватить монитор
  • wait всегда в цикле while

Канонический шаблон

// Ожидающий поток
synchronized (lock) {
    while (!condition) {          // while, а не if!
        lock.wait();
    }
    // условие выполнено, монитор у нас
}

// Сигнализирующий поток
synchronized (lock) {
    condition = true;             // сначала меняем состояние
    lock.notifyAll();             // потом будим
}

Причины: ложные пробуждения, «чужие» пробуждения, состояние могли изменить.

Пример: ограниченная очередь

class BoundedQueue<T> {
    private final Queue<T> q = new ArrayDeque<>();
    private final int cap;
    BoundedQueue(int cap) { this.cap = cap; }
    synchronized void put(T x) throws InterruptedException {
        while (q.size() == cap) wait();      // очередь полна
        q.add(x);
        notifyAll();
    }

    synchronized T take() throws InterruptedException {
        while (q.isEmpty()) wait();          // очередь пуста
        T x = q.remove();
        notifyAll();
        return x;
    }
}
Это подопытная программа для блока 3: производители и потребители будут ждать в wait().

Типичные ошибки

  • if вместо while вокруг wait
  • notify без изменения состояния (сигнал «в пустоту»)
  • wait/notify на объекте, монитор которого не захвачен
  • notify вместо notifyAll, когда ждут разные условия
  • Проглоченный InterruptedException
  • Реальная жизнь: BlockingQueue, Lock/Condition, CountDownLatch

Блок предполагает Linux с доступом к procfs. В контейнерах stack и perf часто недоступны.

Поток Java = поток Linux

  • HotSpot на Linux: модель 1:1, каждый поток Java — поток ядра (pthread)
  • У него свой TID (LWP) и свой стек, общий с остальными — PID и дескрипторы
  • Служебные потоки JVM: GC, компиляторы C1/C2, VM Thread, Signal Dispatcher, Reference Handler…
  • Имя из setName попадает в ядро (поле comm), но обрезается до 15 символов
  • Виртуальные потоки в ядре не видны: только «носители»

ps, top, pidstat

$ ps -L -p $PID -o pid,tid,pcpu,stat,wchan:24,comm
$ ps -eLf | grep java          # столбец NLWP — число потоков
$ top -H -p $PID               # режим потоков: кто «горячий»
$ pidstat -t -p $PID 1         # CPU по потокам (sysstat)
$ pidstat -w -t -p $PID 1      # переключения контекста
$ taskset -cp $TID             # привязка к ядрам
  • Thread.setPriority на Linux почти ничего не меняет
  • Приоритетами управляют nice/chrt уже на уровне ОС

procfs: что смотреть

Файл Что даёт

Ограничения и контейнеры

  • Контейнер: /proc/PID/cgroup, лимиты CPU и памяти
  • Runtime.availableProcessors() учитывает лимиты cgroup
  • pids.max в cgroup ограничивает число потоков

Java Memory Model

  • Зачем нужна модель
  • Понятия: действия, гонка, DRF-SC
  • Happens-before
  • Безопасная публикация, final, DCL
  • Что разрешено и запрещено
Центральный блок. Возвращаемся к примерам 1 и 2 из блока 1.

Откуда берутся «странности»

  • Компилятор (JIT): переставляет операции, держит переменные в регистрах
  • Процессор: буфер записи, внеочередное исполнение
  • Кеши: у каждого ядра своя копия данных

JMM — договор между программистом, компилятором и процессором: какие результаты допустимы.

Пишем код, опираясь на гарантии языка, а не на устройство железа.

Основные понятия

  • Действия: чтение/запись, захват/освобождение монитора, операции с volatile, запуск и завершение потока
  • Порядок программы — порядок внутри одного потока; другие потоки его могут не видеть
  • Гонка данных: два обращения к переменной, одно из них запись, между ними нет happens-before
  • DRF-SC: программа без гонок ведёт себя так, как будто выполняется последовательно

Happens-before

  • Если A happens-before B, то эффекты A видны B и A упорядочено перед B
  • Порядок программы внутри потока
  • Освобождение монитора → последующий захват того же монитора
  • Запись volatile → последующее чтение того же поля
  • Thread.start() → всё в запущенном потоке
  • Всё в потоке → успешный join() этого потока
  • Транзитивность: A → B и B → C дают A → C

Пример: volatile «публикует» данные

int data;
volatile boolean ready;

// Поток A                 // Поток B
data = 42;                 if (ready) {
ready = true;                  print(data);      // 42
                           }
  • data = 42 → ready = true: порядок программы
  • ready = true → чтение ready: volatile
  • Чтение ready → чтение data: порядок программы
  • Транзитивность: B гарантированно видит 42
Вернуться к примеру 1 из блока 1: с volatile флаг останова работает.

Безопасная публикация и final

  • Утечка this из конструктора: другой поток может увидеть объект недостроенным
  • Поля final после конструктора видны корректно (freeze) — только если this не утёк
  • Способы безопасно опубликовать объект: volatile-поле, final-поле, монитор, статический инициализатор, потокобезопасные коллекции
  • Публикация через обычное поле — гонка данных

Double-checked locking

class Singleton {
    private static volatile Singleton inst;      // volatile обязателен

    static Singleton get() {
        Singleton s = inst;
        if (s == null) {
            synchronized (Singleton.class) {
                s = inst;
                if (s == null) inst = s = new Singleton();
            }
        }
        return s;
    }
}

Альтернатива: holder-идиома (класс-держатель со статическим полем).

Почему без volatile ломается

  • new Singleton() = выделить память → инициализировать поля → записать ссылку
  • Без happens-before запись ссылки может оказаться раньше инициализации полей
  • Другой поток видит inst != null и работает с недостроенным объектом
  • volatile устанавливает порядок и запрещает такую перестановку

Что разрешено и запрещено

  • Исход (0, 0) из блока 1 разрешён: гонка данных, порядок не определён
  • Чтение/запись long и double без volatile может быть неатомарным (на 32-битных JVM)
  • Значения «из воздуха» (out-of-thin-air) запрещены; формализация сложна
  • Спецификация: JLS §17.4; проверять гипотезы — jcstress

volatile и Atomic*

  • Что даёт volatile
  • Что даёт Atomic*
  • Сравнение и выбор

volatile: гарантии

  • Видимость: чтение видит последнюю запись (happens-before)
  • Упорядочивание: операции до записи не «перепрыгнут» через неё
  • Нет атомарности составных операций
  • Подходит: флаг остановки, публикация неизменяемого объекта, один писатель — много читателей, DCL

volatile ≠ атомарность

volatile int counter;

void inc() {
    counter++;     // читаем, прибавляем, пишем — три действия!
}
  • Два потока могут прочитать одно значение и записать одинаковый результат
  • Видимость есть, атомарности нет: итог меньше ожидаемого
  • Решения: synchronized или AtomicInteger
Короткая демонстрация: два потока по миллиону инкрементов.

Atomic*: API и CAS

AtomicInteger n = new AtomicInteger();

n.incrementAndGet();
n.compareAndSet(5, 6);          // атомарно: если 5, то 6
n.updateAndGet(x -> x * 2);

// CAS-цикл вручную
int old, next;
do {
    old  = n.get();
    next = old + 1;
} while (!n.compareAndSet(old, next));

Семантика памяти — как у volatile, плюс атомарность одной операции.

Тонкости

  • ABA: значение изменилось A → B → A, CAS этого не заметит; помогает AtomicStampedReference
  • LongAdder: при высокой конкуренции быстрее AtomicLong для счётчиков
  • VarHandle: режимы доступа plain, opaque, acquire/release, volatile
  • Lock-free ≠ wait-free: CAS-цикл может «крутиться» при конкуренции

Сравнение

volatile Atomic* synchronized
Видимость да да да
Упорядочивание да да да
Атомарность составных операций нет одна операция любой блок
Блокирует потоки нет нет да
Несколько переменных сразу нет нет да

Как выбирать

  • Одиночный флаг → volatile
  • Счётчик, накопление, один CAS → Atomic*
  • Инвариант на несколько полей → synchronized или Lock
  • Вопрос: можно ли хранить min и max в двух атомиках при инварианте min ≤ max?
Ответ: нет — между двумя обновлениями другой поток увидит нарушенный инвариант.

JMM на Intel

  • x86-TSO и буфер записи
  • Барьеры в JIT
  • Java → инструкции x86
  • Смотрим ассемблер

Модель памяти x86: TSO

Пара операций Может ли поменяться?
Load → Load нет
Load → Store нет
Store → Store нет
Store → Load да (из-за буфера записи)

Модель «сильная»: почти все порядки сохраняются. Слабее у ARM и POWER.

Буфер записи объясняет (0, 0)

Ядро 0                    Ядро 1
x = 1  ─► [буфер записи]  y = 1  ─► [буфер записи]
r1 = y   (читает y=0)     r2 = x   (читает x=0)
             ▼                         ▼
        запись x = 1 уходит в кеш позже, чем чтение y
  • Запись сначала оседает в буфере, а чтение идёт вперёд
  • MESI обеспечивает согласованность кешей, но буфер не отменяет

Барьеры в JIT

  • Четыре вида: LoadLoad, LoadStore, StoreStore, StoreLoad
  • «JSR-133 Cookbook»: какие барьеры компилятор ставит вокруг volatile и мониторов
  • Барьер бывает для процессора и для самого JIT (запрет перестановок при оптимизации)
  • На x86 из четырёх реально нужен StoreLoad — он самый дорогой

Java → инструкции x86

Java Типичный код x86
Обычное чтение/запись mov
Чтение volatile mov (+ запрет оптимизаций JIT)
Запись volatile mov + lock addl $0,(%rsp) (или xchg)
Вход/выход synchronized lock cmpxchg
incrementAndGet lock xadd
compareAndSet lock cmpxchg

Чтение volatile «бесплатно», запись дороже. Префикс lock — полный барьер.

Код зависит от версии JVM и режима JIT. Опираемся на гарантии JMM.

Почему это не отменяет volatile

  • JIT переставляет и кеширует независимо от процессора
  • На других архитектурах код другой (ARM, POWER)
  • Детали зависят от версии JVM
  • Рассуждаем о гарантиях JMM, а не об инструкциях

  • Поток Java — поток Linux: top -H, /proc, strace, nid в jstack
