Контекст: зачем вообще специальный формат

  • Что за задачу мы решаем
  • Почему одна большая таблица не подходит
  • Термины, которые ещё встретятся
Аудитория не знает Spark/Hive и не писала ETL на Python - вводим термины по ходу.

Что за задачу мы решаем

  • Миллиарды строк логов: event_id, user_id, event_type, country, payload, ts
  • Данные слишком большие для одной обычной базы на одной машине
  • Хранятся как файлы в распределённом хранилище (кластер дисков или облако вроде S3)
  • Читает и считает по ним агрегаты специальная программа — движок обработки данных (Spark, Trino, Hive и другие — сегодня не важно, какой именно)
  • Движок параллельно читает файл с разных машин и умеет выполнять SQL-подобные запросы поверх файлов

Ключевая мысль

  • От того, как именно данные лежат в файле на диске, критически зависит скорость и стоимость ответа на запрос
  • Сегодня разбираем два формата файлов, спроектированных именно для этого: Parquet и ORC

Почему одна большая таблица плохо подходит

SELECT country, COUNT(*)
FROM events
WHERE event_type = 'purchase'
  AND ts BETWEEN '2026-01-01' AND '2026-01-31'
GROUP BY country;

Запрос трогает 3 столбца из 6. payload (тяжёлый JSON) и user_id вообще не нужны.

Строка за строкой — почему это плохо

  • Если файл хранит данные строка за строкой (как CSV), нельзя прочитать только нужные столбцы — они физически перемешаны с остальными
  • Чтобы добраться до country во второй строке, нужно пройти мимо всех полей первой
  • Сжатие тоже работает не очень: в одной строке вперемешку число, строка, JSON — мало похожих байт подряд
Подводка к идее: хранить по столбцам, а не по строкам - разберём подробно в блоке 1.

Термины, которые ещё встретятся

  • HDFS / S3 — распределённые хранилища файлов (кластер / облако). Доступ к ним — сетевой, не такой быстрый, как к локальному диску
  • Spark — популярный движок распределённой обработки; читает Parquet «из коробки» как формат по умолчанию
  • Hive — более старая система, одной из первых принесла в Hadoop идею «пишите SQL, а он превратится в задачи над файлами»; плотно связана с ORC
  • Сегодня смотрим именно на файлы, движки упоминаются только для контекста

Row-oriented vs column-oriented

Строки (row-oriented):           Столбцы (column-oriented):
+---+--------+--------+          +---+---+---+  +--------+--------+
| 1 | Ann    | RU     |          | 1 | 2 | 3 |  | Ann    | Bob    |
+---+--------+--------+          +---+---+---+  | Cid    |
| 2 | Bob    | RU     |           id-столбец      +--------+
+---+--------+--------+                            name-столбец
| 3 | Cid    | US     |          +--------+--------+
+---+--------+--------+          | RU     | RU     | US
                                  +--------+--------+
                                    country-столбец

Те же данные — просто иначе разложены по байтам на диске.

Когда что выигрывает

  • Точечный доступ («вся запись про пользователя X») — построчное хранение выигрывает: значения строки лежат рядом
  • Агрегации по немногим столбцам на многих строках («покупки по странам за январь») — колоночное выигрывает: читаем только нужные столбцы

Что даёт колоночность

  • Column pruning: запрос трогает 3 столбца из 50 — читаем с диска только их
  • Лучшее сжатие: однородные данные одного столбца сжимаются плотнее, чем вперемешку
  • Специализированные кодировки: словарь для малой кардинальности, дельты для почти монотонных чисел, RLE для повторов — ничего из этого не имеет смысла для перемешанных строк
  • Обработка пачками: движок обрабатывает столбец сразу батчем одного типа — быстрее для CPU

Цена вопроса

  • Дорого менять одну запись: вставить строку — значит дописать её кусочек в каждый столбец отдельно. Поэтому колоночные форматы почти всегда неизменяемые
  • Дороже писать «по одной строке»: писатель должен накопить много строк в памяти, прежде чем разложить по столбцам
  • Плохо для «вся запись по ID»: значение нужно собрать из каждого столбца отдельно
  • Вывод: колоночные форматы — для батчевой аналитики, не для систем с частыми точечными изменениями

Кто ещё есть рядом

  • Avro — построчный бинарный формат со схемой; хорош для потоковой передачи (записи по одной) и частой смены схемы целиком
  • CSV/JSON — текстовые, без схемы и сжатия «из коробки»; удобны для обмена и отладки, плохи для больших объёмов
  • Parquet и ORC решают одну задачу и конкурируют напрямую — разбираем дальше

Parquet изнутри

История и контекст

  • 2013 год, совместная разработка Twitter и Cloudera
  • Вдохновлён статьёй Google Dremel (2010) — про хранение вложенных данных в колоночном виде
  • Спроектирован для вложенных структур (списков, полей-объектов), не только для плоских таблиц

Общая структура файла

+-----------------------------+
| "PAR1"  (magic, 4 байта)     |
+-----------------------------+
| Row Group 0                  |
|   Column Chunk (col A)       |
|     Page 0, Page 1, ...      |
|   Column Chunk (col B)       |
|     Page 0, Page 1, ...      |
+-----------------------------+
| Row Group 1  ...             |
+-----------------------------+
| File Metadata (Footer)       |
|   схема, список row group'ов,|
|   статистика по чанкам       |
+-----------------------------+
| Footer length (4 байта)      |
+-----------------------------+
| "PAR1"  (magic, 4 байта)     |
+-----------------------------+

Метаданные — в конце файла: сначала читаем хвост, потом прыгаем к футеру.

Row Group → Column Chunk → Page

  • Row Group — горизонтальный срез строк; внутри данные организованы по столбцам
  • Column Chunk — все данные ОДНОГО столбца для ОДНОГО row group, лежат непрерывно — отсюда column pruning
  • Page (~1 МБ) — единица кодирования и сжатия: dictionary page (словарь) + data page(s)
  • Три уровня: row group — параллелизм, column chunk — pruning, page — мелкий сжатие/skip

Dictionary encoding

Словарь:      0 -> "RU", 1 -> "US", 2 -> "DE"
Данные:       0, 0, 1, 0, 2, 1, ...
  • Вместо строки в каждой строке — маленькое число (индекс словаря)
  • Текст хранится один раз, в словаре
  • Эффективно именно потому, что все значения столбца лежат рядом

RLE и гибридное кодирование

0, 0, 0, 0, 0, 1, 1, 1  ->  (0, 5 раз), (1, 3 раза)
  • RLE: длинные повторы заменяются парой «значение + сколько раз»
  • RLE/Bit-Packing Hybrid: повторы — через RLE, разбросанные значения — упаковка минимальным числом бит
  • 3 уникальных значения в словаре — индексу хватит 2 бит, а не байта/int32

Delta encoding

1000, 1002, 1005, 1009  ->  база 1000, дельты: +2, +3, +4
  • Для почти монотонных целых (id, временные метки в отсортированном логе)
  • Дельты обычно намного меньше самих значений — меньше бит на хранение
  • Поверх всех кодировок ещё накладывается сжатие страницы целиком (Snappy, GZIP, ZSTD, LZ4) — экономия двухуровневая

Вложенные данные: зачем

{"name": "Ann", "phones": ["+7...", "+1..."]}
{"name": "Bob", "phones": []}
{"name": "Cid", "phones": null}

Как хранить phones колоночно, если число значений разное — или их нет вовсе?

Repetition и definition levels

  • Для каждого значения хранятся два маленьких числа
  • definition level — на каком уровне вложенности значение реально определено (не null из-за отсутствующего родителя)
  • repetition level — на каком уровне вложенности началось повторение (новый элемент списка / новая запись)
  • Это Dremel-кодирование: любая вложенность сводится к плоским столбцам + два числа на значение
  • Главная мысль: вложенность не ломает колоночность

Статистика и predicate pushdown

SELECT * FROM events WHERE ts >= '2026-06-01';
  • В футере и в заголовке каждой page — статистика: min, max, null_count
  • Если max(ts) row group'а раньше границы — движок вообще не открывает этот row group
  • Predicate pushdown: фильтр проталкивается вниз, до физических кусков файла
  • Column Index / Offset Index — та же идея, но на уровне отдельной page (~1 МБ), не всего chunk'а

Bloom-фильтры

  • Для точных равенств (WHERE user_id = 12345) min/max не помогает — значение может лежать в диапазоне, но отсутствовать
  • Bloom-фильтр по column chunk отвечает: «точно нет» или «может быть, есть»
  • Снова позволяет пропускать чанки без чтения

Схема и метаданные

  • Схема хранится в футере в формате Apache Thrift
  • Физические типы (INT32, BYTE_ARRAY, ...) — как значение лежит на диске
  • Логические типы (STRING, DECIMAL, DATE, LIST, MAP) — как физический тип интерпретировать
  • Разделение даёт эволюцию схемы: новый (nullable) столбец не требует переписывать старые файлы

ORC изнутри

  • История

  • Stripe
  • Integer RLE v2

  • ACID в Hive

История и контекст

  • Тоже 2013 год, экосистема Hive (Hortonworks/Facebook)
  • Замена более простому формату, который использовался раньше
  • В отличие от Parquet, спроектирован конкретно под Hive — отсюда глубокая интеграция с транзакциями и predicate pushdown через Hive

Общая структура файла

+-------------------------------+
| Stripe 0                       |
|   Index Data                   |
|   Row Data                     |
|   Stripe Footer                |
+-------------------------------+
| Stripe 1  ...                  |
+-------------------------------+
| File Footer                    |
|   stripe'ы, схема, статистика  |
+-------------------------------+
| Postscript                     |
|   компрессор, длина футера,    |
|   magic "ORC"                  |
+-------------------------------+

Как и у Parquet — метаданные в конце. Единица среза называется stripe (обычно 64–256 МБ, крупнее row group).

Внутри stripe'а

  • Index Data — min/max/сумма/количество на каждые 10 000 строк, плюс позиции для перехода без полной распаковки
  • Row Data — данные по столбцам через streams: PRESENT (null-маска), DATA (индексы словаря), LENGTH, DICTIONARY_DATA
  • Stripe Footer — где какой stream лежит и какая кодировка у столбца

Integer RLE v2

  • SHORT_REPEAT — короткая серия одинаковых значений
  • DIRECT — bit-packing без дополнительной модели
  • PATCHED_BASE — база + отклонения, редкие выбросы — отдельным патчем
  • DELTA — как в Parquet, с адаптивным знаком и шагом
  • Идея та же, что у Parquet, реализация — своя, независимая

Индексы и predicate pushdown

  • Встроенные индексы на каждые 10 000 строк — то же, что Column Index у Parquet, но с первого дня формата
  • Опциональные bloom-фильтры — по тому же принципу, что в Parquet
  • SARGs (Search Arguments): Hive переводит WHERE в структуру, по которой читающая библиотека решает, что не читать

ACID и особая роль в Hive

  • ORC — родной формат транзакций Hive (изменить/удалить отдельные строки, не только дописать)
  • Изменения — в отдельных delta-файлах рядом с основными данными
  • При чтении данные собираются «на лету» из base + delta (merge-on-read)
  • Фоновый процесс периодически объединяет всё обратно (compaction)
  • У Parquet такого нет — транзакционность добавляют надстройки: Iceberg, Delta Lake, Hudi

Вложенные типы в ORC

  • Поддерживает STRUCT, LIST, MAP, UNION
  • Кодирует проще, чем Parquet: без Dremel-механизма, через дополнительные потоки длины
  • Менее гибко для очень глубокой вложенности, но полностью достаточно для типичных Hive-схем (обычно 2–3 уровня)

Таблица сравнения

Parquet ORC
Откуда Twitter/Cloudera, Dremel Hortonworks/Facebook, Hive
Срез строк Row Group Stripe (крупнее)
Метаданные Apache Thrift Свой бинарный формат
Целые числа Словарь + RLE/bit-packing, Delta Integer RLE v2 (4 режима)
Вложенные типы Dremel — гибче Потоки длины — проще
Изменение строк Нет своей — Iceberg/Delta/Hudi Встроено в Hive ACID
Сильнее всего Data lake общего назначения Hive, изменяемые таблицы
Python/pandas Широкая, «родная» Есть, но менее полная

Что определяет выбор на практике

  • В какую систему вы уже встроены: без привязки к Hive-транзакциям — Parquet почти автоматический выбор
  • Инструменты за пределами Hadoop: Python/ноутбуки/аналитика — Parquet поддержан заметно шире
  • Разница в скорости при аккуратной настройке обычно не драматична (единицы, изредка десятки процентов)
  • Совет по умолчанию: без причины опираться на Hive — начинать с Parquet

pandas: читаем и пишем Parquet

import pandas as pd

# columns=... - реальный column pruning: остальные столбцы
# вообще не читаются с диска
df = pd.read_parquet(
    "events.parquet",
    columns=["country", "event_type", "ts"],
)
print(df.head())

df.to_parquet(
    "events_out.parquet",
    engine="pyarrow",
    compression="zstd",       # snappy | gzip | zstd
    row_group_size=500_000,   # строк на один row group
)

То же самое для ORC

import pyarrow.orc as orc

table = orc.read_table("events.orc", columns=["country", "event_type"])
orc.write_table(table, "events_out.orc", compression="zstd")

Демо: один датасет в CSV и в Parquet (Snappy/ZSTD), сравнить размер и время агрегирующего запроса.

Размер row group / stripe

  • Слишком маленький — накладные расходы на метаданные перевешивают пользу, сжатие хуже
  • Слишком большой — грубый predicate pushdown, много памяти писателю
  • Стартовая точка: 128 МБ – 1 ГБ на row group/stripe

Проблема мелких файлов и выбор компрессора

  • Тысячи файлов по 10 КБ — время уходит на открытие файлов, а не на данные; нужна периодическая компактификация
  • Snappy — быстро, средне сжимает (частое чтение)
  • ZSTD — обычно лучший баланс сегодня
  • GZIP — сильнее сжимает, заметно медленнее (архив)

Партиционирование по каталогам

country=RU/date=2026-06-01/part-0001.parquet
  • Ещё один, более ранний уровень «обрезки» — по пути в файловой системе
  • WHERE country = 'RU' — движок не заглядывает в папки других стран, ещё до открытия файла

Итоги

  • Колоночное хранение выигрывает там, где читают немного столбцов из многих строк, и проигрывает при частом точечном доступе
  • Parquet и ORC — не «таблица, повёрнутая набок»: трёхуровневая структура, статистика для pushdown, продуманные кодировки, опциональные bloom-фильтры
  • Parquet вырос из Dremel/вложенных структур — сегодня самый широко поддержанный формат озёр данных
  • ORC вырос из Hive — по-прежнему сильнее всего там же, особенно с изменяемыми таблицами
  • Для нового проекта без привязки к Hive — разумная точка старта: Parquet
