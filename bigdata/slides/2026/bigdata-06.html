Мотивация

Почему не MapReduce

01

Проблемы MapReduce

  • Жесткая модель: map → shuffle → reduce. Нельзя выразить произвольный граф вычислений
  • Промежуточные данные на диск: каждый шаг пишет в HDFS. Для итеративных алгоритмов — катастрофа
  • Нет in-memory: даже если данные помещаются в память, MR все равно пишет на диск
  • Сложность кода: все руками — комбинаторы, партишнеры, счетчики

Итеративный алгоритм: PageRank

MapReduceSpark
Итераций1010
Jobs10 (каждая итерация = отдельный job)1 job с конвейером
Промежуточные данныеНа диск (HDFS)В памяти (RDD cache)
ВремяЧасыМинуты

Ключевое отличие: Spark не пересчитывает данные с нуля, а конвейеризирует операции

Решение: Spark

  • RDD — абстракция распределенной памяти (иммутабельная, ленивая, с lineage)
  • Lazy evaluation — ничего не вычисляется, пока не потребуется результат
  • DAG — граф зависимостей вместо цепочки jobs
  • In-memory — данные кэшируются в памяти, а не пишутся на диск

Spark — не про "быстрее", а про "меньше дисковых I/O и меньше кода"

RDD

Resilient Distributed Dataset

02

RDD: Определение

  • Иммутабельная — нельзя изменить, только создать новую
  • Распределенная — данные разбиты на партиции
  • Ленивая — вычисляется только при вызове action
  • С lineage — знает свою историю (как восстановиться после сбоя)

Важно: RDD — это legacy API. DataFrame/Dataset — другая парадигма (декларативная), а не просто "RDD + оптимизации". Но понимание RDD — фундамент

Партиционирование

  • Partition — единица параллелизма (аналог split в MR)
  • Один partition = одна задача (task)
  • Количество партиций определяет степень параллелизма

Пример

// 4 партиции = 4 таска
val rdd = sc.parallelize(1 to 100, 4)

Партиции распределяются по Executor'ам. Каждый Executor может обрабатывать несколько партиций

Lineage

  • Граф зависимостей (DAG) — как RDD был создан
  • При потере партиции — перевычисление по lineage
  • Не нужно хранить копии данных — достаточно помнить, как они были получены

Пример

val rdd = sc.textFile("hdfs://...")   // lineage: file
    .flatMap(_.split(" "))             // lineage: file -> flatMap
    .map((_, 1))                       // lineage: file -> flatMap -> map
    .reduceByKey(_ + _)                // lineage: file -> flatMap -> map -> reduceByKey

Если партиция потеряна — Spark пересчитает только её, по цепочке

Lineage vs Репликация

Репликация HDFSLineage Spark
Что защищаетДанные на дискеПартиции RDD во время вычислений
КакКопии на разных узлахПересчет по графу операций

Это разные механизмы для разных целей. Они не заменяют друг друга

Типы операций

ТипОперацииПоведение
Transformations (lazy)map, filter, flatMap, groupByKey, reduceByKey, joinВозвращают новый RDD. Не выполняются сразу
Actions (eager)collect, count, reduce, saveAsTextFileЗапускают вычисления. Возвращают результат

Transformations строят DAG. Actions запускают его выполнение

Narrow vs Wide зависимости

ТипОписаниеПримерыShuffle
Narrow1 partition → 1 partitionmap, filter, coalesceНет. Pipelining внутри stage
WideN partitions → M partitionsgroupByKey, join, repartitionДа. Граница stage

Narrow зависимости позволяют конвейеризировать операции. Wide — требуют shuffle

Shuffle в RDD

  • Данные перераспределяются между партициями (аналог MR shuffle)
  • Пишутся в shuffle files (на диск), но могут кэшироваться в памяти
  • Граница stage — там, где происходит shuffle

Проблемы shuffle

  • Дорого: запись на диск, передача по сети
  • Может быть узким местом
  • Решение: избегать shuffle, использовать narrow операции

Код: WordCount

val rdd = sc.textFile("hdfs://...")
    .flatMap(_.split(" "))
    .map((_, 1))
    .reduceByKey(_ + _)

// Посмотреть DAG
rdd.toDebugString
// (2) ShuffledRDD[3] at reduceByKey at ...
//  +-(2) MapPartitionsRDD[2] at map at ...
//  |  MapPartitionsRDD[1] at flatMap at ...
//  |  HadoopRDD[0] at textFile at ...

toDebugString показывает lineage. Видно, где shuffle, где narrow операции

Кэширование

  • cache() — ленивая операция. Реально закешируется только после action
  • persist(STORAGE_LEVEL) — выбор уровня: memory, disk, off-heap
  • unpersist() — убрать из кэша

Spark Runtime

Процессы и планирование

03

Иерархия процессов

  • Driver: SparkContext, DAGScheduler, TaskScheduler. Точка входа для spark-shell/notebook
  • Cluster Manager: Standalone / Kubernetes / YARN. Выделяет ресурсы
  • Executors: JVM-процессы на worker-ах. Выполняют задачи, хранят кэш и shuffle-данные

Driver — не только планировщик, но и точка входа для кода пользователя

Cluster Manager

МенеджерСтатусОсобенности
StandaloneАктуальноПростой, встроенный в Spark
KubernetesАктуальноСтандарт де-факто для новых кластеров
YARNLegacyИнтеграция с Hadoop
MesosLegacyУстарел, не рекомендуется

Kubernetes — стандарт для новых проектов. Standalone — для простых случаев

DAGScheduler

  • Разбивает DAG на stages по границам shuffle (wide dependencies)
  • Внутри stage — pipeline narrow transformations
  • Stage = набор идентичных task-ов (по одному на partition)

Пример

Stage 1: textFile -> flatMap -> map (narrow, pipeline)
Stage 2: reduceByKey (shuffle, wide)
Stage 3: saveAsTextFile (narrow)

TaskScheduler

  • Data locality: PROCESS_LOCAL → NODE_LOCAL → RACK_LOCAL → ANY
  • Старается запускать задачу там, где данные (минимизировать сеть)
  • Speculative execution: запуск дубля для медленных task-ов (аналог MR speculative)

Если задача выполняется дольше, чем другие — Spark запускает её копию на другом Executor'е

Memory Management

  • spark.executor.memory — общий heap Executor'а
  • Делится на:
    • Storage memory — RDD cache, broadcast
    • Execution memory — shuffle, join, aggregation
    • User memory — объекты UDF
    • Reserved memory — служебное

Формула: (Executor Memory - Reserved) * spark.memory.fraction = Storage + Execution

UnifiedMemoryManager

  • Динамическое заимствование между Storage и Execution
  • Если Execution не хватает — забирает у Storage (и наоборот)
  • Позволяет эффективно использовать память

Проблема

  • Если Execution забрал память у Storage, RDD может быть вытеснен на диск
  • Решение: правильно настраивать spark.memory.fraction

Shuffle Internals

  • Hash shuffle — удален (с Spark 2.0). Был медленным
  • Sort shuffle — текущий стандарт. Сортировка перед записью
  • Tungsten sort shuffle — off-heap сериализация, bypass merge для small partitions

Не тратьте время на изучение Hash shuffle — его больше нет

Отказоустойчивость

Как Spark переживает сбои

04

Lineage Recomputations

  • При потере partition — перевычисление по DAG
  • Бесплатно: не нужно хранить копии данных
  • Минус: при длинной цепочке — долго

Пример

val rdd = sc.textFile("hdfs://...")
    .flatMap(_.split(" "))
    .map((_, 1))
    .reduceByKey(_ + _)
// Если partition потерян — пересчитаем только его

Checkpoint vs Persist

LineageCheckpoint
СтоимостьБесплатноДорого (пишем на диск)
ГрафПолный lineageОбрезает граф
КогдаВсегдаДлинная цепочка, сложный граф

Checkpoint — материализация в HDFS. Полезен для обрезки длинного lineage

Сбой Executor

  • TaskScheduler пересылает потерянные partitions на другие Executor'ы
  • Данные пересчитываются по lineage (или берутся из кэша)
  • Если есть External shuffle service — shuffle-данные сохраняются

External shuffle service — отдельный процесс на worker-ах. Сохраняет shuffle-данные при падении Executor

Сбой Driver

  • Полный фейл. Spark не умеет восстанавливать Driver (в отличие от Flink)
  • SparkContext потерян, все RDD и кэш — уничтожены
  • В YARN — ApplicationMaster перезапустит контейнер, но состояние не восстановится

Это ключевое отличие от MR: там JobTracker был SPOF, но задачи перезапускались

Итоги

  • Spark — не быстрее MR, а меньше дисковых операций и in-memory pipeline
  • RDD — иммутабельная, ленивая, распределенная коллекция с lineage
  • DAGScheduler разбивает DAG на stages по границам shuffle
  • Отказоустойчивость — через lineage recomputation. Driver — точка отказа
