Технологии хранения и обработки больших данных. Лекция 2

  • Форматы хранения данных в HDFS

Форматы хранения данных в HDFS

  • В первом приближении - никаких специальных форматов нет
  • Храним файл как набор байтов
  • Но нужна какая-то структура для удобства обработки
  • Первое требование к структуре - способность хранить содержимое как набор записей
  • Относительно небольших

Форматы хранения данных в HDFS

  • Нужен формат представления для таблицы в целом
  • И для отдельной записи
  • Это может быть универсальный формат — определяющий оба уровня представления
  • А может быть для отдельных формата
  • Один - позволяющий найти границы между записями как наборами байтов
  • Второй - интерпретирующий наборы байтов

Что нужно от форматов

  • От "глобального" в первую очередь - возможность легко поделить содержимое по границам
  • Чтобы это легко делалось "локально"
  • Без необходимости для этого файл от начала до конца
  • Важно удобство создания файла в контексте HDFS
  • Не хотим в начале файла хранить метаданные, значения которых могут меняться по мере дозаписывания данных"
  • От локального - компактности

Что не подходит для "глобального"

  • Любое "глобальное" архивирование
  • Весь документ как JSON
  • Или как другой иерарихический формат
  • Важный вопрос: легко ли из точки внутри файла найти границу записей ?
  • Если нет - формат не подходит

Что подходит для глобального

  • Текстовый файл с выделенными разделителями строк
  • (Если строка разумной длины)
  • Выделенная константа как размер записи
  • (Если константа разумной величины)
  • Соглашения на уровне байтов
  • Что легко отличать последние или первые байты записи

Что c локальным

  • Зависит от глобального
  • При глобальной разметке на фиксированный размер записи - можно и запись разбить фиксированные поля
  • Но можно хранить произвольный байтовый кусок с паддингом
  • Тогда случай с текстовый разделителем мало отличается от фиксированного размера
  • Смешанный вариант: сначала поля фиксированного размера, потом часть переменной длины

Что c локальным

  • Классика - семейство CSV
  • На уровне записи может пригодиться JSON
  • Запись - JSON-документ
  • Может потребоваться кодирования для разделителей
  • Может пригодиться base32/64

Что c локальным

  • Приоритет - экономия размера
  • В контексте больших данных "микрооптимизации" значимы
  • Даже сокращение общего объема в 2 раза может быть полезным
  • В контексте MapReduce - больше локальных вычислений

protobuf

  • Широко применяется в разных контекстах
  • Уже поэтому заслуживает внимания
  • Как минимум на уровне записи
  • Встает вопрос о границах записей

protobuf: обзор

  • Бинарный формат сериализации данных от Google, схема описывается в .proto-файле
  • Схема описывается в .proto-файле
  • Прямая и обратная совместимость заложена в сам формат: новые поля не ломают старых читателей, и наоборот
  • Сообщение — это последовательность полей вида "тег + значение"

Структура сообщения на уровне байт

[тег][значение][тег][значение]...
  • Сообщение protobuf — это просто конкатенация записей "тег, затем значение", без разделителей и без имён полей
  • Тег кодирует одновременно номер поля (из .proto) и wire type — способ, которым закодировано само значение
  • Порядок полей в байтах не обязан совпадать с порядком в .proto-файле
  • На бинарном уровне нет схемы
  • Соовместимость писателя и читателя - ответственность пользователя

Varint: переменная длина

300 в varint: 10101100 00000010
              ^        ^
              бит      бит
              продолж. продолж.
              =1       =0
  • Целое число кодируется группами по 7 значащих бит на байт
  • Старший бит каждого байта (MSB) — флаг продолжения: 1 значит "далее ещё байт", 0 — "это последний байт"
  • Младшая группа из 7 бит идёт первой (little-endian по группам) — поэтому число 300 требует 2 байта, а не помещается в один (300 > 127)
  • Маленькие числа (0-127) кодируются одним байтом — именно на этом основана компактность protobuf для типичных данных

Тег: номер поля + wire type

tag = (номер_поля << 3) | wire_type
  • Тег — это сам varint, в который упакованы сразу два значения
  • Младшие 3 бита тега — wire type (0-5), всё остальное — номер поля, сдвинутый влево на 3 бита
  • Поэтому номера полей 1-15 умещаются в тег из одного байта (рекомендуется отдавать маленькие номера полей часто используемым полям)
  • Пример: поле №1, wire type 0 (varint) — tag = (1 << 3) | 0 = 8

Все wire types

  • 0 — Varint: int32/int64, uint32/uint64, sint32/sint64, bool, enum
  • 1 — I64 (64-bit): fixed64, sfixed64, double — ровно 8 байт, без varint-сжатия
  • 2 — Len (length-delimited): string, bytes, вложенные сообщения, packed repeated-поля
  • 5 — I32 (32-bit): fixed32, sfixed32, float — ровно 4 байта

Целочисленные типы: int32/uint32/sint32

  • Все три используют wire type 0 (varint) — разница только в том, как именно число превращается в биты перед varint-кодированием
  • uint32/uint64 — прямое кодирование беззнакового значения
  • int32/int64 — отрицательное число сначала расширяется знаком до 64 бит (обычное дополнение до двух), а затем кодируется как varint
  • Следствие: любое отрицательное число, закодированное как int32, всегда занимает 10 байт — все верхние биты 64-битного представления единичные
  • Именно поэтому для полей, где ожидаются отрицательные значения, protobuf рекомендует не int32, а sint32

ZigZag: эффективное кодирование отрицательных чисел

zigzag(n) = (n << 1) ^ (n >> 31)   // для 32-битных значений

0  -> 0
-1 -> 1
1  -> 2
-2 -> 3
  • sint32/sint64 используют ZigZag-преобразование перед обычным varint-кодированием
  • Идея: положительное n превращается в 2n, отрицательное n — в 2|n|-1 — числа чередуются: 0, -1, 1, -2, 2, ...
  • В результате маленькие по модулю отрицательные числа получают такой же компактный varint, как и маленькие положительные — в отличие от обычного int32

fixed32/fixed64: альтернатива varint

  • wire type 5 (fixed32) и wire type 1 (fixed64) — значение записывается ровно 4 или 8 байтами, без варьируемой длины
  • Используются для double/float (там varint неприменим — это не целые числа) и для fixed32/fixed64/sfixed32/sfixed64
  • Имеет смысл для полей, где значения обычно большие: varint для большого числа занял бы 5 байт (32-битный кейс) — столько же или больше, чем фиксированные 4 байта, но без выигрыша
  • Выбор между varint-based (int32) и fixed32 — компромисс, зависящий от типичного диапазона значений конкретного поля

Length-delimited поля (wire type 2)

[тег][varint длина][сырые байты длиной ровно "длина"]
  • Единый механизм для string, bytes, вложенных сообщений — и, отдельно, для packed repeated-полей (следующий слайд)
  • После тега идёт varint с точной длиной данных, а затем сами данные — ровно столько байт, сколько указано
  • Вложенное сообщение кодируется точно так же: как последовательность байт, которая сама по себе является валидным protobuf-сообщением
  • Именно длина-префикс позволяет парсеру пропустить целиком неизвестное/незначимое поле, не разбирая его содержимое

Как представлены массивы (repeated-поля)

// unpacked: тег повторяется для каждого элемента
[тег][val1][тег][val2][тег][val3]

// packed: один тег, суммарная длина, значения подряд без отдельных тегов
[тег][varint длина][val1][val2][val3]
  • Unpacked-представление — каждый элемент массива записывается как отдельное поле с одним и тем же номером, идущее несколько раз подряд (или не подряд)
  • Packed-представление — для скалярных числовых типов (varint/fixed) все элементы упаковываются в одно length-delimited поле (wire type 2), без повторения тега на каждый элемент
  • В proto3 packed-кодирование — поведение по умолчанию для repeated-полей скалярных числовых типов, что даёт заметную экономию на больших массивах
  • string/bytes/вложенные сообщения принципиально нельзя упаковать в packed-виде — они и так уже length-delimited и требуют собственного тега на каждый элемент

Байтовая раскладка типичного сообщения

Protobuf для одной записи в HDFS: преимущества

  • Компактность за счёт varint и packed repeated-полей
  • Эволюция схемы: важно, когда данные в HDFS живут годами, а пишущих и читающих сервисов много и они эволюционируют независимо
  • Быстрый разбор по сравнению с текстовыми форматами (JSON/XML) — при сканировании огромных объёмов в MapReduce/Spark разница в CPU на па рсинг становится ощутимой
  • Межъязыковая генерация кода

Проблема: сообщения сами по себе не ограничены

// без длины — читатель не поймёт, где кончается одна запись и начинается следующая
[байты записи 1][байты записи 2][байты записи 3]...

// с явным префиксом длины — writeDelimitedTo() в Java API
[varint длина][запись 1][varint длина][запись 2]...
  • Формат protobuf сам по себе не самоограничен: если просто склеить много сообщений подряд в один файл, нет способа узнать, где заканчивается одна запись — ровно та же проблема, что решает length-delimited wire type внутри одного сообщения (см. предыдущие слайды), только теперь на уровне всего файла
  • Решение — вручную добавлять префикс длины перед каждой записью (в Java API это writeDelimitedTo()/parseDelimitedFrom())

Проблема: разбиение

  • Не найти начало ближайшей записи, не читая файл с самого начала
  • Даже с префиксами длины поток protobuf-сообщений не даёт такой возможности "с середины" — нет маркеров синхронизации
  • Вариант решения: оборачивать в контейнерный формат
  • Простейший способ - base64 + переводы строк

Avro

  • Разбиваемость — файлы можно делить на части для параллельной обработки.
  • Компактность — сопоставимо с protobuf.
  • Схема в файле — самодостаточность данных.
  • Поддержка MapReduce — нативная интеграция.

Схема (Schema)

  • Схема — это JSON-документ, описывающий структуру данных.
  • Пример схемы: 
    {
  "type": "record",
  "name": "User",
  "fields": [
    {"name": "id", "type": "int"},
    {"name": "name", "type": "string"},
    {"name": "email", "type": ["null", "string"], "default": null}
  ]
}
  • Схема хранится внутри файла

Примитивные типы

  • null — отсутствие значения
  • boolean — true/false
  • int — 32-битное целое
  • long — 64-битное целое
  • float — 32-битное с плавающей точкой
  • double — 64-битное с плавающей точкой
  • bytes — последовательность байтов
  • string — текст (UTF-8)

Представление примитивных типов: Avro

  • Пример: запись User { id: 123, name: "Alice" }
  • Схема известна заранее (хранится в заголовке файла)
  • Данные (только значения): 
    0xF6 0x01  // id = 123 (varint)
0x05       // длина строки = 5
0x41 0x6C 0x69 0x63 0x65
           // "Alice" (UTF-8)
// Итого: 8 байт

Представление примитивных типов: Protobuf

  • Пример: запись User { id: 123, name: "Alice" }
  • Схема в .proto файле, компилируется в классы
  • Данные (тег + значение): 
    0x08 0x7B  // tag=0x08 (field 1,
            // varint) + id=123
0x0A 0x05  // tag=0x0A (field 2,
            // length-delimited)
            // + длина = 5
0x41 0x6C 0x69 0x63 0x65
           // "Alice" (UTF-8)
// Итого: 10 байт

Почему Avro не хранит теги полей?

  • Avro: схема отдельно от данных
  • Схема хранится в заголовке файла или в реестре схем
  • Читатель знает порядок и типы полей заранее
  • В данных — только значения в строгом порядке
  • Нет необходимости в тегах — позиция определяет поле
  • Пример: если схема говорит {"id": int, "name": string}, то читатель знает: первый varint — id, следующая строка — name.

Protobuf: теги обязательны

  • Каждое поле помечается тегом (номер поля + тип)
  • Тег — это 1-2 байта перед каждым значением
  • Обеспечивает гибкость:
    • Пропуск неизвестных полей
    • Изменение порядка полей
    • Добавление новых полей
  • Теги — это цена за самодостаточность сообщения.

Сравнение размеров

  • int = 1: Avro — 1 байт, Protobuf — 2 байта (tag + value), разница -50%
  • string = "A": Avro — 2 байта (len + char), Protobuf — 3 байта (tag + len + char), разница -33%
  • record с 3 полями: Avro — ~10 байт, Protobuf — ~16 байт, разница -37%
  • массив из 100 int: Avro — ~100 байт, Protobuf — ~200 байт, разница -50%
  • Вывод:
    • Avro экономит 20-50% места за счёт отказа от тегов
    • Protobuf платит 1-2 байта за поле ради самодостаточности
    • Для HDFS, где схема уже в файле, подход Avro эффективнее
    • Для сетевых протоколов, где сообщения читаются независимо, Protobuf удобнее

Опциональные поля в Avro

  • Объявление в схеме: 
    {
  "type": "record",
  "name": "User",
  "fields": [
    {"name": "id", "type": "int"},
    {"name": "name", "type": "string"},
    {"name": "email", "type": ["null", "string"], "default": null}
  ]
}
  • Поле email — это union из двух типов: null и string.
  • Порядок важен: ["null", "string"] означает, что null — это индекс 0, string — индекс 1.

Представление опциональных полей

  • email = null: 
    0x00  // индекс union = 0 (null)
// Всего 1 байт
  • email = "a@b.com": 
    0x01       // индекс union = 1 (string)
0x07       // длина строки = 7
0x61 0x40 0x62 0x2E 0x63 0x6F 0x6D
           // "a@b.com"
// Всего 9 байт
  • Ключевое: перед значением union всегда пишется 1 байт — индекс типа в union.

Опциональные поля: Avro vs Protobuf

  • Объявление: Avro — ["null", "string"], Protobuf — optional string email = 3;
  • null представление: Avro — 1 байт (индекс 0), Protobuf — 0 байт (поле отсутствует)
  • значение представление: Avro — 1 байт (индекс) + данные, Protobuf — тег + данные
  • Размер null: Avro — 1 байт, Protobuf — 0 байт
  • Размер значения: Avro — 1 + data, Protobuf — tag + data
  • Особенность Avro: даже null занимает 1 байт (индекс union). Protobuf экономит на отсутствующих полях — они просто не пишутся.
  • Компенсация: для заполненных полей Avro может быть компактнее, так как не хранит теги.

Union — не только для null

  • Union в Avro может содержать любые типы, не только null: 
    // Поле может быть строкой ИЛИ числом
{"name": "value", "type": ["string", "int"]}

// Поле может быть записью ИЛИ массивом
{"name": "data", "type": ["Record", "array"]}

// Несколько опциональных типов
{"name": "result", "type": ["null", "int", "string", "Error"]}

Union — представление и ограничения

  • Индекс типа в union всегда пишется перед значением: 
    // ["null", "int", "string"]
0x00  // null
0x01 0x7B  // int = 123
0x02 0x03 0x66 0x6F 0x6F  // string = "foo"
  • Ограничение: union не может содержать два одинаковых типа (например, ["string", "string"] — ошибка). Также нельзя использовать union внутри union.

Default значения для опциональных полей

    {

  "fields": [
    {"name": "id", "type": "int"},

Default значения: правила и эволюция

  • Правила default:
    • Для union с null, default должен быть null
    • Default используется при чтении старых данных с новой схемой
    • Если поле отсутствует в данных, читатель подставляет default
  • Пример эволюции: 
    // Старая схема (данные без email)
{"id": 1, "name": "Alice"}

// Новая схема (email добавлен)
// Читатель видит: email отсутствует → default = null
// Результат: {"id": 1, "name": "Alice", "email": null}

Record: Protobuf и сравнение

  • Схема (.proto): 
    message User {
  int32 id = 1;
  string name = 2;
}
  • Данные (тег + значение): 
    0x08 0x7B  // tag(1,varint) + 123
0x0A 0x05  // tag(2,length) + len=5
0x41 0x6C 0x69 0x63 0x65
           // "Alice"
  • Каждое поле с тегом
  • Разница: Avro — 8 байт, Protobuf — 10 байт. Avro компактнее на 20%.

Enum: Avro

  • Схема (JSON): 
    {
  "type": "enum",
  "name": "Status",
  "symbols": ["ACTIVE", "INACTIVE", "BANNED"]
}
  • Данные: 
    0x01  // индекс = 1 (INACTIVE)
// Размер: 1 байт
  • Хранится индекс символа

Enum: Protobuf и сравнение

  • Схема (.proto): 
    enum Status {
  ACTIVE = 0;
  INACTIVE = 1;
  BANNED = 2;
}
  • Данные (как int32): 
    0x08 0x01  // tag(1,varint) + 1
// Размер: 2 байта
  • Хранится как число с тегом
  • Разница: Avro — 1 байт, Protobuf — 2 байта. Avro компактнее на 50%.

Array: Avro

  • Схема (JSON): 
    {
  "type": "array",
  "items": "int"
}
  • Данные: [1, 2, 3] 
    0x06       // блок: 3 элемента (count*2)
0x01       // 1
0x02       // 2
0x03       // 3
0x00       // конец массива
// Размер: 5 байт
  • Блоки по N элементов + маркер конца

Array: Protobuf и сравнение

  • Схема (.proto): 
    message List {
  repeated int32 items = 1;
}
  • Данные: [1, 2, 3] 
    0x08 0x01  // tag(1,varint) + 1
0x08 0x02  // tag(1,varint) + 2
0x08 0x03  // tag(1,varint) + 3
// Размер: 6 байт
  • Каждый элемент с тегом
  • Разница: Avro — 5 байт, Protobuf — 6 байт. Для больших массивов разница растёт.

Map: схема

  • Схема (JSON): 
    {
  "type": "map",
  "values": "int"
}
  • Ключ всегда строка, пары в блоках

Map: данные

  • Данные: {"a": 1, "b": 2} 
    0x04       // блок: 2 пары (count*2)
0x01       // len("a") = 1
0x61       // "a"
0x01       // value = 1
0x01       // len("b") = 1
0x62       // "b"
0x02       // value = 2
0x00       // конец map
// Размер: 8 байт

Union: схема и null

  • Схема (JSON): 
    {
  "type": ["null", "int", "string"]
}
  • null: 
    0x00              // 1 байт
  • Индекс типа + значение

Union: int и string

  • int = 123: 
    0x01 0x7B         // 2 байта
  • string = "foo": 
    0x02 0x03 0x66 0x6F 0x6F
// 5 байт

Union: Protobuf и сравнение

  • Схема (.proto): 
    message Value {
  oneof value {
    int32 int_val = 1;
    string str_val = 2;
  }
}
  • null: (пусто, поле отсутствует) — 0 байт
  • int = 123: 
    0x08 0x7B         // 2 байта
  • string = "foo": 
    0x12 0x03 0x66 0x6F 0x6F
// 5 байт
  • oneof — только одно поле активно
  • Особенность: Avro всегда хранит индекс (1 байт), даже для null. Protobuf экономит на null (0 байт).

Union: Protobuf схема и null

  • Схема (.proto): 
    message Value {
  oneof value {
    int32 int_val = 1;
    string str_val = 2;
  }
}
  • null: (пусто, поле отсутствует) — 0 байт
  • oneof — только одно поле активно

Union: Protobuf int, string и сравнение

  • int = 123: 
    0x08 0x7B         // 2 байта
  • string = "foo": 
    0x12 0x03 0x66 0x6F 0x6F
// 5 байт
  • Особенность: Avro всегда хранит индекс (1 байт), даже для null. Protobuf экономит на null (0 байт).

Fixed: Avro

  • Fixed (фиксированный размер): 
    {
  "type": "fixed",
  "name": "UUID",
  "size": 16
}
// Данные: 16 байт (без длины)
  • Fixed — без длины

Bytes: Avro

  • Bytes (переменный размер): 
    {
  "type": "bytes"
}
// Данные: длина + байты
0x05 0x48 0x65 0x6C 0x6C 0x6F
// len=5 + "Hello"
  • Bytes — с длиной

Fixed и Bytes: Protobuf

  • Нет прямого аналога Fixed. Используется bytes с проверкой размера
  • Bytes (переменный размер): 
    message Data {
  bytes payload = 1;
}
// Данные: тег + длина + байты
0x0A 0x05 0x48 0x65 0x6C 0x6C 0x6F
// tag + len=5 + "Hello"
  • Только bytes, нет fixed

Fixed и Bytes: сравнение

  • Разница: Avro имеет отдельный тип fixed для фиксированных размеров.
  • Protobuf использует bytes для обоих случаев.

Сводная таблица: record, enum, array

  • record: Avro — поля по порядку без тегов, Protobuf — каждое поле с тегом, размер -20%
  • enum: Avro — индекс (1 байт), Protobuf — число с тегом (2 байта), размер -50%
  • array: Avro — блоки + маркер конца, Protobuf — repeated с тегами, размер -20-50%

Сводная таблица: map, union, fixed, bytes

  • map: Avro — блоки пар ключ-значение, Protobuf — repeated message, размер -40%
  • union: Avro — индекс + значение, Protobuf — oneof (без индекса), размер зависит от случая
  • fixed: Avro — есть без длины, Protobuf — нет только bytes, Avro компактнее
  • bytes: Avro — длина + данные, Protobuf — тег + длина + данные, -1 байт на поле

Сводная таблица: итог

  • Итог: Avro в среднем на 20-50% компактнее Protobuf для сложных типов, так как не хранит теги полей.
  • Protobuf выигрывает только в случае union с null (0 байт против 1 байта).

Разбиваемость (Splittability)

  • Что это: способность формата быть разделённым на части для параллельной обработки без потери целостности данных.
  • В HDFS файлы хранятся как блоки (обычно 128 МБ). MapReduce обрабатывает каждый блок независимо на разных узлах кластера.
  • Почему это важно:
    • Большой файл (1 ГБ) разбивается на 8 блоков по 128 МБ
    • Каждый блок обрабатывается отдельным маппером
    • Без разбиваемости — весь файл обрабатывается одним маппером (медленно)

Структура файла Avro

  • Заголовок (Header):
    • Схема (JSON)
    • Метаданные
    • Синхромаркер (16 байт)
  • Блок данных 1:
    • count (varint)
    • Записи (binary)
    • Синхромаркер (16 байт)
  • Блок данных 2:
    • count (varint)
    • Записи (binary)
    • Синхромаркер (16 байт)

Ключевые элементы для разбиваемости

  • Синхромаркер — уникальная 16-байтовая последовательность в конце каждого блока
  • count — количество записей в блоке (varint)
  • Самодостаточность блоков — каждый блок можно читать независимо

Исходный файл (300 МБ)

  • Header (схема, 5 КБ)
  • Block 1 (100 МБ) с sync marker
  • Block 2 (100 МБ) с sync marker
  • Block 3 (100 МБ) с sync marker

Разбиение на блоки HDFS (128 МБ)

  • HDFS Block 1 (128 МБ): Header + Block 1 (начало) + sync marker
  • HDFS Block 2 (128 МБ): Block 1 (продолжение) + Block 2 (начало) + sync marker
  • HDFS Block 3 (44 МБ): Block 2 (продолжение) + Block 3 (начало) + sync marker

Как это работает

  • Каждый HDFS-блок содержит целые блоки Avro (или их части)
  • Маппер ищет синхромаркер в начале блока
  • Находит count — сколько записей в блоке
  • Читает записи до следующего синхромаркера
  • Если блок начинается с середины Avro-блока, маппер пропускает до синхромаркера

Формат Protobuf: описание

  • Каждое сообщение — это просто последовательность полей
  • Нет заголовка, нет блоков, нет синхромаркеров
  • Файл с Protobuf-сообщениями — это просто конкатенация сообщений без разделителей.

Формат Protobuf: пример

  • Пример: 
    message User {
  int32 id = 1;
  string name = 2;
}

// Сообщение 1:
0x08 0x7B 0x0A 0x05 0x41 0x6C 0x69 0x63 0x65
// Сообщение 2:
0x08 0x01 0x0A 0x03 0x42 0x6F 0x62
// Сообщение 3:
0x08 0x02 0x0A 0x05 0x43 0x68 0x61 0x72 0x6C 0x69 0x65

Проблемы при разбиении

  • Нет границ — невозможно определить, где заканчивается одно сообщение и начинается другое
  • Нет заголовка — схема не хранится в файле, нужна внешняя схема
  • Нет синхромаркеров — нельзя найти начало блока
  • Переменная длина — varint и length-delimited поля имеют разную длину

Файл и разбиение на блоки HDFS

  • Файл: users.pb (300 МБ) — сообщения идут подряд без разделителей
  • Разбиение на блоки HDFS (128 МБ):
    • HDFS Block 1 (128 МБ): [msg1][msg2]...[msgK]
    • HDFS Block 2 (128 МБ): [msgK+1]...[msgL]
    • HDFS Block 3 (44 МБ): [msgL+1]...[msgN]

Проблема

  • Маппер для Block 2 начинает читать с середины сообщения msgK+1
  • Он не знает, где начинается msgK+1 — нет маркеров границ
  • Он может прочитать мусорные данные как начало сообщения
  • Результат: ошибка десериализации или потеря данных

Как решают проблему: Вариант 1

  • Добавить длину перед каждым сообщением: 
    [длина][msg1][длина][msg2][длина][msg3]...
  • Но это уже не стандартный Protobuf, а кастомный формат поверх него

Как решают проблему: Вариант 2

  • Каждый файл содержит одно Protobuf-сообщение
  • Тогда файл можно разбить (если внутри есть структура)
  • Но это неэффективно для HDFS: слишком много маленьких файлов

Как решают проблему: Вариант 3 и вывод

  • Использовать SequenceFile:
    • Hadoop SequenceFile — обёртка
    • Хранит ключ-значение пары
    • Protobuf-сообщения как значения
    • SequenceFile поддерживает разбиение, но добавляет накладные расходы
  • Вывод: Protobuf не поддерживает разбиваемость "из коробки". Требуются дополнительные механизмы (длина, обёртки), которые добавляют сложность и накладные расходы.

Сравнение: Разбиваемость Avro vs Protobuf

  • Синхромаркеры: Avro — есть (16 байт в конце блока), Protobuf — нет
  • Границы сообщений: Avro — count + sync marker, Protobuf — нет разделителей
  • Схема в файле: Avro — в заголовке, Protobuf — внешняя (.proto)

Сравнение: итог

  • Чтение с середины: Avro — можно (найти sync marker), Protobuf — нельзя (нет маркеров)
  • Параллельная обработка: Avro — нативная, Protobuf — требует доп. механизмов
  • Интеграция с MapReduce: Avro — AvroInputFormat, Protobuf — нет стандартного
  • Итог: Avro спроектирован для HDFS и поддерживает разбиваемость "из коробки". Protobuf требует дополнительных механизмов, что делает его менее подходящим для хранения больших файлов в HDFS.
