Обычный MergeTree при слиянии сохраняет строки, включая повторы.

Один INSERT может обрабатываться несколькими блоками и создавать несколько партов.

Блок — порция данных в памяти: именованные столбцы с типами и одинаковым числом строк. Одна команда INSERT может разбиваться на несколько блоков. Блоки также передаются между операторами при чтении. Поэтому блок не является синонимом команды INSERT или файла на диске.

Парт, или data part, — набор файлов, хранящий порцию строк одной партиции. В рассматриваемых MergeTree-таблицах строки внутри парта упорядочены по ORDER BY; вместе с данными хранятся индекс и отметки чтения. Активный парт участвует в чтении. После замены слиянием или мутацией прежний парт становится неактивным и может оставаться на диске до очистки.

Слияние создаёт новый парт из нескольких партов одной партиции и заменяет ими исходные активные парты. Движок таблицы задаётся ENGINE и определяет поддерживаемые операции и правила обработки данных. Семейство MergeTree использует общий механизм партов, но разные правила обработки совпадающих ключей.

Обычный MergeTree при обычном слиянии сохраняет все строки, в том числе полностью одинаковые. Это правило не запрещает отдельно заданные UPDATE, DELETE или TTL. Партиция ограничивает набор сливаемых партов; конкретный движок определяет, что происходит со строками внутри этого набора. Блок, парт и партиция — три разные единицы, и соответствия один к одному между ними нет.

Партиция: строки с одним значением ключа

Пусть p(r) — значение выражения PARTITION BY для строки r.

Строки r₁ и r₂ принадлежат одной партиции ⇔ p(r₁) = p(r₂).

Каждый парт содержит строки только одной партиции. В одной партиции может быть несколько партов.

Без PARTITION BY все строки относятся к общей партиции.

Ключ партиционирования — выражение p(r), вычисляемое для каждой вставляемой строки. Партиция с ключом k объединяет строки, для которых p(r)=k, и все парты, содержащие эти строки. Равенство результата выражения, включая все компоненты кортежа, определяет принадлежность одной партиции.

Например, при PARTITION BY toYYYYMM(paid_at) все строки ноября 2026 года имеют ключ 202611. Они могут находиться в разных партах. Один парт не содержит одновременно октябрьскую и ноябрьскую партиции. Без PARTITION BY существует одна общая партиция, но число её партов зависит от вставок и слияний.

Партиция является границей слияний и операций над группой данных. Она не задаёт порядок строк внутри парта и не выбирает сервер: здесь рассматриваем один узел.

Зачем выделять группу партов

Храним историю событий. Запросы читают магазин за час, а политика хранения удаляет целый старый месяц.

Для чтения нужны соседние строки магазина. Для удаления — целая группа данных месяца. Эти задачи требуют разных ключей.

Условия чтения и операции над историей не обязательно выделяют одни и те же данные. Для магазина за час выгодна сортировка по магазину и времени. Для удаления октября нужно собрать октябрьские данные независимо от магазина.

Партиционирование вводит вторую границу, внутри которой находятся парты. Поэтому не заменяем ключ сортировки ключом месяца: каждый обслуживает свою задачу.

Равные ключи допускаются. ORDER BY таблицы не задаёт порядок результата SELECT.

Ключ сортировки ORDER BY — упорядоченный набор выражений K(r). Строки внутри каждого парта размещаются лексикографически по K: сначала сравнивается первая компонента, при равенстве — вторая и так далее. Например, ORDER BY (shop_id, paid_at, event_id) располагает рядом строки магазина, затем упорядочивает их по времени и идентификатору события.

Первичный ключ PRIMARY KEY задаёт значения для разреженного индекса. Он должен быть префиксом ключа сортировки; без отдельного объявления совпадает с ORDER BY. Индекс хранит значения ключа у границ гранул, а не отдельную запись для каждой строки. Он помогает исключать диапазоны чтения и не обеспечивает уникальность.

Ключ партиции p(r) определяет группу партов, а не позицию строки внутри парта. У разных партов одной партиции независимая сортировка и индексы. Поэтому даже совпадение ORDER BY таблицы с нужным порядком не является обещанием порядка результата SELECT: для такого контракта задают ORDER BY в самом запросе.

Хеш и соль: сначала определим выражения

Хеш-функция детерминированно отображает аргументы в число фиксированного размера. sipHash64 возвращает UInt64.

bucket(r) = sipHash64(id) % N
0 ≤ bucket(r) < N, N > 0

Соль — дополнительный признак s(r), разделяющий строки одного ключа на подгруппы: (company_id, s(r)).

Одинаковые аргументы тех же типов дают одинаковый хеш. Разные аргументы могут дать одну корзину.

Хеш-функция детерминированно отображает набор аргументов в значение фиксированного размера. sipHash64 возвращает UInt64, то есть беззнаковое 64-битное число. Для одинаковых значений одинаковых типов результат одинаков; приведение типов констант в сравнении с хешем столбцов является частью корректного выражения.

Хеш-корзина задаётся bucket(r)=sipHash64(id)%N при N>0. Возможных номеров не больше N: от 0 до N−1. Разные идентификаторы могут попадать в одну корзину. Само ограничение числа корзин не гарантирует равного числа строк или байтов.

Солью в этой лекции называем дополнительный признак s(r), разделяющий строки одного исходного ключа. Например, s(r)=sipHash64(event_id)%4, а полный ключ партиции — (company_id,s(r)). Хеш компании не является солью, делящей эту компанию: все её строки имеют один и тот же аргумент company_id.

Для независимых событий признак можно вычислить по event_id. Для версий одной сущности он должен сохраняться между версиями; иначе они разойдутся по партициям. Хеш пары (company_id,event_id) задаёт общее пространство корзин, а кортеж (company_id,hash(event_id)%4) оставляет компанию отдельной компонентой ключа.

Граница партиции ограничивает фоновые слияния всех рассмотренных MergeTree-движков.

ClickHouse сливает парты только с одинаковым значением ключа партиции. При слиянии создаётся новый отсортированный парт этой же группы. Объединение разных групп изменило бы заданное размещение строк.

Это даёт независимые операции над группами, но ограничивает укрупнение мелких партов. Если вставка затрагивает много партиций, в каждой могут появляться небольшие парты, которые нельзя собрать одним общим слиянием.

Гранула, индекс и отсечение чтения

Гранула — последовательный диапазон строк парта, к границам которого привязаны отметки чтения. Размер может быть адаптивным.

Разреженный индекс хранит значения PRIMARY KEY у границ гранул. Он отбирает диапазоны; оставшиеся строки проверяет WHERE.

Этап EXPLAINЧто проверяет
MinMaxМинимумы и максимумы полей партиционирования в парте
PartitionЗначение выражения ключа партиции
PrimaryKeyДиапазоны гранул по первичному ключу

Гранула — последовательный диапазон строк внутри парта. Отметка чтения — метаданные позиции в потоках столбцов, позволяющие перейти к началу чтения соответствующей гранулы. Такие отметки привязаны к границам гранул. Гранула не равна блоку исполнения или партиции. Число строк может зависеть от настроек адаптивной гранулярности; в опыте с логами задаём index_granularity=1024 и index_granularity_bytes=0.

Разреженный первичный индекс содержит значения PRIMARY KEY у границ гранул. По условию запроса он определяет диапазоны, которые могут содержать подходящие строки. Отсечение означает исключение диапазона, заведомо не содержащего нужных строк. В оставшихся диапазонах условие WHERE всё ещё проверяется; индекс не возвращает точный список идентификаторов подходящих строк.

На этапе MinMax проверяются минимумы и максимумы полей, участвующих в выражении партиционирования, сохранённые для каждого парта. Это автоматические метаданные партиционирования в нашем примере, а не объявленный отдельно пропускающий индекс INDEX TYPE minmax. Этап Partition проверяет выражение ключа партиции. Затем PrimaryKey отбирает гранулы в оставшихся партах.

Parts: a/b и Granules: c/d показывают число оставленных и рассмотренных партов или гранул на данном этапе. Это счётчики плана, а не число строк результата и не время выполнения. Названия этапов и конкретные счётчики проверяем в EXPLAIN indexes=1.

План запроса — описание операторов, выбранных для его выполнения, и связей между ними. EXPLAIN indexes=1 дополняет его условиями и счётчиками отбора по индексам. Pipeline уточняет физическое исполнение: экземпляры операторов и потоки блоков между ними; его рассмотрим в разделе агрегации.

Сравним два варианта для одной истории: партиции по месяцу и по дню. Предположим, что загружаем ноябрь небольшими блоками и в каждом блоке перемешаны строки за все 30 дней.

При месячном разбиении строки блока относятся к одной партиции. При дневном блок разделяется между 30 партициями, создавая мелкие парты в каждой. Повторение таких вставок увеличивает число партов; слияния могут укрупнять их только внутри каждого дня.

Соль по событию делит компанию, одновременно дробя и мелкие компании. Хеш пары ограничивает общее число групп, но без события компания не определяет корзину. Это разные компромиссы, а не последовательные улучшения одного решения.

Кардинальность ключа — число различных результатов его выражения на рассматриваемом наборе строк. В таблице C означает число компаний. Перекос размеров — неравномерность числа строк или байтов между группами; высокая кардинальность и перекос являются разными свойствами. В нашем сравнении считаем строки, а не байты.

Соль только для крупных компаний

Крупные компании можно разделять на подгруппы, мелким оставлять по одной. Для этого нужен заранее определённый список крупных компаний.

В ClickHouse 24.12 выражение PARTITION BY существующей таблицы так не меняется. Новое правило потребует новой таблицы и переноса данных.

Условие if(company_id IN (...),hash(event_id)%4,0) делит выбранные компании на четыре подгруппы, а остальные оставляет в подгруппе 0. Список крупных компаний нужно определить по данным и зафиксировать в схеме.

В ClickHouse 24.12 нет команды ALTER, которая произвольно заменяет PARTITION BY существующей MergeTree. Для нового выражения создают таблицу с другим ключом и переносят строки через INSERT SELECT, согласуя переключение загрузки.

Если же salt приходит отдельным полем от приложения, смена этого значения затронет новые вставки, а прежние строки останутся в старых группах. Для версий такое расхождение может нарушить фоновое замещение. Поэтому это не автоматическая адаптация к росту компании.

Как выбрать ключ до измерения запросов

  1. Определить, какие данные удаляются целиком и какие должны оставаться вместе.
  2. Оценить число групп, размеры и распределение вставок между ними.
  3. Проверить, какие условия WHERE определяют группу.
  4. Сравнить парты и гранулы с вариантом без разбиения.

Если основная операция — удаление старых периодов, начинаем с временной границы. Для нетемпоральной таблицы отсутствие PARTITION BY является допустимым исходным вариантом.

Хеш и соль выбираем по измеренному распределению данных и запросов. Проверяем число групп и цену вставки, а не только размер крупнейшей партиции. Сортировку и первичный ключ задаём по запросам внутри выбранных групп.

Проверяем отсечение месяца

MinMax проверяет сохранённые минимум и максимум paid_at в каждом парте. Октябрьский диапазон не пересекается с ноябрём — парт исключается без чтения строк.

Для ключа партиционирования toYYYYMM(paid_at) ClickHouse автоматически хранит в каждом парте минимальное и максимальное значения paid_at. В EXPLAIN проверка этих границ называется MinMax.

Сообщения: хеш рабочего пространства и год

Сервис хранит переписку компаний с клиентами: workspace_id — компания, conversation_id — диалог.

Хеш распределяет компании по 16 группам. Год задаёт временную границу; ORDER BY собирает сообщения диалога рядом.

CREATE TABLE workspace_messages
( workspace_id UInt64, conversation_id UInt64,
  created_at DateTime('UTC'), message_id UInt64 )
ENGINE=MergeTree
PARTITION BY (sipHash64(workspace_id) % 16,
              toYear(created_at))
ORDER BY (workspace_id, conversation_id, created_at);
INSERT INTO workspace_messages VALUES
 (1,10,'2025-12-31 12:00:00',101),
 (1,10,'2026-01-01 12:00:00',102),
 (2,20,'2026-01-01 12:00:00',103),
 (12,30,'2026-01-01 12:00:00',104);

В общей таблице хранится переписка нескольких компаний. workspace_id обозначает компанию, conversation_id — диалог, created_at — время сообщения. Основной запрос выбирает диалог одной компании за интервал.

PARTITION BY состоит из хеш-группы компании и года. Если сохраняются Y лет, возможно не более 16 × Y партиций независимо от числа компаний. Отдельная партиция для каждой компании такого ограничения не дала бы.

ORDER BY (workspace_id, conversation_id, created_at) собирает сообщения диалога рядом внутри каждого парта. Партиция ограничивает набор партов, а первичный индекс отбирает диапазоны внутри них. Число 16 — параметр примера, а не универсальная настройка.

Разные компании могут разделять одну хеш-партицию

Условие по workspace_id и году определяет хеш-партицию. Но удалить одно рабочее пространство через DROP PARTITION нельзя: в группе могут быть и другие.

SELECT workspace_id, sipHash64(workspace_id)%16 AS bucket,
 toYear(created_at) AS year, count()
FROM workspace_messages
GROUP BY workspace_id, bucket, year
ORDER BY workspace_id, year;
EXPLAIN indexes=1
SELECT message_id FROM workspace_messages
WHERE workspace_id=1
 AND created_at >= '2026-01-01 00:00:00'
 AND created_at < '2027-01-01 00:00:00';

Компания 1 имеет сообщения двух лет: хеш-группа у них одинакова, годовые партиции различаются. Компания 12 также попадает в группу 14. В 2026 году её строка разделяет партицию со строкой компании 1.

WHERE workspace_id=1 и ограничение года выбирают нужные парты, а первичный индекс различает компании внутри общей хеш-группы. DROP PARTITION для этой группы года удалил бы обе компании. Такая граница не позволяет удалить одну компанию целиком.

Версия — состояние платежа после изменения

У платежа A исправили сумму со 100 до 150 рублей. Это два состояния одного платежа, а не две оплаты.

payment_idamount, руб.version
A1001
A1502

Версия — состояние сущности с номером изменения. Актуальный вклад платежа A в отчёт — 150 рублей.

Сущность — объект с устойчивым ключом идентичности, в примере payment_id. Состояние — значения её атрибутов, например сумма платежа. Версия — запись состояния с меткой порядка изменений. В нашем протоколе version растёт для каждого платежа, а текущее состояние выбирается по максимальной версии среди доступных строк этого платежа.

У A первоначально amount=100 и version=1. Исправление даёт amount=150 и version=2. Обе строки описывают один платёж. Они не являются двумя независимыми оплатами: актуальный вклад A равен 150, а не 250.

Неизменяемое событие описывает отдельную операцию с собственным event_id. Для журнала оплата и возврат — разные операции; для таблицы состояний исправление суммы — новая версия того же payment_id. Смысл строки задаёт источник, движок его не распознаёт автоматически.

«Актуальное» здесь означает максимальную известную версию в выбранной области данных. Запрос не доказывает, что источник уже доставил все изменения реального мира. Далее разберём повторную доставку, выбор версии, ключи и границы партиций.

ALTER UPDATE в 24.12 по умолчанию асинхронен. Обработка партов не является атомарной заменой всей таблицы; ключевые поля изменять нельзя.

ReplacingMergeTree — движок, который замещает строки с одинаковым полным ORDER BY одной выбранной строкой; при заданном version выбирается максимальная версия. Подробное правило разбирается на слайде 41.

Отсутствие истории — только одно отличие. В ClickHouse 24.12 ALTER UPDATE выполняется мутацией: условие выбирает строки, но результат записывается новыми версиями затронутых партов. При Wide неизменённые файлы столбцов можно переиспользовать; затраты определяются затронутыми данными, а не только количеством исправленных строк.

По умолчанию команда асинхронна. До завершения разные парты могут находиться на разных этапах изменения; атомарной замены всей таблицы нет. В нашей схеме нельзя обновлять поля первичного ключа и выражения партиционирования. История прежних значений для запросов сама не появляется.

Поэтому для редкой коррекции атрибута рассматриваем ALTER UPDATE, а для потока состояний — вставки версий. ReplacingMergeTree тоже требует работы: записи новых партов, фонового замещения и выбора версии при чтении. Для архива приложение само записывает каждое изменение новой строкой в отдельный журнал MergeTree и сохраняет прежние строки. Движок автоматически такой журнал не создаёт. Частоту, объём изменений и требования к видимости учитываем вместе с потребностью в истории.

ReplacingMergeTree: правило замещения строк

ReplacingMergeTree(version) оставляет одну строку среди строк с одинаковым полным ORDER BY.

Часть правилаСемантика
ИдентичностьСовпадают все значения ORDER BY; PRIMARY KEY может быть короче
Выбор строкиМаксимальный version; сохраняется вся строка победителя
Без version / при равенствеПоследняя строка из самого нового участвующего парта
Фоновое слияниеПравило применяется к участвующим партам одной партиции
SELECT FINALТо же правило при чтении, без переписывания хранения

INSERT допускает несколько версий. Слияние может удалить прежние состояния.

ReplacingMergeTree заменяет несколько строк с одинаковым ключом одной выбранной строкой. Идентичность определяется полным ORDER BY. В нашей схеме ORDER BY (shop_id, payment_id): строки одного платежа в одном магазине считаются версиями одного объекта. Короткий PRIMARY KEY влияет на индекс, но не меняет это правило.

В ReplacingMergeTree(version) побеждает строка с максимальным значением version среди обрабатываемых строк этого ключа. Сохраняется вся строка победителя: значения столбцов не складываются и не выбираются независимо друг от друга. Если новая версия содержит пустое имя или нулевую сумму, эти значения также сохраняются; движок не восстанавливает их из старой версии.

Параметр version необязателен. У ReplacingMergeTree() остаётся последняя строка в порядке замещения: при последовательных вставках это последняя строка из наиболее нового участвующего парта. Значения времени внутри строки сами по себе не определяют победителя. При равных максимальных version применяется то же правило. Поэтому для потока с доставкой не по порядку задаём версию источника, а одинаковый ключ и одинаковая версия в нашем протоколе должны означать одинаковое содержимое. У argMax при равных версиях собственное правило выбора; согласованность с FINAL при конфликтующих строках не предполагаем.

INSERT записывает новые строки и не ищет прежнюю строку с таким ключом для немедленной замены. Фоновое слияние применяет правило только к строкам участвующих партов внутри одной партиции. Другие парты могут ещё содержать версии того же объекта. Срок полного устранения повторов не гарантируется.

SELECT FINAL выполняет замещение при чтении и не переписывает сохранённые строки. Для версий в разных партициях действует разобранная настройка do_not_merge_across_partitions_select_final; наша схема сохраняет версии в одной партиции. Обычный SELECT читает сохранённые строки и потому может видеть несколько версий.

После физического замещения проигравшие версии могут быть удалены из активных данных. ReplacingMergeTree подходит для хранения текущего состояния с отложенным замещением. Если нужны запросы к прошлым состояниям, историю сохраняют отдельно. Вариант ReplacingMergeTree(version, is_deleted) добавляет версию удаления; его разберём в разделе об удалении.

FINAL — модификатор чтения MergeTree-таблицы, применяющий правило её движка при выполнении SELECT. Для ReplacingMergeTree(version) это выбор строки с максимальной версией среди обрабатываемых строк одного полного ORDER BY. Чтение FINAL не меняет физические парты. Обработка разных партиций зависит от do_not_merge_across_partitions_select_final.

argMax(a,v) — агрегатная функция: для каждой группы она возвращает значение a из строки с максимальным v. При нескольких максимумах выбор a не определён однозначно. В примерах группируем по полному ключу сущности, а tuple(amount,created_at) сохраняет связанные атрибуты одного выбранного состояния.

Для Nullable-аргументов скалярный argMax пропускает строки с NULL в a или v. Кортеж с NULL внутри сам не является NULL, поэтому argMax(tuple(a),v) позволяет сохранить NULL в атрибуте выбранного состояния. Если нужен однозначный выбор при совпадающих версиях, дополнительный порядок должен быть частью протокола и аргумента сравнения.

OPTIMIZE TABLE t FINAL — команда принудительного слияния партов по правилам движка в пределах партиций. Она меняет хранение и отличается от модификатора SELECT FINAL. Новые вставки после слияния снова могут добавить версии. Для отчёта выбираем корректное правило чтения, а не запускаем OPTIMIZE перед каждым запросом.

Что означает запрос к прошлому состоянию

История состояний — сохранённые версии, достаточные для восстановления состояния на выбранную границу.

Исторический срез на b: для каждого ключа выбираем последнюю версию среди записей с batch ≤ b.

Опубликованный batch — полностью загруженный набор изменений с общей для всех сущностей меткой порядка.

Версия 2 объекта A и версия 2 объекта B общей границы не задают.

История состояний — набор сохранённых версий, позволяющий восстановить прежние состояния объектов. Исторический срез на общую границу b выбирает для каждого ключа запись с максимальной меткой не больше b. Если до границы объект ещё не создан, его в срезе нет. Для удалений потребовалось бы также учитывать последнюю версию удаления; в этом примере удалений нет.

В примере batch — общая для всех платежей метка загрузки. Опубликованный batch означает, что загрузчик полностью записал соответствующий набор изменений и больше не добавит в него запоздалые строки. При одинаковых ключе и batch должно быть одно определённое состояние. Сначала фильтруем batch<=b, затем выбираем argMax по каждой сущности.

Независимые версии сущностей общей границы не задают. Полнота batch — прикладной контракт источника и загрузчика. Это не автоматически возникший транзакционный снимок ClickHouse.

История существует потому, что приложение явно вставляет изменения отдельными строками и сохраняет их. Обычный MergeTree не предоставляет автоматического SQL-журнала прежних значений UPDATE/DELETE, а ReplacingMergeTree может удалить прежние версии при слиянии.

Прошлые состояния требуют сохранённой истории

batch — общий номер завершённой загрузки. batch=1: два платежа; batch=2: исправление A; batch=3: исправление B.

Историю ведём добавлением строк в MergeTree. Прежние состояния не обновляем и не удаляем. ReplacingMergeTree мог бы убрать их при слиянии.

CREATE TABLE payment_history
(payment_id String, batch UInt64, amount Decimal(18, 2))
ENGINE=MergeTree ORDER BY (payment_id,batch);
INSERT INTO payment_history VALUES
 ('A',1,100),('B',1,200),
 ('A',2,150),
 ('B',3,250);

Здесь хотим получить состояние платежей после каждой загрузки. batch задаёт одну общую шкалу для всех платежей. В загрузке 1 созданы A на 100 и B на 200; загрузка 2 исправляет A на 150; загрузка 3 — B на 250.

Каждое изменение приложение вставляет отдельной строкой в обычный MergeTree. UPDATE и DELETE к этой истории не применяем; TTL и удаление партиций, стирающие нужные состояния, не задаём. Обычные слияния эти строки не замещают. Номер batch назначает загрузчик. Прежде чем объявить границу доступной, он должен полностью загрузить её данные; после публикации границы добавлять в неё запоздалые изменения нельзя.

Одинаковый payment_id в одном batch должен иметь одно определённое состояние. Обычные независимые номера версий A и B не задают такой общей границы: версия 2 у одного платежа может относиться к другому моменту, чем версия 2 у другого.

Срез на batch=2: выбираем состояние до границы

Сначала WHERE batch ≤ 2, затем последнее состояние каждого платежа. A=150, B=200: сумма 350.

SELECT payment_id, argMax(amount,batch) AS amount
FROM payment_history WHERE batch<=2
GROUP BY payment_id ORDER BY payment_id;
SELECT sum(amount) AS total FROM
( SELECT payment_id, argMax(amount,batch) AS amount
  FROM payment_history WHERE batch<=2
  GROUP BY payment_id );

Проверенный результат · ClickHouse 24.12.3.47

A    150
B    200
350

Сначала исключаем изменения после batch=2. Затем argMax выбирает последнее состояние каждого платежа внутри оставшейся истории. Для A это загрузка 2, для B — загрузка 1: исправление B из загрузки 3 ещё не входит в срез. Итоговая сумма равна 350.

Если сначала выбрать самые новые состояния всей таблицы, а затем пытаться отсечь будущие, нужные старые значения уже будут потеряны. Граница должна применяться до выбора состояния.

Такой запрос даёт прикладной срез истории на опубликованную границу. Он не создаёт автоматически согласованный снимок нескольких таблиц. Для этого источник и загрузчик должны обеспечить общую завершённую границу. Для состояния с удалениями в историю также нужно сохранять флаг удаления и учитывать его после выбора последней версии.

Мутация создаёт новые версии затронутых партов

Мутация — фоновое преобразование уже записанных данных с заменой затронутых активных партов новыми.

ALTER UPDATE вычисляет новые значения выбранных строк; ALTER DELETE исключает выбранные строки.

Формат партаОрганизация данных и следствие
WideСтолбцы в отдельных файлах; неизменённые файлы можно переиспользовать
CompactСтолбцы в общем файле; изменение может потребовать его переписывания

Парт заменяется отдельно; вся таблица не переключается атомарно.

Мутация — фоновое преобразование уже записанных данных таблицы. Для затронутых партов создаются новые версии с изменёнными данными, после чего новые парты заменяют старые в активном наборе. В ALTER UPDATE условие WHERE выбирает строки, а выражения SET задают новые значения столбцов. В ALTER DELETE выбранные строки не входят в новое содержимое парта.

Замена активного парта не означает атомарного изменения всей таблицы: разные парты одной мутации могут обрабатываться в разное время. Успешный возврат асинхронного ALTER означает принятие операции; завершение контролируется отдельно.

Wide и Compact — форматы хранения парта. В Wide данные разных столбцов находятся в отдельных файлах; неизменённые файлы при мутации могут переиспользоваться через жёсткие ссылки. В Compact данные столбцов собраны в общем файле, и изменение может требовать его переписывания. В Docker-опыте различие подтверждается inode файлов до и после UPDATE.

Формат и объём затронутых данных определяют работу по переработке. Одной подходящей строке может соответствовать переписывание большого файла. В нашей схеме UPDATE не может менять поля первичного ключа и выражения партиционирования; соответствующие команды отдельно проверяются как ожидаемые ошибки.

mutations_sync=0: команда принята → фоновая обработка
mutations_sync=1: ответ после завершения на этом сервере

парт A: старый → новый
парт B: старый → новый

До завершения разные парты могут находиться на разных этапах изменения.

Асинхронная операция возвращает управление после принятия задания, до обязательного завершения обработки. Синхронное ожидание задерживает ответ до выполнения заданного условия завершения. Атомарность означает неделимость изменения для наблюдателя: частично изменённое состояние не должно быть видно. Ожидание завершения и атомарность — разные свойства.

По умолчанию mutations_sync=0: успешный ответ означает принятие мутации, а не завершение переписывания. Поэтому SELECT сразу после асинхронной команды может ещё читать старое состояние или промежуточное сочетание партов.

mutations_sync=1 в наших опытах ждёт завершения на текущем сервере. Это не превращает ClickHouse в транзакционную систему с атомарной заменой всей таблицы. Реплики и ожидание нескольких серверов разберём отдельно в теме кластера.

Что проверяем перед разовым исправлением

Изменяется атрибут, а не ключ размещения? Нужна история прежних значений? Когда результат должен стать видимым?

Для UPDATE задаём условие, оцениваем затронутые парты и выбираем ожидание либо наблюдение через system.mutations.

Сначала отделяем изменение состояния с сохранением истории от исправления уже записанных строк. Затем проверяем, не меняется ли ключ. Для наблюдения мутации используем is_done, оставшиеся парты и причину последней ошибки.

Успешное принятие команды не доказывает завершение. В учебном UPDATE дождёмся mutations_sync=1 на текущем сервере, а в system.mutations проверим итоговый статус.

Два способа удаления строк по условию

ОперацияОпределение эффекта
ALTER TABLE … DELETE WHERE PМутация создаёт активные парты без строк, для которых P истинно

Скрытие строки, её исключение из активного парта и очистка старых файлов — разные этапы.

Удаление по условию задаёт предикат P(r), определяющий удаляемые строки. ALTER TABLE t DELETE WHERE P выполняется мутацией и создаёт активные парты, в которых выбранные строки отсутствуют.

DELETE FROM t WHERE P — лёгкое удаление. Внутренняя маска _row_exists определяет, какие физически сохранённые строки видимы обычному чтению: значение 0 скрывает строку. Это не немедленное удаление всех файлов её значений. Для Wide можно сохранить прежние файлы столбцов и записать отдельный файл маски.

ALTER TABLE t APPLY DELETED MASK перерабатывает парты с маской, исключая скрытые строки из нового активного содержимого. Старые неактивные парты могут оставаться на диске до очистки. Поэтому SELECT count(), system.parts.rows активных партов и наличие файлов отвечают на разные вопросы.

Выбор способа зависит от нужного эффекта, формата партов, условия и доли удаляемых строк. Ожидание завершения также задаётся отдельно: lightweight_deletes_sync для лёгкого удаления, mutations_sync для соответствующих ALTER-мутаций.

Удаление в потоке изменений тоже имеет порядок

Версия удаления — запись с ключом сущности, увеличенной версией и is_deleted=1.

В ReplacingMergeTree(version,is_deleted) сначала выбирается максимальная версия; если она помечена удалённой, FINAL не выдаёт сущность.

Запись удаления сохраняется и подавляет поздние строки с меньшей версией.

is_deleted — поле модели сущности; _row_exists — внутренняя маска лёгкого DELETE.

Версия удаления, также называемая tombstone, — запись с устойчивым ключом сущности, очередной версией и флагом is_deleted=1. Она сообщает, что после этого изменения сущность считается удалённой. Обычное физическое удаление имеющихся строк такого порядка для будущих вставок не задаёт.

В ReplacingMergeTree(version,is_deleted) правило максимальной версии применяется и к обычным состояниям, и к удалениям. Если победившая строка имеет is_deleted=1, SELECT FINAL не выдаёт сущность. По умолчанию строка удаления остаётся в хранении, в том числе после обычного слияния, чтобы поздняя строка с меньшей версией не восстановила объект.

Более высокая новая версия состояния может снова сделать сущность видимой; допустимость такого восстановления определяет протокол источника. Удаление самого tombstone требует отдельного соглашения о завершении доставки старых версий. В наших опытах CLEANUP не выполняется.

is_deleted относится к модели изменений сущности. _row_exists — внутренняя маска видимости физически сохранённых строк при лёгком DELETE. Эти механизмы не взаимозаменяемы.

TTL — правило истечения строк по времени

TTL (Time To Live) задаёт выражение срока и действие над данными по достижении этого срока.

Для удаления строк: TTL e(r) DELETE, где e(r) — дата или время истечения строки.

e(r) = event_at + INTERVAL 30 DAY

Достижение срока делает строку подлежащей удалению. Физическое применение выполняется позже при обработке партов.

В этой лекции рассматриваем TTL DELETE.

TTL, или Time To Live, — правило, связывающее вычисляемую дату или время с действием над данными. У ClickHouse есть несколько действий TTL; здесь рассматриваем табличный TTL DELETE, удаляющий строки по сроку.

Выражение e(r) вычисляет дату или время истечения для каждой строки. В TTL event_at+INTERVAL 30 DAY DELETE срок отсчитывается от event_at, а не от момента вставки. При достижении срока строка становится кандидатом на удаление. Обычный SELECT не обязан скрыть её ровно в эту секунду: применение TTL происходит при обработке партов.

MATERIALIZE TTL инициирует применение заданного правила к уже записанным данным; в учебном опыте используем mutations_sync=1 для ожидания на текущем сервере. Партиционирование по времени не является требованием TTL: правило работает и в хеш-партициях.

Если требуется удалить готовую партицию по явной границе, существует DROP PARTITION. TTL задаёт политику сроков и не выбирает актуальную версию сущности.

GROUP BY: определение группы

Ключ группировки G(r)=(g₁(r),…,gₙ(r)) вычисляется для каждой строки после WHERE.

r₁ и r₂ принадлежат одной группе ⇔ G(r₁) = G(r₂).

Агрегатные функции вычисляют показатели отдельно по строкам каждой группы. Обычный GROUP BY выдаёт одну строку на группу.

В ClickHouse значения NULL в ключе группируются вместе. Порядок результата GROUP BY не задан.

Группировка разбивает входные строки на группы по значению набора выражений G(r). Две строки попадают в одну группу, если совпадают все компоненты ключа GROUP BY. Входом здесь являются строки после WHERE. Для обычного GROUP BY без дополнительных ROLLUP/CUBE/GROUPING SETS результат содержит одну строку на группу, оставшуюся после HAVING.

В ClickHouse NULL в ключе группировки рассматривается как отдельное значение: строки с одинаковыми остальными компонентами и NULL в одной позиции входят в одну группу. Это правило группировки не следует заменять обычным SQL-сравнением NULL через знак равенства.

Агрегатная функция вычисляет показатель по строкам своей группы. Выражения результата должны быть вычислимы из ключей группировки и агрегатов. GROUP BY не сортирует результат; если порядок важен, в запросе нужен ORDER BY.

Например, GROUP BY shop_id создаёт группу на магазин, а GROUP BY (shop_id,hour) — на пару магазина и часа. Физически исполнитель может искать группы через хеш-таблицу или использовать порядок чтения. Способ исполнения не меняет заданное разбиение на группы.

Агрегатная функция и её состояние

Агрегатная функция преобразует набор значений группы в один результат: сумму, количество, среднее или другой показатель.

Состояние S — промежуточные данные для добавления строк и объединения порций.

начальное S → add(S, строка)
merge(S₁, S₂) → объединённое S
finalize(S) → готовый результат

Готовое среднее не содержит всю информацию состояния: нужны сумма и количество.

Агрегатная функция A получает значения строк группы и возвращает один результат. Для чисел это может быть sum или avg; результат не обязан быть числом — например, argMax может возвращать строку или кортеж. Агрегат отличается от обычной скалярной функции тем, что обрабатывает набор строк.

Состояние агрегата S — промежуточное представление, достаточное для дальнейшей обработки строк и объединения совместимых частичных результатов. Рассматриваем три операции: add добавляет входную строку, merge объединяет состояния порций, finalize получает готовое значение.

Для sum состояние содержит накопленную сумму, для count — количество, для avg — сумму и количество. Эти математические описания определяют нужную информацию и не обещают конкретный бинарный формат сериализации.

Частичное состояние рассчитано по части входа. Оно может существовать в отдельном потоке, блоке или строке таблицы AggregateFunction. Например, avgState для порции из одного платежа и avgState для трёх платежей нужно объединять как состояния с разными весами. Готовые средние этих порций таких весов не сохраняют.

Состояния sum и count

ФункцияОпределениеОбъединение порций
sum(x)Сумма участвующих значений xs = s₁ + s₂
count()Число строк группыn = n₁ + n₂
count(x)Число строк с x ≠ NULLn = n₁ + n₂

sum и avg пропускают NULL-аргументы. count() учитывает и такие строки.

При фиксированных типах состояния sum и count не растут с числом строк группы.

sum накапливает сумму, count — количество строк. Частичные состояния объединяются сложением: s₁+s₂ и n₁+n₂. Сами платежи хранить в этих состояниях не требуется.

При фиксированных типах размер состояния одной группы не растёт с числом строк. Число разных ключей, однако, увеличивает число состояний.

В формулах n для count() — число строк группы. У count(x) считаются только строки с не-NULL значением x. sum(x) пропускает NULL, а avg(x) делит сумму на число не-NULL значений. Поэтому знаменатель avg(x) при Nullable-аргументе соответствует count(x), а не count(). Далее в денежных примерах amount не Nullable.

Результат: 250

Частичные средние — 100 и 300. Их среднее равно 200, а среднее четырёх платежей — 250.

Среднее avg(x) — сумма участвующих не-NULL значений, делённая на их количество, если количество положительно. Его состояние можно математически представить парой (s,n). Добавление значения x увеличивает s на x и n на 1; объединение двух состояний даёт (s₁+s₂,n₁+n₂); финализация делит s на n.

Первый поток обработал одну строку с суммой 100, второй — три с суммой 900. Объединение даёт (1000,4), результат — 250. Если сохранить только средние потоков 100 и 300 и снова взять среднее, потеряем веса и получим 200.

Для пустого набора и Nullable-аргументов важны конкретная функция и тип результата; формула с делением на n здесь определена только для n>0. В примерах среднее проверяется на непустых группах. Готовое avg от Decimal в используемой версии имеет тип Float64; состояние при этом сохраняет тип исходного аргумента.

Один магазин может встретиться в нескольких потоках. Перед выдачей его частичные состояния нужно объединить.

Параллельная агрегация — вычисление частичных состояний по разным порциям входа с последующим объединением по ключам групп. Один магазин может встретиться в нескольких потоках; потоков исполнения и групп результата не обязано быть одинаковое число.

Pipeline — граф операторов исполнения и потоков данных между ними. EXPLAIN PIPELINE показывает операторы чтения, агрегации и объединения. Несколько AggregatingTransform означают несколько исполнителей, а не несколько независимых бизнес-отчётов. Для наблюдаемого плана отдельно проверяем настройки max_threads и optimize_aggregation_in_order.

Память зависит от групп и функции

Грубая модель: число групп × (ключ + состояние + служебные данные).

ФункцияЧто хранится для одной группы
sum, count, avgСостояние фиксированного размера
uniqExactНабор различных значений
uniqОграниченная выборка хешей для оценки

В параллельном плане частичные состояния могут существовать в нескольких потоках.

Расход памяти включает ключи групп, состояния функций и служебные структуры. Для sum, count и avg размер состояния при фиксированных типах ограничен. Для uniqExact он растёт с числом различных значений.

Параллельная обработка может создавать несколько частичных состояний одного ключа. Поэтому память нельзя оценить только по числу групп на выходе.

Кардинальность группировки — число различных результатов G(r) на входе после фильтрации. uniqExact(x) возвращает точную мощность множества не-NULL значений x; uniq(x) оценивает эту мощность по ограниченной адаптивной выборке хешей. Одинаковые значения одного аргумента в разных строках учитываются один раз. Маленький набор может дать одинаковый ответ обеих функций, что не превращает uniq в точную функцию для всех наборов.

Хеш-агрегация ищет или создаёт состояние по ключу группы в хеш-таблице. Пока группа может встретиться снова, её состояние остаётся доступным для обновления. Детали представления ключей зависят от типов и выбранного метода исполнения.

Агрегация по порядку использует совместимый порядок входа: после завершения диапазона ключа можно завершить соответствующую группу, не удерживая её состояние до конца всего чтения. В нашем примере GROUP BY service_id совпадает с префиксом ORDER BY таблицы, а optimize_aggregation_in_order=1 разрешает этот способ. Наличие сортировки само по себе не означает, что любой GROUP BY выполнится по порядку.

Внешняя агрегация выгружает промежуточные агрегированные данные на диск и затем объединяет их. max_bytes_before_external_group_by задаёт порог начала выгрузки; это не общий жёсткий предел памяти всего запроса. Семантика агрегатных функций и число логических групп при этом не меняются.

Способ исполнения проверяется через EXPLAIN PIPELINE и ProfileEvents. В Docker-опыте внешняя агрегация подтверждается ExternalAggregationWritePart и ExternalAggregationCompressedBytes, а ответ сверяется с ожидаемым. Влияние на память измеряем отдельно; универсального обещания ускорения нет.

Материализация сохраняет результат для повторного чтения

Материализация — сохранение вычисленного результата для последующего чтения.

Витрина — в наших примерах таблица показателей отчёта. Источник содержит операции, приёмник — результаты их обработки.

Материализованное представление (MV) — объект ClickHouse с запросом преобразования и правилом обновления сохранённого результата.

Результат зависит от запроса и способа обновления: при вставке либо при полном пересчёте.

Материализация — сохранение вычисленного результата, чтобы последующее чтение могло использовать его. Витриной в этой лекции называем таблицу показателей отчёта, например суммы платежей по магазину и часу. Это роль таблицы в модели, а не отдельный движок ClickHouse.

Источник — таблица, из которой берутся входные строки. Приёмник — таблица, в которую записываются результаты преобразования. Материализованное представление, MV, задаёт запрос преобразования и механизм обновления сохранённого результата; приёмник может быть задан явно через TO.

Обычное VIEW, инкрементальное MV и периодически обновляемое MV имеют разные правила исполнения. Инкрементальное применяет запрос к вставляемым блокам источника. Периодически обновляемое повторяет полный запрос. Поэтому определение одного SQL-запроса ещё не задаёт момент актуальности витрины.

Далее рассматриваем приёмники на SummingMergeTree и AggregatingMergeTree. Движок приёмника определяет обработку записанных частичных результатов, но не превращает изменения старых строк источника в новые входные события MV.

Почему сохранять отчёт, а не считать его каждый раз

Почасовой отчёт часто повторяется. Можно заново читать события либо сохранить результат и платить за его поддержание.

Выбор зависит от частоты чтения, допустимого запаздывания и характера изменений источника.

Если отчёт читают редко и запрос укладывается в требования, достаточно прямого SELECT. Если одни и те же показатели запрашиваются часто, можно перенести вычисление на вставку либо периодический пересчёт.

Сохранённый результат требует дополнительного места и работы по поддержанию. Поэтому сначала выбираем момент вычисления и правило актуальности, а затем движок целевой таблицы.

Refreshable MV в 24.12 — экспериментальная возможность. Здесь рассматриваем замену результата, без APPEND.

Обычное представление CREATE VIEW v AS Q сохраняет определение Q. Обращение к v выполняет этот запрос; строки отчёта внутри обычного VIEW отдельно не хранятся. Входом Q является текущее состояние, видимое его чтению источников.

Refreshable materialized view периодически выполняет полный запрос Q и сохраняет его результат. В рассматриваемом режиме без APPEND успешное обновление заменяет предыдущий сохранённый результат. Между обновлениями читатели используют результат последнего завершённого расчёта. В ClickHouse 24.12 механизм экспериментальный; пример выполняется в Atomic с allow_experimental_refreshable_materialized_view=1.

Инкрементальное MV с TO T AS Q выполняет Q для каждого входного блока B вставки источника и передаёт Q(B) в таблицу-приёмник T. В простом запросе над одним источником Q получает строки блока, а не всю накопленную таблицу. Объединение Q(B₁), Q(B₂) и следующих вкладов определяется движком T и запросом чтения T.

UPDATE, DELETE, TTL и фоновые слияния уже записанного источника сами не запускают обратный пересчёт этих вкладов. Создание такого MV также не загружает прежние строки источника автоматически. В опытах нет JOIN и нескольких источников; их зависимости разберём отдельно.

Вставка 1: shop 7 → 100 + 200 → 300
Вставка 2: shop 7 → 300         → 300

Витрина до слияния: 300, 300
Отчёт после объединения: 600

GROUP BY в MV обрабатывает блок, а не пересчитывает всю исходную таблицу.

Блок вставки — порция столбцов и строк, поступающая в обработку инкрементального MV. Одна команда INSERT может состоять из нескольких блоков; запись «одна вставка — один блок» далее относится только к маленьким учебным вставкам.

Пусть Q группирует блок по магазину и часу и считает сумму. Для первого блока с платежами 100 и 200 Q(B₁) содержит сумму 300. Для второго блока с платежом 300 Q(B₂) также содержит 300. Это два частичных результата одной отчётной группы.

Отчёт по приёмнику должен объединить оба вклада и получить 600. В нашем опыте фон приёмника остановлен, поэтому две строки видны отдельно. После слияния их физическое представление может измениться, но корректный запрос суммы по ключу отчёта должен возвращать тот же результат.

Что не делает инкрементальное представление

Не загружает старую историю автоматически.

Не отменяет уже записанный вклад при UPDATE, DELETE или замещении версий источника.

Не объединяет результаты всех вставок само по себе: это задача запроса и движка приёмника.

MV получает новые блоки. Для старой истории нужен отдельный backfill, согласованный с началом обработки новых данных. При исправлении уже записанной строки представление не получает её прежнюю сумму как отрицательный вклад.

Даже обычная группировка в MV видит только свой блок. Соседние вставки создают независимые частичные результаты, поэтому приёмник и чтение должны поддерживать корректное объединение. Эти ограничения следуют из границы обработки, а не из отдельной ошибки конфигурации.

Когда выбирать инкрементальный расчёт

Подходит: новые события дают независимые, объединяемые вклады в отчёт.

Полный пересчёт рассматриваем, если старые данные меняются и допустима периодическая актуализация.

Прямой SELECT сохраняем, если стоимость чтения приемлема и отдельная витрина не нужна.

Для суммы неизменяемых операций вклад нового блока можно сложить с предыдущим. Для суммы актуальных состояний такая арифметика неверна без отмены старого вклада. Поэтому модель строк выбираем до MV.

Инкрементальный расчёт переносит часть работы с чтения на вставку. Получится ли ускорить чтение, зависит от размера приёмника, группировки и функций; обработка исправлений при этом усложняется. Полный пересчёт повторно читает источник, зато включает его текущее состояние на каждом запуске. Решение зависит от нагрузки и допустимой задержки отчёта.

Расписание не меняет смысл SELECT. Если источник хранит версии, полный запрос также должен выбирать актуальные состояния через FINAL или argMax; один факт пересчёта эту задачу не решает.

SummingMergeTree: правило суммирования строк

SummingMergeTree((total, payments_count)) объединяет строки с одинаковым полным ORDER BY в пределах сливаемых партов одной партиции.

СтолбцыРезультат объединения
Ключ сортировкиОбщее значение ключа группы
total, payments_countСумма соответствующего столбца по строкам группы
Прочие обычные столбцыПроизвольное значение; смысл последней версии отсутствует

Если все суммируемые показатели равны нулю, при слиянии группа может исчезнуть.

Между партами могут оставаться частичные строки: читаем через GROUP BY и sum.

SummingMergeTree — движок семейства MergeTree, который при слиянии объединяет строки с одинаковым полным ORDER BY внутри одной партиции. Для каждого указанного числового столбца он записывает сумму значений обрабатываемых строк этого ключа. В нашем варианте SummingMergeTree((total,payments_count)) суммируются ровно эти два показателя.

Ключ объединения задаётся ORDER BY, даже если PRIMARY KEY короче. Значения ключа сохраняются; обычные неключевые столбцы вне списка суммирования не имеют семантики последней версии — выбирается произвольное значение. Поэтому измерения отчёта, которые нужно различать, включаем в ключ.

Список суммируемых столбцов в параметре движка необязателен; без него в рассматриваемых плоских схемах суммируются числовые столбцы вне ключей сортировки и партиционирования. В лекции используем явный список, чтобы числовой атрибут случайно не стал показателем. Отдельные правила специальных типов, например AggregateFunction и Nested Map, здесь не рассматриваем.

Если после суммирования все указанные показатели равны нулю, строка может быть удалена при физическом слиянии. В нашей витрине payments_count положителен, поэтому нулевая денежная сумма сама по себе не означает нулевую группу.

Слияние может обработать лишь часть партов. Для того же ключа в других партах могут остаться частичные суммы, поэтому запрос отчёта продолжает использовать GROUP BY измерений и sum каждого показателя. Движок не обеспечивает одну физическую строку на ключ сразу после INSERT.

Ключ витрины должен сохранять измерения

Отчёт группируется по (shop_id, hour) — эти измерения сохраняем в ключе сортировки.

Если оставить только shop_id, слияние сможет сложить разные часы.

Если добавить event_id, строки одной отчётной группы не будут полностью укрупняться.

Измерения отчёта — атрибуты, по значениям которых различаются группы: здесь shop_id и hour. Показатели — вычисляемые значения каждой группы: total и payments_count. Ключ отчётной группы — кортеж всех её измерений.

Приёмник должен сохранять различие тех групп, которые отчёт обязан различать. Для нашей почасовой витрины полный ORDER BY равен (shop_id,hour). Если убрать hour, слияние сможет сложить показатели разных часов одного магазина. Прочий столбец hour не сохранит несколько отдельных часов в одной строке.

Если приёмник, наоборот, сохраняет отдельный event_id и включает его в ORDER BY, строки разных событий не объединятся в одну строку магазина и часа при слиянии. Запрос всё ещё может их сгруппировать, но физическое укрупнение по отчётной группе будет потеряно.

CREATE TABLE payments
( event_id UInt64, shop_id UInt32, user_id UInt64,

ENGINE=MergeTree

SummingMergeTree хранит частичные суммы

Явно задаём, какие столбцы суммируются. Ключ задаёт магазин и час.

CREATE TABLE hourly_sums
( shop_id UInt32, hour DateTime('UTC'),
  total Decimal(38, 2), payments_count UInt64 )
ENGINE=SummingMergeTree((total, payments_count))
PARTITION BY toYYYYMM(hour)
ORDER BY (shop_id, hour);
SYSTEM STOP MERGES hourly_sums;

В ENGINE явно перечисляем суммируемые столбцы: total и payments_count. Ключ магазина и часа задаёт группу, внутри которой они складываются.

Партиция месячная. STOP MERGES позволит увидеть вклады отдельных вставок до их физического объединения.

Как загрузить накопленную историю

Создание MV с TO hourly_sums не загружает уже записанные строки payments.

Простой учебный порядок: остановить запись → создать MV → загрузить историю → возобновить запись.

-- Только если история ещё не попала в витрину!
INSERT INTO hourly_sums
SELECT shop_id, toStartOfHour(paid_at) AS hour,
       sum(amount), count()
FROM payments
GROUP BY shop_id, hour;

Backfill — отдельная загрузка в приёмник результатов по строкам, уже существовавшим в источнике до начала обработки новых вставок MV. Это не создание ещё одного вида движка, а операция согласования истории с новым способом расчёта.

CREATE MATERIALIZED VIEW ... TO hourly_sums не загружает прежние строки payments. В учебном варианте останавливаем запись источника, создаём MV, выполняем INSERT INTO приёмник SELECT ... FROM источник по всей ещё не учтённой истории и затем возобновляем запись.

Каждая исходная операция должна попасть в приёмник один раз: либо через историческую загрузку, либо через обработку новых вставок. Если повторить тот же backfill в суммирующий приёмник, вклад будет добавлен повторно. Конкурентная загрузка требует отдельной границы и протокола переключения.

SQL на этом слайде не входит в общий demo.sql, потому что текущие строки payments уже обработаны MV. Дополнительный Docker-сценарий проверяет backfill на отдельном источнике и показывает удвоение при повторе.

State, Merge и MergeState

Комбинатор — суффикс имени агрегатной функции, изменяющий её вход или выход.

ФормаВход → выход
fState(x)Исходные значения → состояние f
fMerge(s)Совместимые состояния f → готовый результат f
fMergeState(s)Совместимые состояния f → объединённое состояние f

AggregateFunction(f, T…) — тип столбца для состояния заданной функции с аргументами типов T…

Комбинатор агрегатной функции — суффикс имени, меняющий её вход, выход или правило применения. Здесь рассматриваем State, Merge и MergeState, а в примере возвратов — If.

fState(x) обрабатывает исходные значения и возвращает промежуточное состояние f. Его можно хранить в столбце AggregateFunction(f,T…), где f — конкретная функция, а T… — типы её аргументов. Это типизированное состояние, а не готовое число и не обещание переносимого внутреннего бинарного устройства.

fMerge(s) принимает совместимые состояния той же функции, объединяет их и финализирует результат. fMergeState(s) также объединяет состояния, но возвращает состояние для дальнейшего хранения или объединения. Например, avgMerge возвращает среднее, а avgMergeState сохраняет объединённые сумму и количество.

Совместимость включает функцию, её параметры при наличии и типы аргументов. Состояние avg нельзя передать sumMerge только потому, что исходный аргумент был числом. Аналогично avgState(Decimal(18,2)) не объявляем состоянием avg от UInt64.

Комбинатор If добавляет условие участия строки: sumIf(amount,kind='paid') суммирует amount только для строк, где условие истинно. Он не хранит отдельную историю оплат и возвратов — это смысл исходных строк.

Среднее и уникальные не складываются

Средние требуют весов. Число уникальных требует учитывать пересечения покупателей между вставками.

Порция 1: пользователи {10, 20} → 2
Порция 2: пользователи {10}     → 1
Общий результат: {10, 20}      → 2, не 3

Для среднего нужны веса порций. Для числа уникальных — информация о пересечении пользователей.

Первая порция содержит {10, 20}, вторая — {10}. Сложение готовых чисел 2 и 1 даёт неверные 3. Для объединения сохраним состояния функций.

AggregateFunction хранит состояние конкретной функции с конкретными типами аргументов. Оно не является универсальным числом, которое можно передать любой Merge-функции.

AggregatingMergeTree: правило объединения состояний

AggregatingMergeTree объединяет строки одного полного ORDER BY в сливаемых партах одной партиции.

Для каждого столбца AggregateFunction(f,T…) результат — объединённое состояние функции f. Финализация при таком слиянии не выполняется.

Частичные строки могут остаться в других партах. Читаем: GROUP BY измерений и соответствующие fMerge.

Число строк состояний не равно числу исходных операций.

AggregatingMergeTree — движок семейства MergeTree, изменяющий правило обработки равных ключей при слиянии. Среди обрабатываемых строк с одинаковым полным ORDER BY внутри одной партиции состояния каждого столбца AggregateFunction(f,T…) объединяются операцией merge соответствующей функции f.

Результат слияния в таком столбце остаётся состоянием, а не финализированным показателем. Для avg это позволяет продолжать учитывать веса порций; для uniq — пересечения значений. PRIMARY KEY может быть короче, но равенство для объединения определяется полным ключом сортировки.

Другие парты могут ещё содержать состояния той же группы. Запрос чтения поэтому группирует по измерениям и применяет соответствующий fMerge к каждому столбцу состояния. Этот запрос корректен и до фонового объединения, и после него.

SimpleAggregateFunction(f,T) хранит значение типа T для функций, у которых результаты порций можно объединить применением той же f. Для sum это sum(sum(A),sum(B))=sum(A∪B), где A и B — порции строк с сохранением повторов. Движок поддерживает этот тип наряду с AggregateFunction. Готовое среднее такого свойства не имеет; avg/uniq в нашей схеме храним как состояния AggregateFunction. Обычные неключевые столбцы без агрегатного типа не превращаются в показатели автоматически: их произвольные значения не должны определять результат отчёта.

Один INSERT не означает одну сохранённую строку на группу, а число строк в приёмнике не является числом операций источника. Если сохранить только окончательные средние или числа уникальных, движок не восстановит потерянные веса и пересечения.

CREATE TABLE hourly_states
( shop_id UInt32, hour DateTime('UTC'),
  avg_amount AggregateFunction(avg, Decimal(18, 2)),

GROUP BY shop_id, hour;

state_input — отдельный пустой источник структуры payments. Новое MV направляет его данные в hourly_states, не затрагивая предыдущую витрину сумм.

avgState(amount) и uniqState(user_id) создают состояния для каждого магазина и часа текущего блока.

Слияние источника не исправляет витрину

MV реагирует на вставки. Фоновое замещение, мутация или удаление партиции источника не вычитают ранее записанную сумму из витрины.

OPTIMIZE TABLE version_input FINAL;
SELECT sum(amount) AS source FROM version_input;
SELECT sum(total) AS target FROM version_total;

Проверенный результат · ClickHouse 24.12.3.47

150
250

После OPTIMIZE в источнике физически остаётся 150. Витрина по-прежнему хранит 250.

Слияние, мутация и удаление партиции источника не запускают обратный пересчёт инкрементального MV. FINAL в его определении также не вычитает ранее переданный вклад.

Истечение TTL источника также не отменяет уже переданный вклад. Если витрина должна хранить только заданный период, её срок хранения или пересчёт проектируют отдельно от очистки источника.

Витрина для проверки UPDATE и DELETE

Источник содержит один платёж на 100. MV записывает его сумму в отдельную таблицу.

CREATE TABLE mv_change_source
(id UInt64, amount Decimal(18, 2)) ENGINE=MergeTree ORDER BY id;
CREATE TABLE mv_change_total
(k UInt8, total Decimal(38, 2))
ENGINE=SummingMergeTree(total) ORDER BY k;
CREATE MATERIALIZED VIEW mv_change_capture
TO mv_change_total AS
SELECT toUInt8(1) AS k, sum(amount) AS total
FROM mv_change_source;
INSERT INTO mv_change_source VALUES (1,100);

Создаём независимую таблицу с одной строкой и витрину общей суммы. Первая вставка передаёт в приёмник 100.

Этот опыт отделён от таблиц версий: теперь проверяем прямую мутацию и лёгкое удаление уже записанной строки. Они не являются новыми вставленными событиями для MV.

Журнал операций: отдельный возврат

Оплата 100 и возврат 30 — две операции. Считаем сумму оплат, сумму возвратов и разность. Каждую операцию учитываем один раз.

sumIf(x, P) суммирует x только по строкам с истинным условием P.

SELECT sumIf(amount, kind='paid') AS paid,
 sumIf(amount, kind='refund') AS refunded,
 paid-refunded AS net
FROM values('event_id UInt64, kind String, amount Decimal(18, 2)',
 (1,'paid',100),(2,'refund',30));

Проверенный результат · ClickHouse 24.12.3.47

100    30    70

Оплата на 100 и возврат на 30 — отдельные операции. Обе суммы положительны; sumIf разделяет их по kind, а разность даёт 70.

Такой журнал можно накапливать по операциям при однократном учёте каждой. Возврат сохраняет исходную оплату в истории. Повторная доставка операции требует защиты от двойного счёта.

Четыре движка: что происходит при слиянии?

ENGINEРавные ключи при обычном слиянии
MergeTreeСохраняются все строки
ReplacingMergeTree(v)Выбирается максимальная версия
SummingMergeTreeСкладываются указанные числовые показатели
AggregatingMergeTreeОбъединяются агрегатные состояния

Для журнала независимых операций сохраняем события. Для актуальных состояний выбираем версии. Для объединяемых числовых показателей подходит SummingMergeTree, для состояний функций — AggregatingMergeTree.

Движок выбирает действие над одинаковым ключом, а ключ — какие строки должны обрабатываться вместе. Корректный запрос учитывает, что фон ещё может не объединить парты. Ни одна из этих настроек не заменяет определение смысла строки и показателя.

Таблица сравнивает обработку равных ключей при обычном слиянии. Явные UPDATE/DELETE и правила TTL могут изменять или удалять строки отдельно; MergeTree не превращает эти операции в доступную для запросов историю.
