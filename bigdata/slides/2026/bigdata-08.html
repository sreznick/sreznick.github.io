Каким операциям нужно состояние

ОперацияЧто нужно помнить
Проверить amount > 0Ничего о предыдущих записях
Посчитать сумму магазинаУже накопленную сумму
Убрать повторыРанее встреченные event_id
Соединить заказ и оплатуПолученную запись, пока ждём вторую

Состояние, или state, — промежуточные данные, которые оператор хранит между сообщениями.

Оператором будем называть один шаг обработки: фильтрацию, подсчёт суммы или соединение записей.

Фильтр положительных сумм проверяет текущую запись. Предыдущие оплаты ему не нужны. Подсчёту суммы, наоборот, нужно знать, сколько уже накоплено по магазину. Для удаления повторов нужны ранее встреченные event_id. Для соединения заказа и оплаты нужно сохранить запись, которая пришла первой.

Эти промежуточные данные называют состоянием оператора, или state. Оно может находиться в памяти или на диске. Само наличие состояния ещё не означает, что оно переживёт потерю машины: для этого понадобится механизм восстановления.

Как согласовать суммы магазинов и общую сумму

A считает сумму магазина и передаёт изменения B. B считает общую сумму всех магазинов.

A обновил свою сумму: 100 → 300
A отправил B изменение «+200»
Сообщение отправлено, но B ещё не прибавил 200

Сохранили A после отправки, а B — до обработки. Если сообщение не восстановить, в общей сумме не будет этих 200.

Нужно восстановить и сообщение между A и B либо согласовать снимки так, чтобы оно не потерялось.

Рассмотрим два последовательных шага потоковой обработки. Первый считает суммы отдельных магазинов, второй — общую сумму по всем магазинам. Такие шаги называют операторами. На схеме A — обработчик одного магазина, B — обработчик общей суммы. A передаёт B каждое изменение своей суммы: например, «прибавить двести», а не полное значение.

У A была сумма сто. После оплаты на двести он сохранил триста и отправил B сообщение «прибавить двести». Между A и B данные передаются через буферы движка и, если обработчики на разных машинах, по сети. В момент снимка A уже отправил сообщение, но B ещё не обработал его. Это сообщение в пути между двумя шагами вычисления.

Если сохранить A после отправки сообщения, а B — до его обработки, нужно обеспечить и восстановление самого сообщения. Иначе после сбоя в общей сумме будет не хватать двухсот рублей. A уже учёл оплату, а B не получил её изменение. Каждый локальный снимок сам по себе корректен, но их недостаточно для восстановления всей обработки.

Нужно либо сохранить сообщение в пути, либо согласовать снимки иначе: например, сохранить B уже после обработки этого сообщения. Во Flink согласование выполняют checkpoint barriers — служебные отметки границы снимка. В некоторых режимах также сохраняют сообщения в каналах. Checkpoint должен описывать одну согласованную точку восстановления всего вычисления.

Окно, checkpoint и Kafka-транзакция выполняют разные задачи. Окно объединяет события для расчёта. Checkpoint задаёт, как восстановить обработку. Kafka-транзакция подтверждает записи и offsets в одном Kafka-кластере.

Один checkpoint может включать состояние многих окон; одно окно может сохраняться через много checkpoints. Общий checkpoint не заставляет двух независимых клиентов одновременно опубликовать связанные события. Если нужны обе части операции, приложение должно сопоставлять их и решать, сколько ждать недостающую часть.

Непрерывные операторы:
запись → работающий оператор → обновление суммы

Микробатчи:
[A, B] → запуск задач → обновление суммы
[C, D] → следующий запуск → обновление суммы

Окно группирует записи по времени событий. Микробатч — порция записей для исполнения.

Одна минута оплат может обрабатываться многими микробатчами. В одном микробатче могут быть оплаты разных минут.

В непрерывном режиме уже работающий оператор получает очередные записи и обновляет своё состояние. В микробатчевом режиме движок собирает очередную порцию новых записей и запускает обработку этой порции.

Минутное окно может получать оплаты из многих микробатчей. И наоборот, один микробатч может содержать записи разных минут, включая задержавшиеся. Размер окна задаёт смысл группировки, а размер микробатча — организацию работы.

Непрерывный режим тоже может использовать сетевые буферы и пакетную запись. Это не обещание отдельного сетевого вызова на каждое событие. И ни один режим сам по себе не определяет, когда показать окончательную сумму: для этого остаются правила окон и публикации.

Отдельный вычислительный сервис Kafka Streams не требуется. Но сами приложения нужно развёртывать, наблюдать и обновлять. Один процесс может выполнять несколько tasks; task и процесс — не одно и то же.

Spark: driver, executors и checkpoint

Driver определяет порцию и управляет задачами
                  ↓
Kafka → Executors: обработка + state → приёмник
                  ↓
       Checkpoint в надёжном хранилище
  • Каждый микробатч читает новую порцию записей.
  • Состояние сохраняется для следующего микробатча.
  • При сбое запрос восстанавливается из checkpoint.

В микробатчевом режиме Spark driver определяет очередную порцию входа и координирует её обработку. Executors выполняют задачи, обновляют состояние и записывают результат через выбранный sink.

После порции работа продолжается на следующих данных. Сумма одного окна сохраняется между микробатчами. Checkpoint в надёжном хранилище позволяет восстановить и состояние, и место чтения.

Это не то же самое, что persist для ускорения повторных вычислений над RDD. Кэш можно потерять и пересчитать, если доступен вход. Checkpoint потокового запроса нужен для согласованного продолжения работы.

Состояние не обязано навсегда оставаться на одном executor. После сбоя или переназначения задач его загрузка тоже занимает время. Здесь рассматриваем именно микробатчевый режим Structured Streaming.

Для оконной суммы Spark предлагает несколько способов выдавать результат. Append добавляет результат окна после того, как оно больше не будет обновляться по правилам запроса. Update выдаёт изменившиеся суммы. Complete выдаёт всю текущую таблицу результата на каждом шаге.

Для безопасной записи можно использовать batchId. Встроенный Kafka sink тоже не даёт автоматически exactly-once только потому, что у запроса есть checkpoint.

Flink: операторы, состояние и время

Источник → операторы обработки → приёмник

                 ↓
       сохранение в checkpoint

  • Watermarks помогают решать, когда закрыть окно.

Во Flink задание развёрнуто как граф работающих операторов. Записи проходят от источника через преобразования к приёмнику. Если следующему оператору нужно другое распределение по ключам, данные направляются соответствующим обработчикам.

Операторы хранят состояние. Watermarks проходят по графу и позволяют принимать решения о времени событий. Timers запускают действие при достижении заданного времени — например, проверяют, закончено ли ожидание пары.

Несколько операторов могут выполняться в одном процессе. Поэтому стрелка между ними не всегда означает сетевую передачу. Flink поддерживает и другие способы описания обработки, включая SQL; на схеме показаны основные части исполнения.

Как системы завершают расчёт окна

СистемаПо чему решает, что пора завершать
Kafka StreamsStream-time продвигается по timestamps. Grace задаёт дополнительное ожидание
SparkWatermark позволяет завершать оконные суммы. Режим вывода определяет, какие суммы публикуются

Одинаковый допуск «2 минуты» в разных системах не означает одинакового поведения.

Мы обсуждали общую задачу, но настройки времени у систем различаются.

В Kafka Streams оконная агрегация использует stream-time и grace. После того как stream-time прошёл конец окна с учётом grace, оператор больше не принимает в него записи. Выдачу только окончательного результата настраивают отдельно.

В Spark watermark вычисляется по наблюдаемому времени событий; выдача суммы зависит от output mode. При этом записи с опозданием больше указанного допуска могут быть обработаны или отброшены. Из настройки нельзя вывести универсальное правило отбрасывания для любого запроса.

Поэтому сравниваем поведение на одних и тех же данных: меняем порядок получения записей, останавливаем вход, добавляем старые timestamps. Одинаковое число минут в двух настройках ещё не означает одинаковый результат.

Основные понятия потоковой обработки

  • Выбираем ключ и время, по которым считаем.
  • Решаем, когда показать сумму и сколько принимать исправления.
  • Храним промежуточные данные и определяем срок их хранения.
  • Сохраняем состояние вместе с позициями чтения.
  • Проверяем, что произойдёт при повторной записи результата.

При работе с потоком надо определить несколько вещей. По какому ключу собирать записи? Какое время использовать? Когда показать результат и сколько принимать исправления? Какие данные хранить между сообщениями?

Для восстановления сохраняем состояние вместе с позициями чтения. Необходимые для повтора записи должны оставаться в источнике. Запись во внешний приёмник проверяем отдельно: checkpoint не отменяет уже отправленное уведомление или завершённую транзакцию БД.

Kafka Streams, Spark и Flink предоставляют разные способы выполнить эту работу. Выбирать между ними стоит по требованиям к результату и эксплуатации.

Далее перейдём к ClickHouse: будем хранить события и суммы так, чтобы быстро выполнять аналитические запросы.
