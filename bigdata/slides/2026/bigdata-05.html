HBase

Архитектура и проектирование схем

Распределенное key-value хранилище поверх HDFS

Не замена Hive. Дополнение для online-доступа

CAP-теорема

Система координат для распределенных хранилищ

01

CAP-теорема: Формулировка

В распределенной системе невозможно одновременно гарантировать:

  • C (Consistency): все узлы видят одни и те же данные в один момент времени
  • A (Availability): каждый запрос получает ответ (успех или неудача), без бесконечного ожидания
  • P (Partition Tolerance): система продолжает работать при потере связи между узлами

Ключевой вывод: при сетевом разделении (partition) нужно выбрать: жертвуем C или A

CAP-теорема: Классификация

ТипЧто выбираетПримерыПоведение при partition
CPConsistencyHBase, ZooKeeper, etcdОтказывает в обслуживании части запросов, но данные консистентны
APAvailabilityCassandra, DynamoDB, CouchDBОтвечает всегда, но данные могут быть устаревшими
CAConsistency + AvailabilityPostgreSQL, MySQL (single-node)Не переживает разделение сети. Только один узел

CA в распределенной системе невозможна. Только single-node

CAP-теорема: HBase = CP

  • Consistency: чтение всегда возвращает свежие данные (strong consistency)
  • Partition Tolerance: при потере связи между RegionServer'ами, HMaster перераспределяет Region'ы
  • Availability: при разделении сети часть Region'ов может быть недоступна (до перераспределения)

Что это значит на практике

  • Запись считается успешной только после записи в WAL (durability)
  • Чтение идет через один RegionServer — нет "чтения из нескольких мест"
  • При сбое RegionServer'а данные временно недоступны (до failover)

CAP-теорема: Cassandra = AP

  • Availability: любой узел может принять запись/чтение
  • Partition Tolerance: peer-to-peer, нет единой точки отказа
  • Consistency: eventual consistency. Настраивается через QUORUM (например, запись в 2 из 3 узлов)

Что это значит на практике

  • Запись может быть принята, даже если часть узлов недоступна
  • Чтение может вернуть устаревшие данные (если реплика не успела обновиться)
  • Нужен repair (ремонт) для синхронизации данных между узлами

CAP-теорема: RocksDB = CA (single-node)

  • Consistency: strong consistency в рамках одного процесса
  • Availability: всегда доступен (если процесс жив)
  • Partition Tolerance: нет сети, нет разделения

Что это значит на практике

  • RocksDB — встраиваемая библиотека, не распределенная система
  • Используется как движок хранения внутри других систем (Kafka Streams, Flink, TiKV)
  • Масштабирование — только вертикальное (упирается в ресурсы одного сервера)

CAP-теорема: Сравнение

Позиционирование

Где место HBase в экосистеме Hadoop

02

Позиционирование: Проблема

  • HDFS — append-only файловая система. Не умеет перезаписывать файлы
  • MapReduce — пакетная обработка. Latency = минуты/часы
  • Нужен произвольный доступ (Get/Put) с задержкой в миллисекунды

Примеры задач

  • История заказов пользователя (точечный Get по user_id)
  • Фид новостей (Scan по диапазону времени)
  • Счетчики просмотров (Increment)

Позиционирование: Решение

  • HBase — распределенное key-value хранилище поверх HDFS
  • Обеспечивает online-доступ к большим данным
  • Использует LSM-Tree для быстрой записи

Ключевое отличие от Hive

  • Hive — SQL над файлами (полное сканирование)
  • HBase — индекс для точечного чтения (Get/Put)

Позиционирование: Сравнение с соседями

LSM-Tree

Фундамент, на котором построен HBase

03

LSM-Tree: Мотивация

Проблема B-Tree

  • Случайные записи: каждая запись = отдельный seek на диск
  • Пропускная способность ограничена скоростью seek (10ms)
  • Пример: 1000 записей = 1000 * 10ms = 10 секунд

Идея LSM-Tree

  • Не записывать данные сразу на место
  • Накопить в памяти, затем слить одним последовательным потоком
  • Последовательная запись в 10-100 раз быстрее случайной

LSM-Tree: Структура

[MemTable] (RAM, сортированная структура: skiplist, red-black tree)
    |
    | Flush (последовательная запись)
    v
[SSTable 1] -> [SSTable 2] -> [SSTable 3] -> ... (на диске, неизменяемые)
    |
    | Compaction (слияние)
    v
[Новый SSTable] (без дубликатов, отсортирован)
  • MemTable: буфер в памяти, сортированная структура
  • SSTable: неизменяемый файл на диске, данные отсортированы по ключу
  • WAL: журнал для восстановления после сбоя
  • Compaction: фоновое слияние файлов

LSM-Tree: Операции

ОперацияКак работаетСложность
PutWAL + MemTableO(log n) — быстро
GetMemTable + SSTable (от новых к старым)O(n * log n) — может быть медленно
DeleteTombstone (маркер) в MemTableO(log n) — быстро
ScanMemTable + SSTable (merge)O(n) — эффективно

Delete не удаляет данные физически. Только помечает. Реальное удаление — при Compaction

LSM-Tree: Сильные стороны

  • Быстрая запись: все операции последовательные (WAL + Flush)
  • Высокая плотность: сжатие лучше на больших блоках, нет фрагментации
  • Простая отказоустойчивость: SSTable неизменяемы, восстановление = replay WAL

Почему это важно для HBase

  • HDFS не умеет перезаписывать файлы — SSTable идеально подходит (append-only)
  • WAL дает durability без случайных записей

LSM-Tree: Слабые стороны

ПроблемаПричинаРешение
Медленное чтениеПоиск в нескольких SSTableBloom Filter, Block Cache, Compaction
Write AmplificationОдна запись перезаписывается при CompactionLeveled Compaction (RocksDB), Size-Tiered (Cassandra)
Read AmplificationПроверка нескольких файловBloom Filter, Partitioning
Space AmplificationМусор (старые версии) занимает местоCompaction

LSM-Tree: Read Amplification

  • Get: нужно проверить MemTable + все SSTable (от новых к старым)
  • Чем больше SSTable, тем медленнее чтение

Решения

  • Bloom Filter: вероятностная структура. "Ключа точно нет" — пропускаем файл
  • Block Cache: кэш горячих блоков в памяти
  • Compaction: уменьшение числа файлов

LSM-Tree: Write Amplification

  • Одна запись перезаписывается несколько раз при Compaction
  • Пример: запись попадает в MemTable -> Flush -> Compaction (несколько раз)

Решения

  • Leveled Compaction (RocksDB): данные распределены по уровням, каждый уровень в 10 раз больше предыдущего
  • Size-Tiered Compaction (Cassandra): объединение файлов похожего размера
  • HBase: Minor (часто, дешево) + Major (редко, дорого)

LSM-Tree: Возможности

  • Range Scans: данные отсортированы — легко итерироваться по диапазону
  • Версионирование: timestamp у каждой записи, старые версии хранятся до Compaction
  • TTL: автоматическое удаление устаревших данных при Compaction
  • Инкрементальные агрегации: merge при Compaction может выполнять sum/count
  • Merge-Join: два отсортированных потока сливаются за O(n)

LSM-Tree: Ключевой вывод

LSM-Tree — это компромисс:

Жертвуем чтением (Read Amplification) ради записи (Write Optimization).

Идеален для:

  • Write-heavy нагрузок (логи, метрики, события)
  • Append-only данных (временные ряды)
  • Систем, где важна скорость приема данных

HBase — распределенная реализация LSM-Tree поверх HDFS

Модель данных HBase

Как LSM-Tree выражается в таблицах

04

Модель данных: Таблица

  • Не реляционная таблица, а разреженная многомерная карта
  • Строки отсортированы по RowKey (байтовый порядок)
  • Ячейка: (RowKey, Column Family, Qualifier, Timestamp) -> Value

Пример

RowKey=user_42
  CF=profile:  name="Alice", age=30
  CF=settings: theme="dark", lang="ru"

Разные строки могут иметь разные наборы колонок

Модель данных: RowKey

  • RowKey — ключ в LSM-Tree. Все данные сортируются по нему
  • Один RowKey = одна сущность (пользователь, заказ, событие)
  • Доступ: точечный Get (по ключу) или Scan (по диапазону)

Ключевые свойства

  • Сортировка — байтовая (лексикографическая)
  • Длина влияет на память (индексы, кэш)
  • Дизайн RowKey — самое важное решение при проектировании

Модель данных: Column Family

  • Column Family (CF) — физическое хранилище. Каждый CF = отдельный LSM-Tree
  • Колонки внутри CF — динамические (Qualifier). Не нужно заранее определять схему
  • Рекомендуется 1–3 CF на таблицу

Почему мало CF?

  • Каждый CF = отдельные файлы на диске
  • Чтение из нескольких CF = чтение из нескольких LSM-Tree
  • Разные CF могут иметь разные настройки: TTL, сжатие, in-memory

Модель данных: Qualifier и Timestamp

  • Qualifier — имя колонки внутри CF. Динамическое
  • Timestamp — версия значения. По умолчанию — время записи

Пример

RowKey=user_42
  CF=profile:
    name:qualifier="Alice", timestamp=2025-01-01 10:00
    name:qualifier="Alice Smith", timestamp=2025-01-02 15:30
  • Чтение по умолчанию возвращает последнюю версию
  • Можно читать конкретную версию по timestamp
  • Количество хранимых версий настраивается (VERSIONS)

Модель данных: Разреженность

  • Разные строки могут иметь разные наборы колонок
  • Пустые ячейки не хранятся (не занимают место)

Пример

RowKey=user_42
  CF=profile: name="Alice"
  CF=profile: age=30

RowKey=user_43
  CF=profile: name="Bob"
  // нет age — не хранится

В реляционной БД пришлось бы хранить NULL. В HBase — просто отсутствие ячейки

Архитектура кластера

Компоненты и их роли

05

Архитектура: Компоненты

  • HMaster: управление Region'ами, балансировка, обработка сбоев. Не участвует в пути данных
  • RegionServer: рабочая лошадка. Принимает запросы, держит WAL, управляет Region'ами
  • ZooKeeper: координация, поиск META-таблицы, выбор HMaster
  • HDFS: хранение данных (HFile) и WAL

Архитектура: HMaster

  • Управляет Region'ами: назначает на RegionServer'ы, балансирует
  • Обрабатывает сбои: перераспределяет Region'ы упавших серверов
  • Не участвует в пути данных (чтение/запись идут напрямую к RegionServer)

Что это значит

  • HMaster может упасть — данные останутся доступны
  • Но без HMaster нельзя перераспределить Region'ы (нет failover)
  • HA: два HMaster (active/standby) через ZooKeeper

Архитектура: RegionServer

  • Принимает запросы от клиентов (Get/Put/Scan)
  • Держит WAL (Write-Ahead Log) для durability
  • Управляет Region'ами: MemStore, HFile, Compaction

Внутри RegionServer

  • Несколько Region'ов (обычно 10-100)
  • Каждый Region = диапазон RowKey
  • BlockCache — кэш горячих блоков для чтения

Архитектура: Region

  • Region — горизонтальный шард таблицы (по диапазону RowKey)
  • Таблица разбита на Region'ы. Каждый RegionServer держит несколько Region'ов
  • При росте Region делится пополам (Split)

Внутри Region

  • Store = один Column Family внутри Region
  • MemStore = буфер в памяти (MemTable)
  • HFile = SSTable на HDFS

Архитектура: Путь записи

  1. Client -> ZooKeeper (найти RegionServer для ключа)
  2. Запись в WAL (последовательно, для durability)
  3. Запись в MemStore (в память)
  4. При достижении порога — Flush: MemStore -> HFile (последовательная запись на HDFS)

Быстро, потому что все операции последовательные

Архитектура: Путь чтения

  1. Client -> ZooKeeper (найти RegionServer)
  2. Поиск в MemStore (свежие данные)
  3. Поиск в BlockCache (кэш горячих блоков)
  4. Поиск в HFile (старые данные, через Bloom Filter)

Чтение может быть медленным: нужно проверить несколько HFile. Решение — Compaction

Архитектура: WAL (Write-Ahead Log)

  • Журнал для восстановления после сбоя
  • Каждая запись сначала попадает в WAL, потом в MemStore
  • При сбое RegionServer'а данные восстанавливаются из WAL

Особенности

  • WAL хранится на HDFS (репликация)
  • Один WAL на RegionServer (не на Region)
  • При сбое WAL разбивается и распределяется по другим RegionServer'ам

Архитектура: HFile

  • SSTable на HDFS. Неизменяемый файл
  • Данные отсортированы по RowKey
  • Содержит индексы и Bloom Filter для ускорения чтения

Структура HFile

  • Trailer: метаданные, указатели на индексы
  • Index: дерево для поиска блоков
  • Bloom Filter: вероятностная структура для проверки наличия ключа
  • Data Blocks: сами данные (сжатые)

Архитектура: Compaction

  • Minor Compaction: объединение нескольких HFile в один. Быстро, часто
  • Major Compaction: объединение всех HFile в один. Медленно, редко. Удаляет tombstone и старые версии

Проблемы

  • Write Amplification: одна запись перезаписывается несколько раз
  • Major Compaction может блокировать чтение (stop-the-world)

Архитектура: Split

  • Region растет — данные не помещаются
  • Split: Region делится на два по середине RowKey
  • Дочерние Region'ы распределяются по RegionServer'ам

Когда происходит

  • Размер Region превышает порог (hbase.hregion.max.filesize)
  • Настраивается автоматически или вручную

Архитектура: ZooKeeper

  • Координация: выбор HMaster, обнаружение RegionServer'ов
  • Хранение расположения META-таблицы
  • Отслеживание состояния узлов (heartbeat)

META-таблица

  • Содержит расположение всех Region'ов
  • Client сначала обращается к ZooKeeper, потом к META, потом к RegionServer
  • Кэшируется на клиенте для ускорения

Проектирование схемы

Паттерны и антипаттерны RowKey

06

Проектирование: Принципы

Главное правило: все данные физически сортируются по RowKey. Один RowKey = одна сущность.

Три вопроса при проектировании

  • Как я буду читать данные? (по ключу, по диапазону, по префиксу)
  • Как я буду писать данные? (равномерно или в одну точку)
  • Какой у меня паттерн доступа? (горячие ключи, последние данные)

Проектирование: Паттерны RowKey

ПаттернОписаниеКогда использоватьПример
SaltПрефикс = хеш(key) % NРавномерное распределениеuser_42_12345
HashПрефикс = MD5(key)Полная рандомизацияa3f2_12345
ReverseПеревернуть ключГорячие ключи54321_42
CompositeНесколько полейМногоуровневый доступuser_42_event_123
Time-basedВремя в начале/концеВременные ряды20250101_42

Проектирование: Salt

  • Префикс = хеш(key) % N (N — количество "бакетов")
  • Равномерно распределяет записи по Region'ам
  • Минус: при чтении нужно знать N и перебирать все бакеты

Пример

// Без соли (плохо): все пишут в один Region
user_1, user_2, user_3, ..., user_1000000

// С солью (хорошо): записи распределены
0_user_1, 1_user_2, 0_user_3, ..., 3_user_1000000

Проектирование: Hash

  • Префикс = MD5(key) или другой хеш
  • Полная рандомизация распределения
  • Минус: нельзя делать Range Scan по исходному ключу

Пример

// Исходный ключ: user_42
// Хеш: a3f2c1d4e5b6...
// RowKey: a3f2_user_42

Используется, когда нужен только точечный Get

Проектирование: Reverse

  • Перевернуть ключ (например, user_id -> reversed_user_id)
  • Используется для горячих ключей (последние данные)
  • Позволяет избежать Hotspotting

Пример

// Исходный ключ: user_42
// Reverse: 24_resu
// RowKey: 24_resu

Часто используется для временных рядов: последние события в начале

Проектирование: Антипаттерны RowKey

АнтипаттернПроблемаРешение
Монотонный ключ (timestamp в начале)Все пишут в один Region (Hotspotting)Salt или Hash
Слишком длинный ключЗанимает память в индексах и кэшеХешировать, сокращать
Слишком короткий ключМного коллизий, плохая сортировкаДобавить суффикс
Горячая точка (один пользователь пишет постоянно)Один Region перегруженReverse или Salt
Изменяемая часть ключаНельзя обновить без перезаписиВыносить изменяемое в Qualifier

Проектирование: Hotspotting

  • Все записи попадают в один Region
  • Один RegionServer перегружен, остальные простаивают

Причины

  • Монотонный RowKey (timestamp в начале)
  • Один "горячий" ключ (популярный пользователь)

Решение

  • Salt: распределить записи по разным Region'ам
  • Reverse: для горячих ключей

Проектирование: Column Family

Правила

  • Минимум CF (1–3). Каждый CF = отдельный LSM-Tree
  • Группировка по паттерну доступа: горячие данные отдельно от холодных
  • Разные настройки: TTL, сжатие, in-memory

Пример

CREATE TABLE users (
  profile CF: name, age, email,
  settings CF: theme, lang
) WITH ...

Проектирование: Пример 1 — Лог событий

Требования: читать события пользователя за период, писать много, читать редко

Решение

  • RowKey: reverse(user_id)_timestamp — последние события в начале
  • CF: events (TTL = 30 дней)
  • Qualifier: type, data

Проектирование: Пример 2 — Профиль

Требования: читать по user_id (точечный Get), обновлять часто

Решение

  • RowKey: user_id — прямой доступ
  • CF: profile (горячие), settings (холодные)
  • Версионирование: 3 версии для аудита

Проектирование: Пример 3 — Счетчики

Требования: инкремент на каждый просмотр, чтение агрегата за день

Решение

  • RowKey: date_user — агрегация по дню
  • Использовать Increment — атомарная операция на стороне сервера
  • CF: counters (In-memory = true)

Проектирование: Чек-лист

  1. Определите паттерн чтения: точечный Get или Range Scan?
  2. Определите паттерн записи: равномерный или с горячими точками?
  3. Выберите RowKey: Salt/Hash для распределения, Reverse для горячих ключей
  4. Выберите Column Family: группировка по доступу, TTL
  5. Проверьте на антипаттерны: нет монотонного ключа, нет горячей точки

Специфика HBase

Что отличает HBase от Cassandra и RocksDB

07

Специфика: HDFS

  • HBase хранит данные на HDFS (HFile) — репликация и отказоустойчивость на уровне HDFS
  • RegionServer может упасть — данные остаются в HDFS
  • Минус: лишний сетевой hop (RegionServer -> DataNode)

Cassandra пишет на локальный диск — быстрее, но сложнее консистентность

Специфика: Master и Strong Consistency

  • HMaster управляет Region'ами, но не участвует в пути данных
  • Strong Consistency (CP): читаете всегда свежие данные
  • Cassandra — eventual consistency (AP), настраиваемая через QUORUM

Что это значит на практике

  • HBase проще в эксплуатации (нет repair, нет gossip)
  • Cassandra лучше для multi-DC, где нужна доступность

Итоги

  • HBase — распределенный LSM-Tree поверх HDFS с strong consistency (CP)
  • LSM-Tree — компромисс: быстрая запись, медленное чтение
  • RowKey — самое важное решение при проектировании
  • Column Family — группировка по паттерну доступа
