MergeTree: запись и чтение

INSERT создаёт отсортированные парты.
SELECT выбирает столбцы и диапазоны для чтения.

MergeTree — движок таблиц ClickHouse: он определяет, как данные записываются, хранятся и читаются. При вставках появляются новые отсортированные порции данных, которые затем могут объединяться фоновыми слияниями.

Начнём с запроса к payments: сумма amount для магазина 7. Сначала выберем нужные столбцы, затем рассмотрим блоки обработки. После этого разберём сохранённые данные и индекс, который сокращает диапазоны чтения.

Запрос читает два столбца: shop_id для фильтра и amount для суммы.

Запрос обращается к payments. Из shop_id берётся условие shop_id = 7, из amount — слагаемые. Поля payment_id, user_id, channel и promo в вычислении не участвуют.

Поэтому движок может читать только два столбца: shop_id и amount. Остальные столбцы не нужны ни для фильтрации, ни для вычисления суммы.

Запрос возвращает одно число, но для его вычисления нужно прочитать подходящие значения. Если записи магазина перемешаны с остальными, столбец shop_id придётся просмотреть на большом диапазоне. Сортировка по магазину позволяет расположить эти записи рядом.

Обработка блоков значений

shop_id: [7,   9,   7,   9,   ...]
amount:  [100, 300, 200, 400, ...]
              ↓ shop_id = 7
маска:   [1,   0,   1,   0,   ...]
              ↓ sum(amount)
частичная сумма → объединение → 300

Здесь показан фрагмент данных. Блок обработки содержит значения столбцов для одних и тех же строк.

Операторы передают друг другу блоки: фильтр проверяет строки, затем сумма учитывает подходящие значения.

На рисунке показан фрагмент данных: четыре номера магазина и четыре соответствующие суммы. Условие shop_id = 7 даёт маску [1, 0, 1, 0]. Суммирование учитывает 100 и 200, получая 300 для этого фрагмента.

Такую порцию значений нескольких столбцов для одних и тех же строк называют блоком обработки. Операторы запроса передают блоки дальше: фильтр отбирает позиции, агрегат накапливает сумму. Результаты по нескольким блокам затем объединяются.

Работа блоками сокращает число вызовов и позволяет обрабатывать соседние значения в памяти. Для некоторых операций используются SIMD-инструкции: одна инструкция выполняет действие над несколькими значениями.

Создание таблицы payments

CREATE TABLE payments
(
  payment_id UUID,
  paid_at DateTime64(3, 'UTC'),
  shop_id UInt32, user_id UInt64,
  amount Decimal(18, 2),
  status Enum8('paid' = 1, 'refunded' = 2),
  channel LowCardinality(String),
  promo Nullable(String)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(paid_at)
ORDER BY (shop_id, paid_at, payment_id);

На слайде команда CREATE TABLE, создающая основной журнал payments. В скобках перечислены поля и типы. Поле payment_id идентифицирует событие, paid_at задаёт время, shop_id и user_id — магазин и пользователя. Поле amount содержит сумму, status различает оплату и возврат. Типы разберём после устройства хранения.

ENGINE = MergeTree задаёт движок. Он сохраняет строки отсортированными порциями — партами (parts). ORDER BY определяет порядок внутри каждого парта: магазин, время, идентификатор. Один парт содержит строки одной партиции.

Партиция — группа данных с одинаковым значением PARTITION BY. У нас toYYYYMM(paid_at) возвращает номер месяца: для ноября 2026 года это 202611. Ноябрьские данные попадают в одну партицию, октябрьские — в другую.

PRIMARY KEY здесь не указан отдельно, поэтому совпадает с ORDER BY. По этому ключу строится разреженный индекс; его устройство рассмотрим на следующих слайдах.

Парт (part) — отсортированная порция данных, сохранённая движком.

Партиция — группа данных с одинаковым значением PARTITION BY. В нашем примере это данные одного месяца.

При вставке движок получает блок строк, вычисляет для них значение PARTITION BY и разделяет их по партициям. Внутри каждой записываемой порции строки сортируются по ORDER BY, после чего сохраняется новый парт.

В одном INSERT могут оказаться октябрьские и ноябрьские события. Тогда они не попадут в один парт: партиции разные. Несколько входных блоков также могут дать несколько партов. Поэтому одна команда вставки не равна одному парту.

При обычном добавлении данных существующая история не переписывается целиком. Новые порции сохраняются отдельно; их последующее объединение выполняет механизм слияний.

Гранула — последовательный диапазон строк внутри парта.

Парт содержит сохранённые значения столбцов и структуры для их чтения. Значения записаны в порядке ORDER BY. Строки парта разделены на гранулы — последовательные диапазоны. Первичный индекс хранит значение ключа из первой строки каждой гранулы.

Отдельно находятся отметки (marks): позиции, по которым можно перейти к данным выбранного диапазона в столбце. Файлы также содержат служебную информацию, например число строк и контрольные суммы.

Данные сжимаются блоками байтов. Чтобы получить значения из сжатого блока, его нужно распаковать. Гранула задаёт диапазон строк, а сжатый блок — порцию байтов; их границы могут различаться.

В формате Wide данные столбцов находятся в отдельных файлах. В Compact они собраны в одном файле. Оба формата сохраняют колоночную организацию чтения.

Первичный индекс хранит значение ключа в начале каждой гранулы.

В учебной схеме — 4 строки. Типичный предел index_granularity — 8192 строки.

На схеме гранула содержит четыре последовательные строки. Из первой строки каждой гранулы берётся значение ключа для первичного индекса. Записей индекса поэтому гораздо меньше, чем строк в данных.

Параметр index_granularity ограничивает число строк в грануле; типичное значение — 8192. При включённом ограничении index_granularity_bytes гранула также ограничивается размером данных в байтах. Последняя гранула парта может содержать меньше строк.

Запрос выбирает гранулы, которые могут содержать нужные строки, затем проверяет WHERE на прочитанных значениях. Часть строк выбранной гранулы может не пройти условие.

ClickHouse умеет переносить условия из WHERE в PREWHERE автоматически.

PREWHERE экономит чтение столбцов; первичный индекс сокращает диапазоны-кандидаты.

В запросе к payments нужно вернуть payment_id, amount и promo только для магазина 7 с status = 'paid'. PREWHERE shop_id = 7 позволяет сначала прочитать и проверить shop_id. Затем читаются остальные нужные столбцы, а WHERE проверяет status.

Если в грануле не осталось подходящих строк, данные остальных столбцов этой гранулы можно пропустить. Если подходящие строки есть, читаются содержащие их сжатые блоки. Экономия зависит от того, сколько диапазонов удалось исключить после первого фильтра.

Первичный индекс сокращает набор гранул до чтения. PREWHERE меняет порядок чтения столбцов внутри выбранных диапазонов. ClickHouse умеет автоматически переносить подходящие условия WHERE в PREWHERE; явная запись задаёт такой этап непосредственно в запросе.

PREWHERE: последовательность чтения

Фоновое слияние партов

В парах указаны (shop_id, paid_at). Схема показывает объединение отсортированных строк.

Парт A: (7,12:00), (9,12:15)
Парт B: (7,12:01), (9,14:10)
                    ↓ слияние
Парт C: (7,12:00), (7,12:01),
        (9,12:15), (9,14:10)
  • Новый парт сохраняет порядок ORDER BY.
  • Слияние выполняется внутри одной партиции.
  • Меньше партов — меньше накладных расходов чтения.

На схеме два парта одной месячной партиции. В каждом строки отсортированы по магазину и времени. Слияние читает оба парта и записывает новый: две записи магазина 7 идут перед двумя записями магазина 9.

Новый парт становится активным вместо исходных. Старые файлы удаляются позднее, когда они больше не нужны запросам. Количество активных партов уменьшается, а набор строк обычного MergeTree сохраняется.

Фоновый планировщик выбирает слияния с учётом размеров и доступных ресурсов. В одной партиции может остаться несколько партов. Принудительное слияние рассмотрим отдельно при подготовке опыта.

Повторная запись оплаты может увеличить сумму отчёта. PRIMARY KEY этого не предотвращает.

PRIMARY KEY в обычном MergeTree задаёт разреженный индекс. Ограничения уникальности строки он не создаёт. Поэтому две записи с одинаковым payment_id могут присутствовать одновременно.

Если событие A на 100 рублей записать дважды, обычное фоновое слияние сохранит обе строки. Последующее суммирование может учесть обе. Чтобы исключить повторный учёт события, нужен отдельный механизм обработки повторов.

В сегодняшнем наборе каждая запись добавлена один раз. На следующей лекции сравним повторную доставку и исправление уже известного события.

Три похожих ключа — три разных решения

ORDER BY · PRIMARY KEY · PARTITION BY

Теперь отдельно разберём три выражения из CREATE TABLE: ORDER BY, PRIMARY KEY и PARTITION BY. Они задают порядок строк, содержание первичного индекса и разделение данных на партиции.

После этого сравним две нагрузки: запрос одного магазина за период и запрос всех магазинов за короткий интервал. Для них удобно разное расположение строк.

Что задаёт каждый ключ

ORDER BY в CREATE TABLE задаёт физическую сортировку внутри каждого парта. PRIMARY KEY задаёт выражения, значения которых записываются в первичный индекс. PARTITION BY разделяет строки по партициям; парты разных партиций не сливаются.

Когда PRIMARY KEY опущен, индекс строится по ключу ORDER BY. Отдельное определение позволяет сделать индекс короче ключа сортировки — такой пример разберём через несколько слайдов.

ORDER BY в SELECT задаёт другой порядок: порядок результата запроса. Чтение нескольких отсортированных партов параллельно не гарантирует порядок вывода. Поэтому для двух крупнейших платежей запросу понадобится свой ORDER BY amount DESC.

Если задано только время, оно встречается в отдельных группах каждого магазина. Движок всё ещё может анализировать условие, но эффективность отсечения зависит от числа магазинов и расположения временных границ.

PARTITION BY toYYYYMM(paid_at)

В одной таблице на одном узле может находиться много партиций.

В основной payments значение toYYYYMM(paid_at) определяет месячную партицию. Все октябрьские парты относятся к 202610, ноябрьские — к 202611. Запрос за ноябрь может исключить октябрьскую группу.

Внутри ноябрьской партиции остаются отдельные парты, каждый со своим индексом. Чтобы выбрать один час магазина 7, нужны условия по ключу внутри этих партов.

Разделение по месяцу также задаёт границы слияния: октябрьские парты не объединяются с ноябрьскими. Если сделать PARTITION BY уникальным payment_id, получится множество маленьких партиций, которые не смогут сливаться друг с другом.

Перейдём от расположения строк к представлению значений. В памяти числовой столбец — массив чисел, строковый — байты и смещения, LowCardinality — словарь и коды. Сериализация превращает эти структуры в последовательности байтов для хранения. Кодеки преобразуют и сжимают полученные байты.

При делении Decimal дробные разряды за пределами масштаба результата отсекаются. Если отчёт требует округления, его нужно задать отдельным выражением. Поэтому фиксированное представление суммы и правило округления расчёта задаются отдельно.

Схема String соответствует сериализации версии 24.12; пробелы между байтами добавлены для чтения.

В памяти String хранит общий массив байтов строк и массив смещений. В версии 24.12 после каждой строки в этом массиве находится завершающий нулевой байт. Для строк web и app байты имеют вид web\0app\0, а смещения конца строк равны 4 и 8.

При обычной сериализации в парт для каждой строки записывается длина VarUInt, затем её байты. VarUInt — целое переменной длины: значения меньше 128 помещаются в один байт. Маска — байт на строку, не бит. Значения и маска сжимаются отдельно.

Nullable(T) состоит из вложенного столбца T и NULL-маски UInt8 той же длины. Для каждой строки маска содержит 0, если значение известно, и 1 для NULL. Это один байт на строку до сжатия, а не один бит.

Например, значения 10, NULL, 20 для Nullable(UInt32) можно представить как массив UInt32 с заглушкой на месте NULL и маску [0, 1, 0]. Значение заглушки игнорируется: смысл пропуска задаёт маска. Сериализация записывает маску и вложенные значения отдельно; оба набора данных затем сжимаются.

В layout_demo столбец id32 содержит 100 тысяч UInt32 и занимает 400 тысяч байт до сжатия. Пропущенная позиция не удаляется из вложенного столбца.

Для promo вложенный тип — String. Пустая строка имеет длину ноль при нулевой маске NULL. Неизвестный промокод отмечен единицей в маске. Поэтому NULL и пустая строка различаются физически, а агрегаты и фильтры должны учитывать маску.

Nullable: хранение маски

COUNT зависит от того, что считаем

SELECT count() AS rows,
       count(promo) AS known,
       countIf(promo = '') AS empty,
       countIf(isNull(promo)) AS missing
FROM payments;
rows  known  empty  missing
6     3      1      3

count() считает строки, count(promo) — значения без NULL.

Для проверки пропуска пишем isNull(promo), а не promo = NULL.

Возвращаемся к payments с шестью событиями. У B и F промокод SALE, у D — пустая строка, у A, C и E — NULL. Запрос на слайде вычисляет четыре счётчика над этим столбцом.

count() возвращает число строк: 6. count(promo) пропускает NULL, но учитывает SALE и пустую строку, поэтому возвращает 3. countIf(promo = '') находит строку D и возвращает 1. countIf(isNull(promo)) находит A, C и E и возвращает 3.

Функция isNull проверяет NULL-маску. Обычное сравнение promo = NULL не заменяет эту операцию: при сравнении с NULL результат сам равен NULL и не считается истинным условием.

Несколько условий в одном GROUP BY

SELECT shop_id,
  sumIf(amount, status = 'paid') AS paid,
  sumIf(amount, status = 'refunded') AS refunded,
  countIf(status = 'paid') AS payments_count
FROM payments
GROUP BY shop_id
ORDER BY shop_id;

-If — комбинатор: агрегат принимает дополнительное условие.

Общий фильтр WHERE status = 'paid' убрал бы возвраты до вычисления всех агрегатов.

Для каждого shop_id нужны три показателя: сумма оплат, сумма возвратов и число оплат. sumIf(amount, status = 'paid') прибавляет amount только для строк paid. Второй sumIf делает то же для refunded. countIf считает строки paid.

Суффикс -If называется комбинатором. Он добавляет к агрегату условие отбора строк. Поэтому несколько агрегатов одного GROUP BY могут получать разные подмножества общего входа.

Если вынести status = 'paid' в WHERE, строки refunded исчезнут до вычисления всех трёх агрегатов. Сумма возвратов станет нулевой. В этом запросе оба статуса оставляем на входе, а условие задаём каждому показателю отдельно.

uniq и uniqExact: память и точность

SELECT shop_id,
  uniq(user_id) AS buyers_estimate,
  uniqExact(user_id) AS buyers_exact
FROM payments
WHERE status = 'paid'
GROUP BY shop_id
ORDER BY shop_id;
shop_id  buyers_estimate  buyers_exact
7        2                2
9        1                1

uniqExact хранит точное множество; uniq оценивает количество по выборке хешей.

После WHERE status = 'paid' у магазина 7 остаются пользователи 101 и 102, у магазина 9 — два платежа пользователя 103. Поэтому точное число покупателей равно 2 и 1, хотя оплат в каждом магазине две.

Агрегат uniqExact хранит точное множество различных значений; его состояние растёт с числом покупателей в каждой группе. Агрегат uniq использует адаптивную выборку хешей, до 65 536 элементов в состоянии, и оценивает число различных значений.

В нашем маленьком наборе оба агрегата вернули одинаковые 2 и 1. На большом наборе uniq может дать приближённый ответ. Выбор между ними определяет одновременно допустимую погрешность и расход памяти, особенно при большом числе групп.

Атрибуты последней записи: argMax

SELECT shop_id,
  argMax(tuple(user_id, amount, status),
         tuple(paid_at, payment_id)) AS last_payment
FROM payments
GROUP BY shop_id
ORDER BY shop_id;

argMax(arg, val) возвращает arg для максимального val.

Первый кортеж — возвращаемые поля, второй — критерий выбора.

Тот же выбор можно записать через ROW_NUMBER() и фильтр rn = 1. Сравнение — в demo.sql.

Функция argMax возвращает поля строки с максимальным критерием. В payments выбираем последнюю запись каждого магазина. Возвращаемый кортеж содержит user_id, amount и status, критерий — (paid_at, payment_id). Сначала сравнивается время, при равенстве — идентификатор.

Этот выбор можно записать через оконную функцию row_number(): разбить строки по shop_id, упорядочить внутри магазина по paid_at DESC, payment_id DESC, затем во внешнем запросе оставить rn = 1. Полный вариант находится рядом с argMax в demo.sql. На наших данных оба запроса возвращают одинаковые записи C и F.

ArgMax выражает эту операцию одним агрегатом в GROUP BY. При чтении он сохраняет лучшего кандидата для каждой группы: критерий и связанные с ним поля. Частичные результаты можно объединять, поэтому для выбора кандидата не требуется сортировать все исходные платежи по времени.

Здесь выбирается последняя запись по paid_at, а не по моменту загрузки. Строки paid и refunded участвуют вместе: фильтра по статусу нет. В следующем примере проверим совпадающее время, затем — NULL в возвращаемом поле.

argMax

Как выбрать последнюю запись при равном времени

shop_id  last_payment
7        (101,  50.00, 'refunded')
9        (104, 150.00, 'refunded')

У E и F одно время. При сравнении (paid_at, payment_id) выбран F: его payment_id больше.

При одинаковом максимальном val выбор argMax не определён однозначно.

Здесь при равном времени выбирается больший payment_id. Для порядка исправлений понадобится версия источника.

В магазине 9 у E и F одно время — 14:10:00. Если val содержит только paid_at, обе строки дают одинаковый максимум. При таком совпадении argMax может вернуть атрибуты любой из них.

В запросе добавлен payment_id. В нашем наборе идентификатор F больше идентификатора E, поэтому выбран F: пользователь 104, сумма 150, статус refunded. Это воспроизводимое правило для данных с разными ID.

Если источник задаёт порядок исправлений версией, в критерий выбора нужно включить эту версию. Сравнение UUID само по себе не сообщает, какое событие произошло позже; в этом примере оно только разрешает равенство времени.

В первом возвращаемый аргумент — promo. Строка с NULL в этом аргументе пропускается, поэтому получается SALE из B: последний известный промокод.

Во втором возвращаемый аргумент — tuple(promo). Кортеж с одним NULL-элементом сам не является NULL, поэтому строка C участвует в выборе. Возвращается (NULL): значение промокода именно последней строки.

Часовые интервалы задаём явно

SELECT
  toStartOfInterval(
    paid_at, INTERVAL 1 HOUR, 'UTC') AS hour,
  sum(amount) AS revenue
FROM payments
WHERE shop_id = 7 AND status = 'paid'
  AND paid_at >= toDateTime64(
    '2026-11-20 12:00:00', 3, 'UTC')
  AND paid_at < toDateTime64(
    '2026-11-20 15:00:00', 3, 'UTC')
GROUP BY hour;

После фильтра остаются A и B. Результат GROUP BY: одна строка 12:00 → 300 ₽.

В payments выбираем магазин 7, статус paid и период [12:00, 15:00) 20 ноября. Функция toStartOfInterval с шагом INTERVAL 1 HOUR и часовым поясом UTC возвращает начало часа. A и B попадают в одну группу 12:00, сумма равна 300.

Начало периода включено, конец исключён: запись ровно в 15:00 уже относится к следующему периоду. Такой фильтр позволяет считать соседние интервалы без повторного учёта граничной записи.

В 13 часов оплат нет; в 14 часов есть только возврат C, который исключён фильтром. Поэтому после GROUP BY остаётся одна строка 12:00. Для графика с тремя часами добавим недостающие строки следующим шагом.

toStartOfInterval

WITH FILL: добавить пропущенные часы

К предыдущему запросу после GROUP BY hour добавляем:

ORDER BY hour WITH FILL
  FROM toDateTime('2026-11-20 12:00:00', 'UTC')
  TO   toDateTime('2026-11-20 15:00:00', 'UTC')
  STEP INTERVAL 1 HOUR;
hour                 revenue
2026-11-20 12:00:00   300.00
2026-11-20 13:00:00     0.00
2026-11-20 14:00:00     0.00

При заполнении граница FROM включается, TO исключается. Остальные поля получают значения по умолчанию.

К предыдущему запросу после GROUP BY hour добавляем ORDER BY hour WITH FILL. FROM задаёт 12:00 включительно, TO — 15:00 исключительно, STEP — один час. Заполнение создаёт позиции 12:00, 13:00 и 14:00.

Строка 12:00 уже содержит сумму 300. Для созданных строк 13:00 и 14:00 поле revenue получает значение по умолчанию своего типа Decimal — ноль. После заполнения результат состоит из трёх строк.

Фильтр WHERE за период остаётся в запросе: FROM и TO управляют генерацией пропущенных значений, но не удаляют существующие строки вне диапазона. Этот пример строит шкалу для одного магазина; для отчёта по всем магазинам сначала потребуется задать нужные сочетания магазинов и часов.

WITH FILL не отличает отсутствие оплат от задержки их загрузки.

Поздняя оплата может изменить ранее показанный ноль.

В нашем завершённом наборе данных за 13 часов у магазина 7 нет оплат. Созданный WITH FILL ноль соответствует этому набору: мы знаем, что все шесть строк загружены.

При работающем источнике пропуск часа может означать задержку загрузки. WITH FILL всё равно добавит ноль, хотя оплаты ещё могут поступить. По одному результату GROUP BY эти ситуации не различить.

Для отчёта нужны сведения о завершённости загрузки периода. Это связано со временем событий из прошлой лекции: полученная позднее оплата может изменить сумму за прошедший час.

Напишите запрос к payments: для магазина 7 посчитайте сумму успешных оплат и точное число покупателей по часам и каналам. Период — [12:00, 15:00) UTC 20 ноября. Пустые часы добавлять не нужно.

Рассчитаем ответ по событиям. A — 100 рублей, пользователь 101, web; B — 200 рублей, пользователь 102, app. Обе оплаты относятся к 12 часам. Значит, ожидаются две группы: web — 100 и один покупатель, app — 200 и один покупатель.

Дополнительный вопрос: можно ли складывать числа уникальных покупателей по каналам? В общем случае нет: один пользователь может присутствовать в обоих каналах. Для общего числа за час нужен отдельный расчёт по множеству пользователей этого часа.

Ответ: фильтр → группы → агрегаты

SELECT
  toStartOfInterval(
    paid_at, INTERVAL 1 HOUR, 'UTC') AS hour,
  channel, sum(amount) AS revenue,
  uniqExact(user_id) AS buyers
FROM payments
WHERE shop_id = 7 AND status = 'paid'
  AND paid_at >= toDateTime64(
    '2026-11-20 12:00:00', 3, 'UTC')
  AND paid_at < toDateTime64(
    '2026-11-20 15:00:00', 3, 'UTC')
GROUP BY hour, channel
ORDER BY hour, channel;

WHERE оставляет магазин 7, строки paid и нужный период. Функция toStartOfInterval вычисляет начало часа, GROUP BY hour, channel создаёт группы по паре «час, канал». sum(amount) считает сумму, uniqExact(user_id) — точное число покупателей в каждой группе.

ORDER BY hour, channel даёт сначала app — 200 рублей и один покупатель, затем web — 100 рублей и один покупатель. Событие C исключено условием по статусу, поэтому группы для 14 часов нет.

LowCardinality хранит channel через словарь, но выражение GROUP BY channel остаётся обычным. Отдельного индекса по channel этот тип не создаёт; отбор по магазину и времени опирается на ключ таблицы.

Что связывает хранение и SQL

  • Колоночное выполнение сокращает работу с ненужными полями.
  • Сортировка и индекс сокращают диапазоны чтения.
  • Партиции позволяют управлять группами партов.
  • Типы задают двоичное представление; кодеки преобразуют и сжимают байты.
  • Фильтры и агрегаты определяют, какие события попадут в показатель.

Проверены три опыта: сортировки, короткий индекс, типы и кодеки.

В MergeTree вставка создаёт отсортированные парты. Каждый парт имеет первичный индекс по началам гранул и marks для перехода к данным столбцов. Фоновые слияния объединяют парты внутри одной партиции.

В опыте с двумя порядками один запрос выбрал 2 или 57 гранул при одинаковой сумме. В опыте с типами ширина значения, словарные коды и цепочка кодеков определили размеры столбцов.

В аналитическом SQL результат зависит от входных строк и выбранных операций. Мы отдельно проверили условные суммы, уникальных покупателей, совпадающее время в argMax, NULL и заполнение часов.
