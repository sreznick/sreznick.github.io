Inline

Функция принимает лямбду

  • При обычной передаче лямбды в байткоде остаётся вызов функции. Способ представления лямбды зависит от компилятора.
fun regular(x: Int, block: (Int) -> Int): Int = block(x)
inline fun inlined(x: Int, block: (Int) -> Int): Int = block(x)

fun useRegular() = regular(4) { it + 1 }
fun useInline() = inlined(4) { it + 1 }

Inline

Что подставляется в место вызова

  • При прямом вызове inline-функции компилятор встраивает её тело и тело переданной лямбды.
  • В useInline арифметические операции выполняются прямо в вызывающем методе.
// Исходный вызов
val result = inlined(4) { it + 1 }

// Смысл преобразования; не буквальный байткод

val result = x + 1

Inline и JIT работают на разных этапах

Когда встраивание имеет смысл

  • Встраивание небольших функций высшего порядка может сократить расходы на создание и вызов лямбд.
  • Встраивание увеличивает объём кода в местах вызова.
  • Inline позволяет использовать reified и возвращаться из внешней функции внутри лямбды.

Возвраты

Возврат из внешней функции

  • Лямбда, переданная inline-параметру без noinline и crossinline, может завершить внешнюю именованную функцию.
  • В примере return true завершает hasError.
fun hasError(lines: List<String>): Boolean {
    lines.forEach { line ->
        if (line.startsWith("ERROR")) return true
    }
    return false
}
17–24 минуты. Проследить управление на входе без ошибки и с ошибкой в середине.

Возвраты

Метка задаёт локальный выход

  • return@forEach завершает текущий вызов лямбды.
  • Перебор продолжится со следующим элементом; внешняя функция продолжит работу.
fun printNonEmpty(lines: List<String>) {
    lines.forEach { line ->
        if (line.isEmpty()) return@forEach
        println(line)
    }
    println("Обработка завершена")
}
Теоретическая опора к практическому блоку «Возвраты».

Возвраты

Анонимная функция имеет свой return

  • return без метки внутри fun(...) завершает саму анонимную функцию.
fun printNonEmpty(lines: List<String>) {
    lines.forEach(fun(line: String) {
        if (line.isEmpty()) return
        println(line)
    })
    println("Обработка завершена")
}

Параметры inline

Почему обычный inline-параметр нельзя сохранить

  • Лямбда обычного inline-параметра может содержать выход из внешней функции.
  • Сохранённую функцию можно вызвать позже, когда внешняя функция уже завершилась. Для хранения нужен модификатор noinline.
val callbacks = mutableListOf<() -> Unit>()

// Не компилируется: недопустимое использование block
inline fun remember(block: () -> Unit) {
    callbacks.add(block)
}
35–44 минуты. Этот фрагмент намеренно не компилируется.

Параметры inline

noinline оставляет функцию значением

  • Параметр можно сохранить, вернуть и передать обычной функции.
  • Нелокальный return из такой лямбды запрещён.
inline fun register(
    name: String,
    noinline callback: () -> Unit,
    log: (String) -> Unit
) {
    log("register: $name")
    callbacks.add(callback)
}
Теоретическая опора к практическому блоку «Параметры inline».

Параметры inline

crossinline: вызов через обёртку

  • Переданная лямбда вызывается из метода другого объекта.
  • crossinline запрещает нелокальный возврат; локальный return с меткой разрешён.
inline fun task(crossinline block: () -> Unit): Runnable =
    Runnable { block() }

fun demo() {
    val work = task { println("Работа") }
    work.run()
}
Теоретическая опора к практическому блоку «Параметры inline».

Параметры inline

Как выбрать модификатор параметра

  • Обычный inline-параметр: вызываем лямбду напрямую или передаём другому inline-параметру с совместимыми ограничениями.
  • noinline: сохраняем или возвращаем саму функцию как значение.
  • crossinline: вызываем лямбду через обёртку и запрещаем выход из внешней функции.

Reified

Какой тип доступен во время выполнения

  • Компилятор проверяет использование T, но после компиляции конкретный аргумент типа обычно недоступен в теле generic-функции.
  • Поэтому T::class и value is T недоступны для обычного параметра типа.
// Оба объявления намеренно не компилируются
fun <T : Any> klass() = T::class
fun <T> matches(value: Any?): Boolean = value is T
Теоретическая опора к практическому блоку «Reified».

Reified

Класс можно передать параметром

  • KClass представляет класс и может быть обычным параметром функции.
import kotlin.reflect.KClass
import kotlin.reflect.full.primaryConstructor

fun <T : Any> construct(type: KClass<T>): T =
    requireNotNull(type.primaryConstructor).callBy(emptyMap())

data class Event(val service: String = "unknown")
val event = construct(Event::class)
55–64 минуты. Для этого примера нужен kotlin-reflect. Условие: primary constructor существует, все его параметры optional. Это небольшой пример над уже изученным API, а не универсальная фабрика.

Reified

Обёртка с reified

  • В прямом inline-вызове компилятор знает конкретный аргумент типа.
  • Обёртка передаёт KClass обычной функции; рефлексия внутри неё остаётся.
inline fun <reified T : Any> construct(): T =
    construct(T::class)

val event = construct<Event>()
// После встраивания по смыслу:
// construct(Event::class)
Теоретическая опора к практическому блоку «Reified».

Reified

Как вызвать обёртку из generic-функции

  • Обычный параметр T вызывающей функции нельзя передать как reified-аргумент.
  • Можно передать KClass явно или объявить вызывающую функцию inline с reified-параметром.
// Не компилируется
fun <T : Any> make(): T = construct<T>()

// Работает с явным описанием
fun <T : Any> make(type: KClass<T>): T = construct(type)

inline fun <reified T : Any> make(): T = construct<T>()

Reified

Проверка внешнего типа

  • При T = List<String> выражение value is T проверяет, что value — список.
  • Типы элементов при этом не проверяются: reified не восстанавливает аргумент типа из объекта списка.
inline fun <reified T> matches(value: Any?): Boolean =
    value is T

matches<String>(42)                  // false
matches<List<String>>(listOf(1, 2))   // true

Reified

Когда возникнет ошибка приведения

  • Приведение списка к List<String> не проверяет его элементы.
  • При чтении элемента как String JVM выполняет приведение самого элемента.
val value: Any = listOf(1, 2)
@Suppress("UNCHECKED_CAST")
val strings = value as List<String>
println(strings.first().length) // ClassCastException
Теоретическая опора к практическому блоку «Reified».

Reified

Описание типа и проверка данных

  • typeOf описывает указанный тип вместе с его аргументами. Содержимое value при этом не проверяется.
  • Для проверки элементов нужен обход. Для пустого списка all возвращает true, но это ничего не говорит об исходном аргументе типа.
import kotlin.reflect.typeOf

typeOf<List<String>>() != typeOf<List<Int>>() // true

fun containsOnlyStrings(value: Any?): Boolean =
    value is List<*> && value.all { it is String }

Параллелизм и ожидание

Что ограничивает скорость программы

  • Вычисления ограничены доступными ядрами: увеличение числа задач не добавляет вычислительных ресурсов.
  • При вводе-выводе задача может большую часть времени ждать сеть или диск.
  • Для вычислений важна загрузка ядер; для множества ожидающих операций — стоимость ожидания.
Различить CPU-bound и I/O-bound на примере обработки и загрузки логов. Параллельное чтение может сократить общее время независимых запросов, но не ускоряет арифметику каждого запроса.

Потоки JVM

Платформенный поток

  • Платформенный java.lang.Thread связан с потоком операционной системы.
  • Каждый такой поток требует стека и ресурсов ОС. Создавать по потоку на каждый из тысяч запросов затратно.
  • Блокирующее ожидание занимает поток, даже если он в этот момент не выполняет вычислений.
Платформенные потоки JVM → потоки ОС → ядра процессора
Контекст: https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html . Уточнение про блокировку здесь относится к платформенным потокам; виртуальные потоки разберём отдельно.

Пулы и задачи

ExecutorService: задача отдельно от потока

  • Приложение передаёт задачи пулу, а пул распределяет их по рабочим потокам.
  • Future представляет будущий результат; get блокирует вызывающий поток, пока результат не готов.
  • Если все рабочие потоки заняты блокирующими операциями, новые задачи ждут в очереди.
val pool = Executors.newFixedThreadPool(2)
try {
    val a = pool.submit(Callable { readBlocking("A") })
    val b = pool.submit(Callable { readBlocking("B") })
    println(a.get() + b.get())
} finally {
    pool.shutdown()
}
Импорты java.util.concurrent.Callable и Executors. readBlocking — условное блокирующее чтение, возвращающее String. Запускаем оба submit до первого get. Источник: https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ExecutorService.html .

Композиция задач

CompletableFuture: продолжение по готовности

  • Продолжения задают, что сделать с результатом: thenApply, thenCompose, thenCombine.
  • Сборку следующего этапа можно описать без get между этапами.
  • Потоки и блокирующие вызовы остаются: supplyAsync переносит операцию в executor, а не меняет её реализацию.
val a = CompletableFuture.supplyAsync({ readBlocking("A") }, pool)
val b = CompletableFuture.supplyAsync({ readBlocking("B") }, pool)
val combined = a.thenCombine(b) { x, y -> x + y }
combined.thenAccept { println(it) }
Фрагмент использует открытый executor pool из предыдущего примера. Не назначать thenCombine отдельный поток: без Async продолжение может исполняться потоком, завершившим этап. Источник: https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CompletableFuture.html .

Асинхронный ввод-вывод

Ожидать данные без выделенного потока на запрос

  • Неблокирующие сетевые API позволяют обслуживать много ожидающих операций небольшим числом потоков.
  • Готовность данных запускает продолжение: через обработчик, future или возобновление корутины.
  • Сложность переносится в композицию операций: зависимости результатов, обработку ошибок и отмену.
запрос → регистрация ожидания → поток свободен
готовность данных → продолжение обработки
Речь о неблокирующей реализации ввода-вывода. Callback или Future сами по себе не гарантируют, что внутри нет блокирующего вызова.

Виртуальные потоки

Java 21: виртуальный поток на задачу

  • Виртуальные потоки — экземпляры Thread, которые JVM планирует на платформенных потоках.
  • При поддерживаемом блокирующем ожидании JVM может освободить несущий поток для других задач.
  • Они удобны для большого числа ожидающих операций с обычным блокирующим кодом. Вычислительный параллелизм по-прежнему ограничен ядрами.
Executors.newVirtualThreadPerTaskExecutor().use { executor ->
    val a = executor.submit(Callable { readBlocking("A") })
    val b = executor.submit(Callable { readBlocking("B") })
    println(a.get() + b.get())
}
Java 21. Не утверждать, что любой блокирующий вызов освобождает несущий поток: есть ограничения, зависящие от операции и версии JDK. Виртуальные потоки не являются пулом корутин. Источник: https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html .

Корутины на JVM

Корутина — приостанавливаемая задача

  • Корутины исполняются на JVM-потоках; диспетчер определяет, на каких именно.
  • При приостановке ожидание хранится как продолжение, а поток может выполнять другую работу.
  • В Kotlin последовательный suspend-код сочетается с деревом задач: родитель ждёт дочерние задачи и участвует в их отмене.
Корутины → диспетчер → потоки JVM → ядра процессора
Это библиотечная модель задач и приостановок, а не виртуальные потоки Java. suspend сам не делает блокирующий API неблокирующим. Источник: https://kotlinlang.org/docs/coroutines-basics.html .

Место корутин

Разные средства решают разные задачи

  • Executor и диспетчер управляют исполнением; Future и Deferred представляют будущий результат.
  • Виртуальные потоки снижают стоимость ожидания в блокирующем коде; корутины дают явные точки приостановки и структуру дочерних задач.
  • Выбор зависит от используемых API, характера нагрузки и требований к времени жизни задач.
ЗадачаСредства
Распределить работу по потокамExecutor, диспетчер
Собрать зависимые результатыCompletableFuture, async/await

Не представлять эти средства как линейную смену поколений. На JVM они сосуществуют; корутины также могут адаптировать блокирующие операции через IO. Далее перейти к двум источникам и практикуму.

  • Нужно дождаться результатов и понимать, кому принадлежат запущенные задачи.
  • Вызов delay имитирует ожидание данных от источника.

Модель выполнения

Конкурентность и параллелизм

  • При конкурентном выполнении несколько задач начаты и ещё не завершены. Они могут работать по очереди.
  • При параллельном выполнении несколько участков кода исполняются одновременно, например на разных ядрах процессора.
  • На одном потоке корутины могут чередоваться при приостановках.

Модель выполнения

Блокировка и приостановка

  • Thread.sleep удерживает текущий поток в ожидании.
  • delay приостанавливает корутину, освобождая поток для другой работы.
  • Пока корутина выполняет вычисления, она занимает поток. Другая корутина сможет использовать его после приостановки или завершения текущей.
Теоретическая опора к практическому блоку «Модель выполнения».

Suspend

Что означает suspend

  • Функция может вызывать приостанавливающие функции.
  • Вызов сам по себе не создаёт корутину и не выбирает другой поток.
  • Функция может завершиться без фактической приостановки.
suspend fun readSource(name: String): String {
    println("start $name")
    delay(300)
    println("end $name")
    return "data:$name"
}

Запуск примеров

Граница обычного и suspend-кода

  • Библиотека kotlinx.coroutines предоставляет основные средства работы с корутинами и подключается отдельно.
  • runBlocking блокирует вызывающий поток до завершения своего блока и дочерних задач.
  • Встроенный цикл обработки событий позволяет выполнять корутины на этом же потоке.
import kotlinx.coroutines.*

fun main() = runBlocking {

}

start B
end B
data:A; data:B
8–19 минут: задание 5. Предсказать журнал нескольких последовательных suspend-вызовов. Попросить объяснить, где именно могла выполняться другая задача.

Launch

Запуск дочерней задачи

  • launch — расширение CoroutineScope; запускает корутину и возвращает Job.
  • Job описывает время жизни задачи, но не её возвращаемое значение.
  • Если диспетчер не указан явно, новая задача наследует его от своего scope.
fun main() = runBlocking {
    val a: Job = launch { readSource("A") }
    val b: Job = launch { readSource("B") }
    a.join()
    b.join()
    println("Все завершены")
}
19–28 минут. Обратить внимание: readSource возвращает String, но launch не предоставляет его как результат.

Launch

Что гарантирует join

  • join приостанавливает ожидающую корутину до завершения Job.
  • После двух join обе задачи завершены. Пока мы ждём первую, вторая может продолжать работу.
  • join не возвращает результат задачи. Для получения результата или ошибки через await используем Deferred.
Теоретическая опора к практическому блоку «Launch».

Порядок событий

Какие события должны идти по порядку

  • Для каждого источника start предшествует end.
  • «Все завершены» должно идти после завершения обеих задач.
  • Порядок событий разных источников может меняться. Проверяем только необходимые зависимости.
start A ─────→ end A ──┐
                      ├──→ Все завершены
start B ─────→ end B ──┘
28–40 минут: задание 6. Три операции и завершающее событие; проверить необходимые отношения порядка, а не единственную строку журнала.

Async

Задача с возвращаемым значением

  • async запускает дочернюю корутину и возвращает Deferred<T>.
  • await дожидается завершения задачи и возвращает значение типа T. Если задача завершилась с ошибкой, await бросает исключение.
fun main() = runBlocking {
    val a: Deferred<String> = async { readSource("A") }
    val b: Deferred<String> = async { readSource("B") }
    println("${a.await()}; ${b.await()}")
}
40–49 минут. Оба async вызваны до первого await.

Async

Сначала запускаем задачи, затем ждём результаты

  • В первом варианте B ещё не запущен, пока ожидается A.
  • Во втором обе задачи запущены до ожидания результатов.
val a = async { readSource("A") }.await()
val b = async { readSource("B") }.await()

// Конкурентный вариант
val pendingA = async { readSource("A") }
val pendingB = async { readSource("B") }
val combined = pendingA.await() to pendingB.await()
Теоретическая опора к практическому блоку «Async».

Scope

Suspend-функции нужен scope для дочерних задач

  • У suspend-функции нет неявного получателя CoroutineScope, необходимого для вызова launch и async.
  • coroutineScope предоставляет scope и ожидает своих дочерних задач.
  • Функция возвращает результат после завершения своего блока и всех дочерних задач.
data class Summary(val a: String, val b: String)

suspend fun loadSummary(): Summary = coroutineScope {
    val a = async { readSource("A") }
    val b = async { readSource("B") }
    Summary(a.await(), b.await())
}
49–61 минута: задание 7. Реализовать loadSummary из заготовки. Не создавать новый самостоятельный CoroutineScope и не использовать GlobalScope.

Scope

Дерево задач задаёт время жизни

  • runBlocking ждёт loadSummary.
  • coroutineScope внутри loadSummary ждёт обе дочерние задачи.
  • Тело родительской задачи может закончиться раньше дочерних задач. Сама родительская задача завершится после них.
runBlocking
└── loadSummary / coroutineScope
    ├── async: источник A
    └── async: источник B
Теоретическая опора к практическому блоку «Scope».

Scope

Функция ждёт свои дочерние задачи

  • После возврата из loadSummary оба чтения завершены и результат готов.
  • Если дочерняя задача в coroutineScope завершается с ошибкой, остальные дочерние задачи отменяются, а ошибка передаётся вызывающему.
  • Перед выходом coroutineScope ждёт завершения всех дочерних задач, в том числе отменённых.
Теоретическая опора к практическому блоку «Scope».

Диспетчеры

Время жизни задач и место выполнения

  • Scope задаёт контекст запуска и связь со временем жизни родителя.
  • Диспетчер определяет, на каких потоках выполняется корутина.
  • Смена диспетчера сохраняет связь задачи с родителем.
Теоретическая опора к практическому блоку «Диспетчеры».

Диспетчеры

Где выполняется код

  • Dispatchers.Default предназначен для вычислительной работы.
  • Dispatchers.IO предназначен для блокирующих операций ввода-вывода на JVM.
  • Если не передать диспетчер в launch или async, он наследуется от scope. Это не обязательно Dispatchers.Default.
Теоретическая опора к практическому блоку «Диспетчеры».

Блокирующий код

suspend не изменяет Thread.sleep

  • Этот вызов всё ещё блокирует поток, на котором выполняется slowRead.
  • Во время sleep другие корутины на этом потоке не смогут продолжить работу.
suspend fun slowRead(): String {
    Thread.sleep(600)
    return "data"
}
61–70 минут. Сопоставить с readSource, использующим delay.

Блокирующий код

Наблюдение на одном потоке

  • Дочерняя корутина ticker и тело runBlocking используют один поток.
  • yield позволяет задаче ticker начать работу до вызова Thread.sleep.
  • Заменим Thread.sleep на delay и сравним, когда появляются сообщения tick.
fun main() = runBlocking {
    val ticker = launch {
        repeat(5) {
            println("tick $it")
            delay(100)
        }
    }
    yield()
    Thread.sleep(600) // затем заменить на delay(600)
    ticker.join()
}
Теоретическая опора к практическому блоку «Блокирующий код».

WithContext

Перенос блокирующего участка

  • withContext выполняет блок в заданном контексте и возвращает его результат.
  • Пока поток диспетчера IO занят блокирующим вызовом, вызывающая корутина ждёт, не занимая свой поток.
  • IO не превращает блокирующее чтение в неблокирующее.
suspend fun slowRead(): String =
    withContext(Dispatchers.IO) {
        Thread.sleep(600)
        "data"
    }
70–81 минута: задание 8. Перенести готовое блокирующее чтение, сохранив suspend-интерфейс; запустить рядом ticker. Обсудить границы участка, который действительно нужно переносить.

WithContext

Что перенос на IO не гарантирует

  • Потоки диспетчера IO не бесконечны: число одновременных блокирующих операций нужно контролировать.
  • Если suspend-функция уже использует неблокирующий ввод-вывод, переносить её на IO обычно не требуется.
  • Отмена корутины сама по себе не гарантирует прерывания произвольного блокирующего API.
Теоретическая опора к практическому блоку «WithContext».

Время жизни

Завершение блока и завершение scope

  • Последняя строка тела runBlocking может выполниться раньше дочерней задачи.
  • Но сам runBlocking вернётся только после её завершения.
fun main() {
    runBlocking {
        launch { delay(100); println("child done") }
        println("body done")
    }
    println("scope done")
}
// body done → child done → scope done
