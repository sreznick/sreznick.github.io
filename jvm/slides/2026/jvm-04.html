Общая рамка лекции

  • Kotlin не переизобретает коллекции — List/Set/Map это java.util.*
  • Два добавленных слоя: read-only/mutable интерфейсы и функции-расширения
  • Функции-расширения по умолчанию eager — ключевое отличие от Stream API
  • Центральный блок сегодня — Sequence и её устройство изнутри

List — та же Java-коллекция

val backing = mutableListOf(1, 2, 3)
      val readOnlyView: List<Int> = backing
  • Никакой отдельной реализации под капотом — это один и тот же объект
  • List просто не показывает методы изменения на уровне типа

Read-only ≠ immutable: демонстрация

backing.add(4)
      println(readOnlyView)
      // [1, 2, 3, 4] — изменения видны через "read-only" ссылку!
  • Объект физически мутабелен, "неизменяемость" — только со стороны конкретной переменной
  • В Java Collections.unmodifiableList бросил бы исключение при попытке менять САМУ обёртку — тут иначе

Приведение открывает мутацию снова

val mutableAgain = readOnlyView as MutableList<Int>
      mutableAgain.add(5)
      println(backing) // [1, 2, 3, 4, 5]
  • Компилятор не мешает такому касту — рантайм-защиты от него нет
  • Вывод для дизайна API: возврат List<T> — не гарантия неизменности для недоверенного кода

Список, содержащий сам себя: постановка

val list = mutableListOf<Any>(1, 2, 3)
      list.add(list) // список содержит сам себя как элемент
  • MutableList — реальный объект со ссылочной семантикой, циклы возможны
  • Что произойдёт при печати, хешировании, сравнении?

toString(): специальная защита от рекурсии

println(list) // [1, 2, 3, (this Collection)]
  • java.util.AbstractCollection.toString() проверяет if (e == this)
  • Вместо бесконечной рекурсии печатает маркер — защита есть только здесь

hashCode()/equals(): защиты нет

list.hashCode()      // StackOverflowError
      list.equals(other)   // StackOverflowError
  • Проверено напрямую на JVM — MutableList = java.util.ArrayList
  • Вывод: коллекции — обычные mutable-объекты со всеми острыми углами объектного графа с циклами

Трансформации

  • map { } — применить функцию к каждому элементу
  • mapIndexed { i, v -> } — то же самое, но с индексом
  • mapNotNull { } — как map, но null-результаты выбрасываются
listOf("1","x","2").mapNotNull { it.toIntOrNull() } // [1, 2]

Фильтрация

listOf(1,2,3,4).filter { it % 2 == 0 }        // [2, 4]
      listOf<Any>(1,"a",2).filterIsInstance<String>() // ["a"]
      val (evens, odds) = listOf(1,2,3,4).partition { it % 2 == 0 }

fold vs reduce: разница в безопасности

emptyList<Int>().fold(10) { acc, v -> acc + v }   // 10 — безопасно
      emptyList<Int>().reduce { acc, v -> acc + v }     // UnsupportedOperationException!
  • fold всегда имеет стартовое значение — работает и на пустой коллекции
  • reduce берёт первый элемент как старт — падает, если брать неоткуда

Группировки и агрегация

listOf("a","bb","ccc").groupBy { it.length }
      // {1=[a], 2=[bb], 3=[ccc]}
      listOf("a","bb").associateWith { it.length }
      // {a=1, bb=2}
      listOf(1,2,3).sumOf { it * 2 } // 12

Терминальные проверки

listOf(1,2,3).any { it > 2 }   // true
      listOf(1,2,3).all { it > 0 }   // true
      listOf(1,2,3).none { it > 5 }  // true
      listOf(1,2,3).count { it > 1 } // 2

Менее очевидные операции

listOf(1,2,3).zip(listOf("a","b","c"))
      // [(1,a), (2,b), (3,c)]
      listOf(1,2,3,4,5).windowed(3)
      // [[1,2,3], [2,3,4], [3,4,5]]
      listOf(1,2,3,4,5).chunked(2)
      // [[1,2], [3,4], [5]]

flatMap: map + разворачивание вложенности

  • map над списком списков даёт список списков — вложенность остаётся
  • flatMap делает то же самое, но затем "разворачивает" один уровень вложенности
listOf(listOf(1,2), listOf(3,4)).map { it }
      // [[1, 2], [3, 4]] — вложенность осталась
      listOf(listOf(1,2), listOf(3,4)).flatMap { it }
      // [1, 2, 3, 4] — развернули один уровень

flatMap: трансформация ВНУТРИ разворачивания

data class Person(val name: String, val hobbies: List<String>)
      val people = listOf(
      Person("Аня", listOf("рисование", "бег")),
      Person("Боря", listOf("шахматы"))
      )
      val allHobbies = people.flatMap { it.hobbies }
      // [рисование, бег, шахматы] — плоский список всех увлечений

Лямбда возвращает список ДЛЯ КАЖДОГО элемента — flatMap склеивает их все в один

flatMap vs map(...).flatten()

val a = people.map { it.hobbies }.flatten()
      val b = people.flatMap { it.hobbies }
      // a и b — одинаковый результат
  • flatMap — это ровно map, а затем flatten, объединённые в одну операцию
  • Разница практическая: не создаётся промежуточный список списков — меньше аллокаций

flatMap на Sequence: ленивость сохраняется

people.asSequence()
      .flatMap { it.hobbies.asSequence() }
      .first()
      // вычисляется только до первого найденного увлечения,
      // остальные Person и их списки не трогаются вовсе

Внутренние списки тоже оборачиваются в Sequence — ленивость не теряется на вложенном уровне

flatMap: параллель с Java

// Java
      list.stream()
      .flatMap(p -> p.getHobbies().stream())
      .collect(Collectors.toList());
  • Тот же самый смысл: "для каждого элемента — поток элементов, все потоки — в один"
  • Название и смысл операции в Kotlin и Java идентичны — переносится знание один в один

Нюанс типизации: тип не сохраняется

val s = setOf(1, 2, 3)
      val mapped = s.map { it % 2 }
      println(mapped) // [1, 0, 1] — список с дубликатами!

Интуиция подсказывает "Set на входе — Set на выходе". Это не так.

Почему это не баг, а необходимость

  • Лямбда не обязана быть инъективной — разные элементы могут схлопнуться в одно значение
  • Если бы map всегда возвращал Set — куда делся бы "лишний" дубликат?
  • Стандартная библиотека не пытается угадывать — map/filter/distinct/sorted всегда дают List

Явное преобразование и Scala для контраста

val result: Set<Int> = setOf(1,2,3).map { it % 2 }.toSet() // {1, 0}
  • Нужен Set на выходе — просите об этом явно через .toSet()
  • В Scala иначе: Set(1,2).map(_+1) вернёт Set (через CanBuildFrom) — другой архитектурный выбор

Многомерность: список списков, не матрица

val matrix: Array<IntArray> = Array(3) { IntArray(4) }
      matrix[1][2] = 99
  • Нет истинной прямоугольной матрицы, как в C# (int[,]) или Fortran
  • matrix[i][j] работает потому, что matrix[i] — независимый IntArray

Jagged array: строки разной длины

val jagged = arrayOf(intArrayOf(1), intArrayOf(1,2), intArrayOf(1,2,3))
      // [[1], [1, 2], [1, 2, 3]] — совершенно валидно

Раз строки независимы — ничто не требует одинаковой длины

Классическая ловушка: общая ссылка на строку

val row = MutableList(4) { 0 }
      val broken = MutableList(3) { row } // ОДИН И ТОТ ЖЕ объект 3 раза!
      broken[0][0] = 99
      // [[99,0,0,0],[99,0,0,0],[99,0,0,0]] — изменилось всё сразу
val correct = MutableList(3) { MutableList(4) { 0 } } // новый объект каждый раз

Eager vs Lazy: один и тот же код, два поведения

listOf(1,2,3,4,5)
      .map { println("map $it"); it * 2 }
      .filter { println("filter $it"); it > 4 }
      .first()

Вывод: все 5 map, потом все filter — 10 вызовов лямбд

То же самое через Sequence

sequenceOf(1,2,3,4,5)
      .map { println("map $it"); it * 2 }
      .filter { println("filter $it"); it > 4 }
      .first()

Вывод: map 1, filter 2, map 2, filter 4, map 3, filter 6 — СТОП

Разбор: по вертикали, а не по горизонтали

  • List: сначала ВСЯ операция для всех элементов, потом следующая операция
  • Sequence: каждый элемент проходит ВСЮ цепочку целиком, один за другим
  • first() нашёл результат на 3-м элементе — 4-й и 5-й вообще не потребовались

Когда Sequence даёт реальный выигрыш

  • Длинные цепочки трансформаций над большими коллекциями — нет промежуточных списков
  • Ранний выход: first, find, take, any
  • Бесконечные последовательности:
generateSequence(1) { it * 2 }.take(10).toList()
      // [1, 2, 4, 8, 16, 32, 64, 128, 256, 512]

Когда Sequence не нужна и даже вредна

  • Маленькие коллекции — оверхед обёрток-итераторов перевешивает выигрыш
  • Если в конце всё равно нужен полный toList() — ленивость не даёт ничего
  • Карго-культ "Sequence = всегда быстрее" — неправда на малых данных

Практическая эвристика выбора

  • 1–2 операции, небольшая коллекция → обычный List
  • 3+ операций, или коллекция большая, или нужен ранний выход → asSequence()
  • Параллельная обработка → не Sequence (она ленивая, но не параллельная), а Stream.parallel()

Интерфейс Sequence: один метод

interface Sequence<out T> {
      operator fun iterator(): Iterator<T>
      }

Вся "магия" ленивости — в том, как оборачиваются итераторы, а не в структуре данных

Реализация map(): TransformingSequence

class TransformingSequence<T, R>(
      private val source: Sequence<T>,
      private val transform: (T) -> R
      ) : Sequence<R> {
      override fun iterator() = object : Iterator<R> {
      val inner = source.iterator()
      override fun hasNext() = inner.hasNext()
      override fun next(): R = transform(inner.next())
      }
      }

Иллюстративная реконструкция механизма, не дословная цитата stdlib

Почему filter() сложнее map()

  • map: один входной элемент → ровно один выходной — тривиальная обёртка next()
  • filter: неизвестно заранее, сколько элементов придётся пропустить до подходящего
  • Нужна мини-машина состояний — "найти следующий подходящий и запомнить его"

Реализация filter(): FilteringSequence

class FilteringSequence<T>(
      private val source: Sequence<T>,
      private val predicate: (T) -> Boolean
      ) : Sequence<T> {
      override fun iterator() = object : Iterator<T> {
      val inner = source.iterator()
      var nextItem: T? = null
      var found = false
      fun seekNext() {
      while (inner.hasNext()) {
      val c = inner.next()
      if (predicate(c)) { nextItem = c; found = true; return }
      }
      found = false
      }
      override fun hasNext(): Boolean {
      if (!found) seekNext(); return found
      }
      override fun next(): T {
      if (!found) seekNext()
      found = false
      return nextItem as T
      }
      }
      }

Трассировка: map{}.filter{}.first(), шаг 1

  • first() запрашивает у цепочки: hasNext(), затем next()
  • Запрос идёт СНАРУЖИ ВНУТРЬ: FilteringSequence спрашивает TransformingSequence
  • TransformingSequence спрашивает исходный sequenceOf(1,2,3,4,5)

Трассировка: map{}.filter{}.first(), шаг 2

  • Источник отдаёт 1 → TransformingSequence применяет map → 2
  • FilteringSequence.seekNext() проверяет predicate(2) → 2 > 4? нет — просит следующий
  • Источник отдаёт 2 → map → 4 → predicate(4)? нет — просит следующий
  • Источник отдаёт 3 → map → 6 → predicate(6)? ДА — останов

Трассировка: итог

  • Элементы 4 и 5 исходной последовательности НЕ запрошены вообще
  • Ни один промежуточный список нигде не создавался — только цепочка вложенных Iterator
  • Это и есть буквальный смысл "ленивости": работа делается по требованию, а не заранее

generateSequence: как устроен бесконечный источник

fun <T> generateSequence(seed: T, next: (T) -> T?): Sequence<T>
  • Каждый вызов next() у итератора вызывает переданную функцию next(prev)
  • Ничего не хранится заранее — следующее значение вычисляется в момент запроса
  • Возврат null из next завершает последовательность

take(): как обрывается бесконечность

generateSequence(1) { it * 2 }.take(10)
  • TakeSequence оборачивает источник и считает, сколько элементов уже отдано
  • После n-го элемента hasNext() начинает возвращать false — источник больше не трогают
  • Без take() бесконечный generateSequence просто никогда не завершит toList()

Пример 1: обработка заказов — постановка

data class Order(val customer: String, val amount: Double, val paid: Boolean)

Задача: посчитать суммарную оплаченную выручку по каждому клиенту, отсортировано по убыванию

Пример 1: конвейер целиком

val totals = orders
      .filter { it.paid }
      .groupBy { it.customer }
      .mapValues { (_, list) -> list.sumOf { it.amount } }
      .toList()
      .sortedByDescending { (_, sum) -> sum }

Четыре операции подряд — filter, groupBy, mapValues, sortedByDescending — читаются как описание задачи

Пример 2: анализ лога — постановка

// строки вида "2026-01-01 ERROR disk full"
      val logLines: List<String>

Задача: найти первую строку уровня FATAL, не читая файл целиком, если он гигантский

Пример 2: конвейер на Sequence

val firstFatal = logLines.asSequence()
      .map { it.split(" ", limit = 3) }
      .filter { it.size == 3 && it[1] == "FATAL" }
      .map { it[2] }
      .firstOrNull()

asSequence() здесь принципиален: как только нашли FATAL — остаток лога не разбирается вовсе

Пример 3: flatMap в конвейере — постановка

data class Student(val name: String, val grades: List<Int>)
      val students: List<Student>

Задача: средний балл по ВСЕМ оценкам ВСЕХ студентов разом (не по каждому студенту отдельно)

Пример 3: конвейер с flatMap

val overallAverage = students
      .flatMap { it.grades }
      .average()

Без flatMap пришлось бы вручную собирать плоский список через цикл — здесь одна строка

Когда в конвейер стоит вставлять asSequence()

  • Пример 1 (заказы) — обычно небольшой список, groupBy всё равно материализует Map целиком → asSequence() не нужен
  • Пример 2 (лог) — потенциально гигабайты строк, ранний выход через firstOrNull() → asSequence() критичен
  • Пример 3 (студенты) — average() всё равно обходит всё до конца → asSequence() почти не поможет

groupingBy().eachCount(): компактность

words.groupingBy { it.first() }.eachCount()
      // {a=2, b=2, c=1}
// Java
      words.stream().collect(Collectors.groupingBy(
      w -> w.charAt(0), Collectors.counting()));

Итоги, часть 1

  • List/Map — Java-коллекции с урезанным на уровне типов интерфейсом, не новая реализация
  • Мутабельные коллекции — обычные объекты со ссылочной семантикой, включая циклы
  • Трансформации не сохраняют тип коллекции — только семантически возможный List
  • flatMap — map, слитый с разворачиванием на один уровень вложенности

Итоги, часть 2 — что дальше

  • Sequence — цепочка обёрток над Iterator, вычисление по требованию
  • Многомерность — вложенность, а не матрица; следите за общими ссылками
  • В реальных конвейерах asSequence() полезен ровно там, где есть ранний выход или гигантский вход
