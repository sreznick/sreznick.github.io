Свойства и инициализация

  • Свойство = поле + геттер/сеттер

  • lateinit, lazy, const
  • Prototype · Builder · Value Object

Свойство = поле + геттер (+ сеттер)

class User(val id: Int, var name: String)

val u = User(1, "Ann")
u.name = "Bob"          // на самом деле вызов setName("Bob")
println(u.id)           // getId()
  • val — поле и геттер; var — поле, геттер и сеттер
  • Из Java виден обычный JavaBean: getId(), getName(), setName()
  • @JvmField отдаёт поле напрямую, без методов (упоминание)

Свои get/set и backing field

class Temperature(celsius: Double) {
    var celsius: Double = celsius
        set(value) {
            require(value >= -273.15) { "ниже абсолютного нуля" }
            field = value                    // backing field
        }

    val fahrenheit: Double                   // вычисляемое, без поля
        get() = celsius * 9 / 5 + 32
}
  • field — ссылка на поле внутри аксессора
  • Начальное значение пишется в поле напрямую, сеттер при инициализации не вызывается
  • Свойство без field не хранит данных — вычисляется при каждом обращении

private set

class Counter {
    var value = 0
        private set                 // писать можно только внутри

    fun inc() { value++ }
}

val c = Counter()
c.inc()
// c.value = 5                    // ошибка компиляции

Инкапсуляция без ручных геттеров: публичное чтение, закрытая запись.

init и порядок инициализации

class Order(val id: Int) {
    val created = System.currentTimeMillis()
    init { println("init 1: id=$id") }
    val items = mutableListOf<String>()
    init { println("init 2: items=${items.size}") }
}
  • Свойства и блоки init выполняются сверху вниз, в порядке записи
  • Параметры основного конструктора видны в init и инициализаторах
  • Обращаться к свойству, объявленному ниже, из init нельзя (ошибка компиляции)

Вторичные конструкторы и значения по умолчанию

class Money(val amount: Long, val currency: String = "RUB") {
    constructor(text: String) : this(text.toLong())   // обязан вызвать основной
}

Money(100)                          // валюта по умолчанию
Money(100, currency = "USD")        // именованный аргумент
Money("250")                        // вторичный конструктор
  • Значения по умолчанию и именованные аргументы заменяют перегрузки из Java
  • Для Java-вызовов есть @JvmOverloads

Проверка инвариантов

data class Money(val amount: Long, val currency: String) {
    init {
        require(amount >= 0) { "сумма отрицательна: $amount" }
        require(currency.length == 3) { "код валюты: $currency" }
    }
}

Money(-5, "RUB")     // IllegalArgumentException
  • require — проверка аргументов (IllegalArgumentException)
  • check — проверка состояния (IllegalStateException)
  • Объект корректен с момента создания — не бывает «полупустых» экземпляров

lateinit, lazy, const

class Service {
    lateinit var config: Config              // будет задано позже (DI, тесты)
    val heavy: Heavy by lazy { Heavy() }     // создаётся при первом обращении

    fun ready() = ::config.isInitialized
}

const val MAX_ITEMS = 100                    // константа времени компиляции
  • lateinit: только var, не для примитивов и nullable; до присваивания — UninitializedPropertyAccessException
  • lazy: считается один раз, по умолчанию потокобезопасно
  • const val: примитивы и String, на верхнем уровне или в object

Ловушка: свойства в теле data-класса

data class Item(val name: String) {
    var note: String = ""      // вне equals/hashCode/toString/copy
}

val a = Item("x").apply { note = "1" }
val b = Item("x").apply { note = "2" }
println(a == b)                // true
println(a.copy().note)         // "" — note не скопирован

В equals, hashCode, toString, copy участвуют только свойства из основного конструктора.

Prototype: copy()

data class Address(val street: String, val city: String)
data class Customer(val name: String, val address: Address,
                    val tags: MutableList<String>)

val c1 = Customer("Ann", Address("Lenina 1", "Perm"), mutableListOf("vip"))
val c2 = c1.copy(name = "Bob")
c2.tags.add("new")

  • copy() — готовый Prototype: «клон с изменениями»
  • Копия поверхностная: изменяемые вложенные объекты разделяются
  • Решение: неизменяемые коллекции и вложенные data-классы

Builder: чаще не нужен

class HttpRequest(
    val url: String,
    val method: String = "GET",
    val timeoutMs: Int = 5_000,
    val headers: Map<String, String> = emptyMap(),

HttpRequest("https://example.com", timeoutMs = 1_000)
  • Именованные аргументы и значения по умолчанию заменяют Builder и «телескопические» конструкторы

Value Object

  • Value Object — значение без идентичности: равенство по содержимому
  • В Kotlin: data class + только val + проверка в init (Money)
  • Неизменяемость: безопасно разделять между потоками (вспомните блок про JMM)
  • Операции возвращают новые объекты: fun plus(o: Money) = copy(amount = amount + o.amount)
  • Для «типизированных примитивов» без накладных расходов — value class (за рамками лекции)

Видимость, object и companion

Модификаторы видимости

Модификатор Где виден
public (по умолчанию) везде
private в классе; для верхнего уровня — в файле
protected в классе и наследниках (на верхнем уровне нет)
internal во всём модуле (Gradle/Maven-модуль)

Отличия от Java: по умолчанию public; нет package-private.

Инкапсуляция состояния

class Cart {
    private val _items = mutableListOf<Item>()
    val items: List<Item> get() = _items       // наружу — только чтение

    fun add(item: Item) { _items += item }
}
  • Приём _items / items: изменяемое внутри, «только чтение» снаружи
  • List — read-only интерфейс, а не копия: привести к MutableList всё ещё можно
  • Строгая защита — отдавать копию: _items.toList()

nested и inner

class Outer(val name: String) {
    class Nested {                          // нет ссылки на Outer
        fun hi() = "nested"
    }
    inner class Inner {                     // хранит ссылку на Outer
        fun hi() = "inner of ${this@Outer.name}"
    }
}

val n = Outer.Nested()
val i = Outer("A").Inner()

В Java наоборот: вложенный класс по умолчанию «внутренний»; static нужно писать явно. В Kotlin случайных утечек ссылки на внешний объект меньше.

object: синглтон

object Clock {
    private var offset = 0L
    fun now() = System.currentTimeMillis() + offset
}

Clock.now()
  • Один экземпляр; создаётся при первом обращении, инициализация потокобезопасна (гарантия JVM)
  • Нет параметров конструктора; может реализовывать интерфейсы и наследоваться
  • object expression (object : Runnable { ... }) заменяет анонимные классы

companion object

class Order private constructor(val id: Int) {
    companion object {
        const val MAX_ITEMS = 100

        fun create(id: Int): Order {
            require(id > 0)
            return Order(id)
        }
    }
}

val o = Order.create(1)
  • Ключевого слова static в Kotlin нет: companion, object, функции верхнего уровня
  • Companion — обычный объект: может реализовывать интерфейсы, хранить состояние
  • Из Java: Order.Companion.create(), либо @JvmStatic → Order.create()

Что в байткоде

  • object Clock → класс с полем INSTANCE и приватным конструктором
  • companion object → вложенный класс Companion и статическое поле во внешнем классе
  • Свойство → приватное поле + геттер/сеттер
  • internal → в байткоде public, но имя метода с суффиксом модуля (foo$module)
  • Верхнеуровневые функции → статические методы класса FileKt

Singleton

Java:

public final class Config {
    private Config() {}
    private static class Holder { static final Config INSTANCE = new Config(); }
    public static Config getInstance() { return Holder.INSTANCE; }
}

Kotlin:

object Config
  • Паттерн в одно слово; ленивость и потокобезопасность даёт JVM
  • Оговорка: скрытая глобальная зависимость, сложнее тестировать — лучше передавать через конструктор (DI)

Factory Method

class Money private constructor(val amount: Long, val cur: String) {
    companion object {
        fun of(amount: Long, cur: String) = Money(amount, cur)
        fun rub(amount: Long) = of(amount, "RUB")
        fun parse(text: String): Money {
            val (a, c) = text.split(" ")
            return of(a.toLong(), c)
        }
    }
}

val m = Money.parse("10 RUB")
  • Приватный конструктор + именованные фабрики: скрывают создание, могут кешировать и валидировать
  • Соглашения об именах: of, from, parse, create
  • operator fun invoke в companion позволяет вызывать как конструктор

Наследование и полиморфизм

  • final по умолчанию: open и override
  • Порядок инициализации и его ловушка
  • abstract, приведение типов, smart cast
  • Template Method · LSP · хрупкий базовый класс

open и override

open class Animal(val name: String) {
    open fun sound() = "..."
    fun describe() = "$name says ${sound()}"       // final по умолчанию
}

class Dog(name: String) : Animal(name) {
    override fun sound() = "Woof"
}
  • Классы и методы закрыты по умолчанию: наследовать можно только то, что помечено open
  • override обязателен; сам он тоже открыт, закрыть — final override
  • Идея (Effective Java): проектируйте для наследования или запрещайте его

Конструктор родителя и порядок

open class Base(val x: Int) {
    init { println("Base init") }
}

class Derived(x: Int, val y: Int) : Base(x) {
    init { println("Derived init") }
}

Derived(1, 2)      // Base init → Derived init
  • Родитель инициализируется первым, параметры для него передаются в заголовке класса
  • Без основного конструктора вызов родителя пишут во вторичных: : super(...)

Ловушка: open-метод в init

open class Base {
    init { describe() }
    open fun describe() {}
}

class Derived : Base() {
    val name = "x"
    override fun describe() = println(name)      // выведет null
}

Derived()
  • init базового класса выполняется до инициализации полей Derived
  • name типа String оказывается null
  • Вывод: не вызывайте open-члены из init и конструкторов
Компилятор Kotlin предупреждает: Calling non-final function in constructor.

abstract, protected, super

abstract class Shape {
    abstract fun area(): Double
    open fun describe() = "Shape with area ${area()}"
    protected fun round(v: Double) = Math.round(v * 100) / 100.0
}

class Circle(val r: Double) : Shape() {
    override fun area() = round(Math.PI * r * r)
    override fun describe() = "Circle: " + super.describe()
}
  • abstract — без реализации, экземпляр создать нельзя
  • protected — виден наследникам; super.describe() — реализация родителя

Полиморфизм и приведение типов

class Square(val a: Double) : Shape() { override fun area() = a * a }

val shapes: List<Shape> = listOf(Circle(1.0), Square(2.0))
for (s in shapes) println(s.describe())       // выбор реализации в рантайме

fun show(s: Shape) {
    if (s is Circle) println(s.r)             // smart cast
    val c = s as? Circle                      // Circle? — без исключения
}
  • is, !is, as (может бросить), as? (вернёт null)

Smart cast и особые типы

  • Smart cast работает для локальных переменных, не меняющихся между проверкой и использованием, и для val-свойств без кастомного геттера в том же модуле
  • Не работает для var-свойств и open-свойств: значение может измениться
  • Any — корень иерархии (equals, hashCode, toString)
  • Unit — «нет значения», Nothing — функция не возвращается (throw), подтип всех типов

Data-классы и наследование

  • Data-класс не может быть open, abstract, sealed, inner
  • Может наследовать другой класс и реализовывать интерфейсы
  • При наследовании ломается симметричность equals: он сгенерирован под конкретный класс
  • Рекомендация: финальные data-классы + интерфейс или sealed-иерархия

Template Method

abstract class Report {
    fun render(): String =                       // final по умолчанию
        header() + body() + footer()

    protected open fun header() = "== Report ==\n"
    protected abstract fun body(): String
    protected open fun footer() = "\n== end =="
}

class SalesReport : Report() {
    override fun body() = "Sales: 42"
}
  • Метод-шаблон фиксирует последовательность, шаги переопределяются
  • Финальность по умолчанию защищает шаблон; в Java нужно писать final вручную
  • Hook-методы: open с реализацией по умолчанию

Принцип подстановки Лисков (LSP)

  • Объект подкласса можно подставить вместо базового, не нарушив ожиданий вызывающего кода
  • Классика: изменяемые Rectangle и Square — установка ширины у квадрата меняет высоту, тест «2×3 = 6» ломается
  • Лекарство: неизменяемые фигуры или общий интерфейс Shape без «сеттеров»
  • Сигналы нарушения: override бросает UnsupportedOperationException, усиливает предусловия, ослабляет результат

Хрупкий базовый класс

open class CountingSet : HashSet<String>() {
    var added = 0
    override fun add(element: String): Boolean {
        added++
        return super.add(element)
    }
    override fun addAll(elements: Collection<String>): Boolean {
        added += elements.size
        return super.addAll(elements)
    }
}

val s = CountingSet()
s.addAll(listOf("a", "b"))
println(s.added)                  // 4, а не 2!
  • HashSet.addAll внутри вызывает add — наследник зависит от деталей реализации родителя
  • Решение — композиция и делегирование (блок 6)

Интерфейсы и абстрактные классы

  • Реализации по умолчанию, конфликты

Интерфейсы с реализацией по умолчанию

interface Named {
    val name: String                       // абстрактное свойство
    fun greet() = "Hello, $name"           // реализация по умолчанию
}

class User(override val name: String) : Named

User("Ann").greet()                        // "Hello, Ann"
  • Свойства в интерфейсе не хранят состояние (нет backing field)
  • Класс может реализовывать сколько угодно интерфейсов

Конфликт реализаций

interface A { fun hello() = "A" }
interface B { fun hello() = "B" }

class C : A, B {
    override fun hello() = super<A>.hello() + super<B>.hello()
}

C().hello()          // "AB"
  • Если два интерфейса дают реализацию одного метода, компилятор требует явный override
  • super<A> выбирает нужную реализацию

Интерфейс или abstract class?

Интерфейс Abstract class
Состояние (поля) нет да
Конструктор нет да
Множественное наследование да нет (один родитель)
Когда брать контракт, роль, поведение общая часть реализации и состояние

fun interface и функциональные типы

fun interface Discount {
    fun apply(price: Int): Int
}

val tenPercent = Discount { it * 90 / 100 }     // SAM-преобразование
println(tenPercent.apply(200))                 // 180

val same: (Int) -> Int = { it * 90 / 100 }      // функциональный тип
  • Интерфейс с одним абстрактным методом можно создавать лямбдой
  • Функциональный тип часто заменяет такие интерфейсы совсем

Strategy

interface Discount { fun apply(price: Int): Int }

class Percent(private val p: Int) : Discount {
    override fun apply(price: Int) = price * (100 - p) / 100
}
class Fixed(private val off: Int) : Discount {
    override fun apply(price: Int) = maxOf(0, price - off)
}

class Order(val price: Int, val discount: Discount) {
    fun total() = discount.apply(price)
}
  • Поведение подменяется без наследования Order
  • Упрощение: параметр discount: (Int) -> Int — стратегия как лямбда

Null Object

object NoDiscount : Discount {
    override fun apply(price: Int) = price
}

val order = Order(1000, NoDiscount)   // вместо Discount? и проверок на null
println(order.total())                // 1000
  • «Пустая» реализация вместо null: вызывающему не нужны проверки
  • Nullable-типы Kotlin хороши, когда «отсутствие» — просто отсутствие; Null Object — когда у отсутствия есть поведение

Adapter (первый подход)

interface Notifier { fun send(text: String) }

class LegacySms {
    fun push(number: String, msg: String) { /* ... */ }
}

class SmsNotifier(
    private val sms: LegacySms,
    private val number: String,
) : Notifier {
    override fun send(text: String) = sms.push(number, text)
}

Приводит чужой интерфейс к нужному. Короче — через by (блок 6) и расширения (блок 7).

Принципы

  • DIP: зависим от Discount, а не от Percent
  • OCP: новая скидка — новый класс, Order не меняется
  • ISP: маленькие интерфейсы: клиент видит только нужное
  • LSP: любая реализация Discount ведёт себя в рамках контракта
  • Интерфейсы — основа Strategy, Adapter, Decorator

enum и sealed

  • enum class
  • sealed-классы и интерфейсы, exhaustive when

enum class

enum class Status(val label: String) {
    NEW("Новый"),
    PAID("Оплачен") { override fun next() = SHIPPED },
    SHIPPED("Отправлен");

    open fun next(): Status = this
}

Status.PAID.next()          // SHIPPED
Status.entries              // список констант
Status.valueOf("NEW")
  • Константы — синглтоны, у них могут быть свойства, методы и собственные тела
  • entries — современная замена values()

when по enum

fun label(s: Status) = when (s) {
    Status.NEW -> "новый"
    Status.PAID -> "оплачен"
    Status.SHIPPED -> "в пути"
}                 // без else: компилятор проверил полноту

Если добавить константу и забыть ветку when-выражения, код не скомпилируется.

sealed: закрытая иерархия

sealed interface PaymentResult {
    data class Success(val txId: String) : PaymentResult
    data class Failure(val reason: String) : PaymentResult
    data object Cancelled : PaymentResult
}

fun report(r: PaymentResult): String = when (r) {
    is PaymentResult.Success -> "OK ${r.txId}"
    is PaymentResult.Failure -> "Ошибка: ${r.reason}"
    PaymentResult.Cancelled  -> "Отмена"
}
  • Все подтипы известны компилятору (один пакет и модуль)
  • when без else: добавили подтип — компилятор покажет все забытые места

enum, sealed и Java

enum sealed
Что это фиксированный набор констант закрытая иерархия типов
Данные у вариантов одинаковые у каждого подтипа свои
Экземпляры по одному на константу сколько угодно (кроме object)

State

sealed interface OrderState {
    data object New : OrderState
    data class Paid(val txId: String) : OrderState
    data class Shipped(val trackingNo: String) : OrderState
    data object Cancelled : OrderState
}

fun pay(s: OrderState, tx: String): OrderState = when (s) {
    OrderState.New -> OrderState.Paid(tx)
    else -> error("нельзя оплатить заказ в состоянии $s")
}
  • Переходы — функции, возвращающие новое состояние; недопустимые запрещены явно
  • В GoF состояния — классы с методами; здесь — данные и when: логика видна в одном месте

Composite

sealed interface Expr {
    data class Num(val v: Int) : Expr
    data class Sum(val l: Expr, val r: Expr) : Expr
    data class Mul(val l: Expr, val r: Expr) : Expr
}

fun eval(e: Expr): Int = when (e) {
    is Expr.Num -> e.v
    is Expr.Sum -> eval(e.l) + eval(e.r)
    is Expr.Mul -> eval(e.l) * eval(e.r)
}

eval(Expr.Sum(Expr.Num(2), Expr.Mul(Expr.Num(3), Expr.Num(4))))   // 14

Лист и составной узел — один тип; рекурсия по структуре.

Visitor

  • Java (классика): интерфейс Visitor с методом на каждый тип и accept(visitor) в каждом классе — двойная диспетчеризация
  • Kotlin: sealed + when: новая операция — просто новая функция (eval, print, simplify)
  • Компромисс (expression problem): новую операцию добавить легко; новый подтип потребует правки всех when, но компилятор их покажет
  • В обычном ООП наоборот: подтип добавить легко, операцию — трудно

Композиция вместо наследования

  • Наследование связывает наследника с деталями родителя (пример с CountingSet)
  • Композиция: содержим объект и делегируем ему, а не расширяем
  • Проблема композиции в Java — рутина: писать методы-пробросы для каждого метода интерфейса
  • В Kotlin рутину берёт на себя компилятор: by

Делегирование интерфейса: by

interface Repo {
    fun save(order: Order)
    fun find(id: Int): Order?
}

class LoggingRepo(private val inner: Repo) : Repo by inner {
    override fun save(order: Order) {
        println("save ${order.id}")
        inner.save(order)
    }
}
  • Компилятор генерирует проброс всех методов интерфейса (find тоже)
  • Переопределяем только то, что нужно; в декомпиляции видны сгенерированные методы

Decorator

class CachingRepo(private val inner: Repo) : Repo by inner {
    private val cache = mutableMapOf<Int, Order>()
    override fun find(id: Int): Order? =
        cache[id] ?: inner.find(id)?.also { cache[id] = it }
}

val repo: Repo = LoggingRepo(CachingRepo(InMemoryRepo()))
  • Декораторы вкладываются друг в друга и остаются Repo
  • Порядок обёрток определяет поведение (логировать ли обращения к кешу?)

Композиция без хрупкости

class MetricsList<T>(
    private val inner: MutableList<T>,
) : MutableList<T> by inner {
    var adds = 0
        private set

    override fun add(element: T): Boolean {
        adds++
        return inner.add(element)
    }
}
  • addAll идёт напрямую в inner и не вызывает наш add: счётчик не удваивается
  • Считать элементы addAll нужно явным переопределением — контроль у нас

Делегированные свойства

import kotlin.properties.Delegates

class Product {
    val description: String by lazy { loadFromDb() }     // лениво

    var price: Int by Delegates.observable(0) { _, old, new ->
        println("price: $old -> $new")                   // реакция на изменение
    }

    private fun loadFromDb() = "long description"
}
  • Готовые делегаты: lazy, observable, vetoable (может отклонить), by map
  • Свой делегат — интерфейс ReadWriteProperty

Proxy и Observer

  • Virtual Proxy: by lazy — дорогой объект создаётся при первом обращении
  • Protection Proxy: класс с by и проверкой прав перед вызовом
  • Observer: Delegates.observable — реакция на изменение одного свойства
  • Для нескольких подписчиков — список колбэков (Int) -> Unit (лямбды — отдельная лекция)
  • Adapter (полная форма): by + несколько своих методов приводят чужой интерфейс к нужному

Функции-расширения

  • Синтаксис и правила
  • Как компилируется

Функции и свойства-расширения

class Money(val amount: Long, val currency: String)

fun Money.format() = "%d %s".format(amount, currency)
val Money.isZero: Boolean get() = amount == 0L

Money(10, "RUB").format()        // "10 RUB"
  • Внутри расширения this — объект-получатель (receiver)
  • Класс не меняется и не пересобирается: расширение можно написать для чужого типа
  • Бывают и для nullable-типов: fun String?.orEmpty()

Правила расширений

open class A
class B : A()

fun A.who() = "A"
fun B.who() = "B"

val a: A = B()
println(a.who())          // "A" — выбор по статическому типу!
  • Разрешаются статически: не полиморфны
  • Нет доступа к private/protected членам
  • Если у класса есть метод с той же сигнатурой, метод побеждает расширение

Как компилируется

Kotlin:

fun Money.format(): String = "..."

Что видит Java:

// файл MoneyKt.java (имя можно задать @file:JvmName)
public static final String format(Money $this) { ... }
  • Обычный статический метод, receiver — первый параметр
  • Вызов m.format() — сахар над MoneyKt.format(m)

Adapter и Facade-подобный API

fun ExternalDto.toOrder() = Order(id = orderId, total = sum)

val orders = dtos.map { it.toOrder() }
  • Adapter без обёртки: приводим чужой тип к своему, не создавая класс-обёртку
  • Facade-подобный API: удобные операции над сложными типами
  • Замена *Utils-классов из Java
  • Ограничения: нельзя добавить состояние и переопределить; нужен import
  • Мост к следующим темам: лямбды, let/apply, DSL
