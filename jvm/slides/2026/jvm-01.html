Правила оценивания (возможны небольшие уточнения)

  • В первом приближении - оценивание по формуле
  • В отдельных (редких) случаях возможно ручное модерирование
  • Модерирование оценки - мера исключительная и редкая 
  • Модерирование оценки обязательно сопровождается объяснением в объективных терминах
  • Модерирование оценки может быть проаппелировано

Правила оценивания

  • Внутренняя оценка - по 100-бальной шкале
  • Итоговая 100-бальная переводится в 10-бальную
  • Нижний порог зачета - 50 баллов
  • Границы между балламм - с шагом 7: 57, 64, 71, 78, 95, 92
  • Итоговая оценка по формуле 0.5 * Exam + 0.3 * Big-HW + 0.2 * Small-HW
  • Exam - 100-бальная оценка за экзамен
  • Big-HW - 100-бальная оценка большую домашку
  • Small-HW - 100-бальная оценка большую домашку

Big-HW

  • Большая домашка - мини-проект на Kotlin
  • Ориентировочно на 1000-1500 строк
  • Одна на семестр
  • Выдается в декабре
  • Требует аппрува на ревью
  • Для аппрува нужно устранение критичных замечаний
  • Объективно сформулированных и релевантных целям курса
  • Балл зависит от количества замечаний и итераций в исправлении

Small-HW

  • Малые домашки - небольшие задания
  • Отрабатываем материал прошедшего занятия
  • Небольшой размер
  • Могут быть разными по форме
  • Как вариант - небольшой контест
  • Еще вариант - небольшой кодинг с ревью

Small-HW

  • Идеальная цель - после каждого занятия
  • Смысл - оперативно закрепить материал
  • Увидеть, как идет усвоение
  • Важна быстрая проверка
  • Что я и планирую делать
  • При задержках в проверке новые задания не выдаются

Исправление после ревью

  • В больших домашках - возможно несколько попыток
  • Но в новых попытках может расти штраф
  • В малых с ревью - попытка скорее одна
  • Штраф - примерно 50 процентов
  • Возможны вариации
  • При задержках в проверке новые задания не выдаются

Правила оценивания

  • Каждая отдельная домашка оценивается на 100 баллов
  • Оценка за малые домашки в целом - среднее от отдельных домашек
  • У домашек есть дедлайны
  • Пропуск домашки снижает балл, но не фатально
  • Общий смысл правил про дедлайны - мотивация ритмичной и равномерно распределенной работы
  • Сглаживание последствий ситуативных проблем и цейтнотов
  • Регулярные небольшие задержки в сдаче НЕ влияют фатально на оценку
  • Долгие провалы в активности влияют - и сильно

Правила про дедлайны

  • Дедлайн выставляется в формате dd.mm.yyyy hh:mm
  • Если сдать до указанного времени - работа оценивается без понижающего коэффициента
  • В течение 14 суток действует период линейного понижающего коэффициента
  • В течение суток он уменьшается на 0.05
  • Если работа сдана в течение суток после дедлайна - действует коэффициент 0.95
  • Если задержка больше суток, но меньше двух - действует коэффициент 0.9
  • Если задержка больше 13 суток, но меньше 14 - действует коэффициент 0.35

Правила про дедлайны

  • После 14 суток понижающий коэффициент выходит на плато
  • Он навечно фиксируется на значении 0.3
  • Небольшая задержка на границе суток может прощаться
  • Минуты - почти наверняка
  • 1-2 часа - очень может быть
  • Без гарантий, воспринимайте как бонус

Правила про дедлайны

  • Есть резерв индивидуального продления дедлайна
  • 5 суток на семестр
  • Гранулярность использования - сутки
  • Об использовании нужно уведомить до общего дедлайна
  • Начало линейного спуска и последующего плато для конкретного человека сдвинется на заданное число суток

Правила про дедлайны

  • Просьбы о сдвиге общего дедлайна сходу не отвергаются
  • Но всесторонне исследуются
  • На решение влияет степень использования индивидуальных продлений
  • И контекст конкретного задания
  • И обсуждение в чате и/или на занятиях

Правила про доделки

  • В домашках возможны доделки
  • Кроме редких индивидуальных случаев - одна итерация
  • Почти всегда решение с доделкой оценивается ниже, чем аналогичное с первого раза
  • Конкретные понижающие коэффициенты зависят от задания и типа ошибок
  • Сценарий типа "отправить абы что, получить подсказки в комментариях, сделать по подсказкам нормальное решение" считается антипаттерном
  • Итоговая оценка будет в таком случае будет в районе 0.5-0.6 от полного балла

Критически важные моменты

  • Некоторые факты/определения будут помечены как критически важные моменты
  • Отсутствие понимания хотя бы n критически важного моментов делает невозможной оценку за курс (9 - n) и выше
  • (n - положительное число)
  • Пример критически важного момента: отличие корутины от нити

Честность и самостоятельность

  • Ожидается, что студенты пришли чему-то научиться, а не получить балл любой ценой
  • Самостоятельность работы - обязательное условие прохождения курса
  • При обнаружении признаков несамостоятельности работы возможно снятие штрафных баллов
  • Если несамостоятельность проявляется в копиях работ - штраф накладывается на всех сдавших копии
  • При разительном несоответствии балла за задание ДЗ из ответа по той же теме на экзамене - баллы за ДЗ могут быть отозваны со штрафом
  • Студент может быть вызван на созвон для беседы о решениях
  • При неспособности поддержать беседу можно получить штрафные баллы

Особенности онлайн-обучения

  • Онлайн-занятия - это занятия, только в онлайн
  • Ожидается базовая вовлеченность в происходящее
  • Ожидается, что студент выделяет время и место для занятий
  • Базовая этика предполагает приветствие голосом
  • Ответ на вопрос, заданный голосом, ожидается голосом

Особенности онлайн-обучения

  • Лица слушателей - важный канал обратной связи
  • По умолчанию стараемся включать камеры
  • Качество связи может вносить коррективы
  • У нас нет формы наговаривания аудиолекций
  • При отсутствии студентов занятие не записывается
  • И считается проведенным

Посещаемость/активность

  • Отсутствие студента на занятия можно интерпретировать так
    1. Человек заболел
    2. Человек участвует в университетском мероприятии
    3. Человека что-то не устраивает в занятиях
    4. Человек и так все знает по данному предмету
    5. Что-то другое

Посещаемость/активность

  • Болезнь и мероприятия - явления скорее разовые
  • Если что-то не устраивает - имеет смысл дать обратную связь
  • По умолчанию систематически пропускающие люди воспринимаются как и так все знающие
  • Из этого исходим в оценивании

Пересдачи

  • Изложенные правила работают до конца сессии
  • Кто не получает зачет в рамках сессии - уходит на пересдачу
  • Пересдача - формальный термин, следующий из порядка работы вузов
  • Не обязательно это пересдача устного экзамена
  • Для каждого из ушедших на пересдачу предлагается свой план получения зачета
  • Планы индивидуальны, но с в каждом случае с мотивировкой

Пересдачи

  • Если немного не хватило баллов в общей сумме - скорее всего надо просто доделать какие-то домашки
  • Но доделки будут с учетом стандартных понижающих коэффициентов
  • Если плохо сдан экзамен - скорее всего потребуется пересдать экзамен
  • Если живого места нет - скорее всего потребуется хорошо сдать экзамен и сделать все домашки

К делу

  • Kotlin - мультипарадигменный язык программирования
  • В некотором смысле "безыдейный"
  • Со статической проверкой типов
  • Технически - позволяющий писать код в императивном стиле
  • Но де-факто с приоритетом ООП-подходов

К делу

  • Kotlin-код компилируется в байткод JVM
  • Первоначальная мотивация языка - преодоление проблем Java-программирования
  • Впоследствии появился KotlinJS
  • И KotlinNative
  • Наш приоритет - KotlinJVM

К делу

  • В паре Java-JVM оба элемента проектируются в общих интересах
  • В паре Kotlin-JVM такого нет
  • Какие-то свойства JVM ограничивают варианты семантики языка
  • Например, проблемы в семантике инициализации объектов в JVM переходят на семантику Kotlin
  • Какие-то элементы Kotlin-семантики остаются на уровне языка
  • Например, более богатая семантика прав доступа на уровне Kotlin не воплошается в полной мере в JVM

Пример



fun main() {
   println("Hello")
}

Разбор

  • Функция main - точка входа
  • Синтаксически это "просто" функция, без класса
  • В JVM нет "просто" функций
  • За кулисами будет создан класс
  • Для каждого исходника проекта - свой
  • "Просто" функции станут статическими методами в нем

Разбор

  • Компилятор порождает класс-файлы с байткодом
  • Исполнением байткода занимается реализация JVM (OpenJDK)
  • Kotlin-компилятор и реализация JVM - независимые продукты от разных разработчиков
  • У них нет персональных соглашений между собой
  • JVM работает по своей публичной спецификации
  • Kotlin порождает код согласно этой спецификации

Разбор

  • По спецификации JVM исполняемый класс должен содержать метод main
  • Статический
  • С публичным доступом
  • С одним параметром, тип которого - строковый массив (в системе типов JVM)

Разбор

  • В нашем случае будет содан метод main
  • Его статичность обеспечит Kotlin-компилятор
  • Доступ у нас явным не указан
  • Неуказанный доступ в Kotlin подразумевает публичный доступ

Пример


          
public fun main() {
   println("Hello")
}

Пример


          
fun main() {
    m()
}

private fun m() {
    println("Hello")
}

Пример



private fun main() { // может иметь смысл
    m()
}

private fun m() {
    println("Hello")
}

private main

  • При штатном запуске JVM из командной строки не запустится
  • Но IDEA запускает через кнопку Run
  • Удобно для отладочных точек входа
  • Которые остаются недоступными для штатного запуска

Важно

  • В Java-коде метод без указания досупа НЕ становится public
  • Одна из целей Kotlin-а - сделать JVM-программирование более лаконичным и удобным
  • В силу этого по умолчанию методы в Kotlin становятся публичными
  • Но это не совсем стыкуется с дизайн-принципом максимальной закрытости
  • "Метод должен иметь минимально необходимый уровень доступа"
  • Легко пролить в публичное API служебный метод

Параметры main

  • JVM требует массива строк в качестве параметра
  • Чтобы передать аргументы командной строки
  • Часто они неинтересны
  • Kotlin дает упрощенный вариант
  • За кулисами он породит метод с параметром - массивом строк
  • Впишемся в контракт, полученные аргументы проигнорируем

Вызов println

  • println выглядит как вызов библиотечной функции
  • Но "просто" функций в JVM нет
  • Есть библиотечный класс java.lang.System
  • В нем есть публичное статическое поле out типа java.io.PrintStream
  • И у него есть метод println

Вызов println

  • println("Hello") превратится во время исполнения в java.lang.System.out.println("Hello")
  • Это не только удобство
  • Это уход закладки на платформу в коде
  • Код, использующий println("Hello"), можно использовать в контексте KotlinJS или KotlinNative

Типы данных

  • В JVM есть разделение между примитивными типами и классами
  • Примитивные целые: byte, short, int, long
  • Примитивные вещественные: float, double
  • Примитивный символьный: char
  • Примитивный логический: bool
  • Примитивный пустой: void
  • Строковый - объект класса java.lang.String

Типы данных

  • Kotlin переносит целые, вещественные и логические целиком к себе
  • Со всеми их свойствами и синтаксической поддержкой
  • Названия типов-аналогов в Kotlin начинаются с большой буквы
  • На уровне языка это классы
  • Компилятор прилагает максимальные усилия к сохранению эффективности во время исполнения
  • На уровне байткода данные хранятся в примитивных типах
  • Иногда это можно поломать - будем отмечать такие опасные места

Типы данных

  • Размеры целых зафиксированы
  • Byte - 8 бит, Short - 16, Int - 32, Long - 64
  • Все - знаковые
  • Целочисленный литерал с суффиксом L - Long
  • Тип целочисленного литерала без суффикса определяется по значению и по контексту

Типы данных

  • Если по контексту ожидается конкретный тип и литерал влезает в диапазон - будет этот тип
  • Если по контексту не ожидается конкретный тип и литерал влезает в диапазон Int - будет Int
  • Если по контексту не ожидается конкретный тип и литерал влезает в диапазон Long - будет Long
  • Если литерал не влезает в диапазон Long - будет ошибка

Приведение целочисленных типов

  • Разные правила для присваивания (в широком смысле) и для вычислений внутри выражений
  • В иерархии объектов Byte/Short/Int/Long - "братья"
  • Поэтому при присваивании нет автоматического приведения
  • Даже если более "узкий" тип присваивается более "широкому"
  • При вычислении аргументы приводятся к более "широкому" типу, но не менее, чем к int

Пример



fun main() {
    val v: Int = 5
    println(v + 1)
}

Пример



fun main() { 
    val v = 0x12  // выведение типа
    println(v + 1)
}

Пример



// в комментариях - неработающие варианты

fun main() {
    val v1: Byte = 12
    val v2: Byte = 1
  //  val v3: Byte = v1 + v2 
  //  val v4: Short = v1 + v2
    val v5: Int = v1 + v2
  //  val v6: Long = v1 + v2
}

Разбор

  • Byte + Byte дает Int
  • И поэтому не приводится к Byte
  • И к Long - тоже не приводится
  • Потому что при присваивании нет "расширяющего" приведения целых
