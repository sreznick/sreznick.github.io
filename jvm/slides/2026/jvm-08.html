Задача: источник данных

// Два одинаковых контракта для разных типов
interface IntSource { fun nextOrNull(): Int? }
interface StringSource { fun nextOrNull(): String? }

// Один контракт с параметром типа
interface Source<T : Any> {
    fun nextOrNull(): T?
}

В этой модели null означает конец источника. Поэтому T ограничен Any.

Реализация и обобщённая функция

interface Source<T : Any> { fun nextOrNull(): T? }

class ListSource<T : Any>(items: List<T>) : Source<T> {
    private val iterator = items.iterator()
    override fun nextOrNull(): T? =
        if (iterator.hasNext()) iterator.next() else null
}

fun <T : Any> first(source: Source<T>): T? = source.nextOrNull()

val source = ListSource(listOf(10, 20))
val firstItem: Int? = first(source) // 10
val secondItem: Int? = first(source) // 20
val end: Int? = first(source) // null

Параметр T связывает тип источника с типом результата.

Ограничения: что алгоритм требует от T

fun <T> describe(item: T): String
    where T : CharSequence, T : Comparable<T> =
    "length=${item.length}, compare=${item.compareTo(item)}"

fun <T : Comparable<T>> List<T>.maximumOrNull(): T? {
    val iterator = iterator()
    if (!iterator.hasNext()) return null
    var maximum = iterator.next()
    for (item in iterator) if (item > maximum) maximum = item
    return maximum
}
val maximum = listOf(1, 3, 2).maximumOrNull() // 3

Ошибка проектирования: изменяемый список

val ints: MutableList<Int> = mutableListOf(1, 2)
// Ошибка: val numbers: MutableList<Number> = ints

// Если бы присваивание было разрешено:
// numbers.add(3.14)
// val value: Int = ints.last() // В списке оказался бы Double!

// Один объект имеет две ссылки. Запись через широкую ссылку
// должна оставаться безопасной для узкой ссылки.

MutableList<T> инвариантен: отношение Int <: Number не переносится на MutableList.

Шаг 1: источник только читаем

fun copyNumbers(
    from: MutableList<out Number>,
    to: MutableList<Number>
) {
    for (item in from) to.add(item)
    // Ошибка: from.add(3.14)
}
val ints = mutableListOf(1, 2)
val numbers = mutableListOf<Number>()
copyNumbers(ints, numbers) // OK

out запрещает опасную запись через from. Сам исходный список остаётся изменяемым.

Шаг 2: обобщаем перенос

fun <T> transfer(
    from: List<T>,
    to: MutableList<in T>
) {
    for (item in from) to.add(item)
    val existing: Any? = to.firstOrNull()
    // Ошибка: val typed: T = to.first()
}
val ints = listOf(1, 2)
val numbers = mutableListOf<Number>()
val objects = mutableListOf<Any>()
transfer(ints, numbers)
transfer(ints, objects)

List уже объявлен с out T. Проекция in T допускает приёмник T и его супертипов.

Шаг 3: вариантность в контракте

interface Source<out T : Any> { fun nextOrNull(): T? }
interface Sink<in T> { fun accept(item: T) }

fun <T : Any> transfer(source: Source<T>, sink: Sink<T>) {
    while (true) {
        val item = source.nextOrNull() ?: return
        sink.accept(item)
    }
}
// Source<Int> подходит вместо Source<Number>.
// Sink<Number> подходит вместо Sink<Int>.
// null означает конец источника; в sink передаётся только T.

Declaration-site вариантность задаётся один раз в объявлении интерфейса.

Сквозной пример: запускаем перенос

val values = mutableListOf<Number>()
val sink: Sink<Number> = object : Sink<Number> {
    override fun accept(item: Number) { values.add(item) }
}
val source: Source<Int> = ListSource(listOf(10, 20))

val numbers: Source<Number> = source // out
val intSink: Sink<Int> = sink        // in
transfer(source, sink)               // Тип T выводится из аргументов
// Ошибка: val wrong: Source<Int> = numbers
println(values) // [10, 20]

Source, ListSource, Sink и transfer — контракты с предыдущих слайдов.

Три вида вариантности

  • Ковариантность: Source<Int> — подтип Source<Number> (out)
  • Контравариантность: Sink<Number> — подтип Sink<Int> (in)
  • Инвариантность: MutableList<Int> не подтип MutableList<Number>
  • Use-site: ограничиваем операции проекцией в месте использования
  • Declaration-site: задаём отношение типов в объявлении API

Read-only и immutable — разные обещания

// Ошибка: readOnly.add(3.14)

List не предоставляет запись через эту ссылку. Он не гарантирует неизменяемость объекта или элементов.

Проекции инвариантного Array

fun <T> copy(from: Array<out T>, to: Array<in T>) {
    require(to.size >= from.size)
    for (i in from.indices) to[i] = from[i]
}
val source: Array<Int> = arrayOf(1, 2)
val target: Array<Number> = arrayOf(0, 0)
// Ошибка: val bad: Array<Number> = source
copy(source, target)
val output: Array<out Number> = source
// Ошибка: output[0] = 3.14
val input: Array<in Int> = target
val item: Any? = input[0]

out ограничивает запись, in — тип результата чтения. Проекции не создают копии.

Тип функции контравариантен по параметрам и ковариантен по результату.

Граница правила «out — только возвращает»

interface Source<out T : Any> {
    fun nextOrNull(): T?
    fun forEach(action: (T) -> Unit) // Допустимо!
    // Ошибка: fun accept(item: T)
}

// В action тип T — параметр функции: отрицательная позиция.
// Сам action — параметр forEach: ещё одна отрицательная позиция.
// Два изменения направления дают положительную позицию T.

// Источник вызывает action со своими T; пользователь
// не может передать через action новый элемент в источник.

Позиция считается по всей вложенности типов, а не только по внешнему параметру метода.

Аргументы и ожидаемый тип

Smart cast: информация из потока управления

fun lengthOrZero(value: Any?): Int {
    if (value !is String) return 0
    return value.length // Здесь value рассматривается как String
}
fun local(input: String?): Int {
    var text = input
    if (text != null) return text.length // Локальная var: OK
    return 0
}
class Holder(var text: String?)
fun property(holder: Holder): Int {
    // Ошибка: if (holder.text != null) return holder.text.length
    val snapshot = holder.text
    return if (snapshot != null) snapshot.length else 0
}

Свойство var может измениться между чтениями. Сохраняем значение в локальный val.

Nullable

  • Отсутствие значения — часть контракта
  • Ранний выход, Nothing и границы защиты
  • Когда null недостаточно для модели данных

Nullable в алгоритме переноса

fun <T : Any> transfer(source: Source<T>, sink: Sink<T>) {
    while (true) {
        val item = source.nextOrNull() ?: return
        sink.accept(item) // item: T, не T?
    }
}
// ?: вычисляет правую часть, только если слева null.
// return не даёт продолжить выполнение с отсутствующим item.
// T : Any гарантирует: null — конец, не элемент данных.

Один контракт связывает обобщение, вариантность, выведение типа и nullable.

Безопасный вызов и значение по умолчанию

data class User(val name: String, val email: String?)
fun emailLabel(user: User?): String = user?.email ?: "No email"
fun printEmail(user: User?) {
    user?.email?.let { email -> println(email) }
}
fun describe(items: List<String?>?, fallback: String): String {
    return items?.firstOrNull()?.uppercase() ?: fallback
}
// ?. пропускает вызов при null; ?.let запускает блок при наличии.
// ?: может скрыть различие нескольких причин отсутствия.

Используйте значение по умолчанию, если причины отсутствия действительно равнозначны.

Nothing и ранний выход

fun length(text: String?): Int {
    val value = text ?: return 0
    return value.length
}
fun required(text: String?): String =
    text ?: throw IllegalArgumentException("Text required")
fun fail(message: String): Nothing = error(message)

// У Nothing нет значений: функция с таким результатом не вернётся.
// Nothing — подтип любого типа; у Nothing? есть значение null.
// return и throw имеют тип Nothing.

Поэтому ветка return/throw не делает результат Elvis nullable.

Границы null safety

fun validateArgument(text: String?): String = requireNotNull(text)
fun validateState(text: String?): String = checkNotNull(text)
fun assertPresent(text: String?): String = text!!

// При null:
// requireNotNull — IllegalArgumentException: неверный аргумент
// checkNotNull   — IllegalStateException: неверное состояние
// !!            — NullPointerException

// Platform type из Java: String! — обозначение IDE, не синтаксис.
// Java может вернуть null; аннотации nullability улучшают проверку.
// Нарушение порядка инициализации тоже может привести к NPE.

Выбирайте проверку по смыслу ошибки; !! не доказывает наличие значения.

Java interop: platform type

val raw = Legacy.name() // IDE: String!; фактически null

// Ошибка в runtime: raw.length

Java-метод без аннотаций: static String name() { return null; }. На границе API полезно выбрать явный nullable-контракт.

Когда T? недостаточно: Stack<String?>

sealed interface PopResult<out T> {
    data object Empty : PopResult<Nothing>
    data class Value<T>(val item: T) : PopResult<T>
}
fun describe(result: PopResult<String?>): String = when (result) {
    PopResult.Empty -> "Stack is empty"
    is PopResult.Value -> "Popped: ${result.item}"
}
val empty: PopResult<String?> = PopResult.Empty
val nullItem: PopResult<String?> = PopResult.Value(null)
// У T? при T = String? нет отдельного «второго null».
// Результат pop(): T? смешал бы пустоту и извлечённый null.

Либо запрещаем nullable-элементы через T : Any, либо явно моделируем два разных состояния.

Nullable, Optional, Option: выбираем контракт

  • Kotlin T?: встроенная проверка null, ?. и ?:; для Int? на JVM возможен boxing
  • Java Optional<T>: библиотечная обёртка и методы map/flatMap/orElse
  • Scala Option[T]: библиотечные Some/None, map/flatMap и разбор через match
  • Kotlin when различает null и значение; sealed-типы различают дополнительные состояния
  • Производительность зависит от представления данных и оптимизаций JIT — нужны измерения

Nullable удобен для одного состояния отсутствия. Несколько разных состояний требуют более явной модели.

Что должно остаться после лекции

  • Обобщение связывает типы входов и результатов; bounds задают нужные операции
  • Вариантность описывает безопасную подстановку; проекции ограничивают операции
  • Позиция типа зависит от всей вложенности, включая функциональные типы
  • Выведение решает ограничения; smart cast использует проверки потока управления
  • Nullable описывает одно отсутствие; отдельные состояния моделируем явно
